# Permissions: the tool gate

> Covers how pi-foreman decides every tool call: the permission files, the order of the steps, default allow, the judge-first list and the judge, the floors, the owner dialog, child asks, protected targets, the decision log and the config keys.
> Read it when a call is denied or asks and you expected it to run.
> The floors run first and nothing here (judge, dialog) can allow what a floor refuses.

pi-foreman decides tool calls with its own gate, `extensions/core-adapter/gate.ts` plus the judge step in `index.ts`. It is the first `tool_call` handler in load order and decides every tool call of every session kind. The default is **allow**: a call that no floor, protected target or judge-first entry names runs. Only a few kinds go to a cheap [judge](#the-judge) first (the [judge-first list](#the-judge-first-list): losing local work through git, git settings and remotes, typing into another terminal pane, a whole-filesystem scan, a delete or write whose target the harness cannot read, a child's write whose target cannot be resolved). A clear from the judge runs the call; anything else asks you in a dialog (a child asks its parent), except a child's write whose target cannot be read, which is refused with the judge's reason when the judge does not clear it and the line has no other judge-first label (its labels are only `danger-write-outside` and `danger-unknown-write-target`). Deploys, forge writes, installs, network writes, process control, MCP actions, opaque lines and the rest run with no judge call. Reads, GET fetches, routine git, role launches and PR creation never ask.

A guard rail, not a sandbox: a prompt-injected agent can still find commands the parser marks opaque. An opaque line runs unless a floor reads it: the floors run on the raw text, so obfuscation reaches a deny or a question, not an allow. What the floors and the judge-first list do not name is allowed.

## Files and locations

One short JSON file holds the whole policy. Three files can exist; all use the same keys.

| File | Location | What it may contain |
|---|---|---|
| user | `<agentDir>/pi-foreman/permissions.json` | every key: `protected`, `additionalDirectories`, `workFolders`, `floors.noteTools`, `classifier.deny` |
| project | `<main checkout>/.workflow/permissions.json` | `protected`, `additionalDirectories` and `classifier.deny` (the first two only when the file is trusted, see the trust rule) |
| tracked | `<worktree>/.pi/permissions.json` | `classifier.deny` only |

A missing user file is an empty policy. The project file lives in the **main checkout**, found with `git worktree list`, so every worktree of a repository shares it.

The keys `mode`, `allow`, `ask`, `deny`, `classifier.allow` and `profiles` were removed. A file that still holds one is read, the key is ignored, and `/foreman doctor` prints one INFO line per key and file (`INFO permissions: <file> <key> is no longer used and is ignored`). Nothing else in the file is affected.

```json
{
  "additionalDirectories": ["~/reference"],
  "classifier": { "deny": ["Anything that touches the production database."] },
  "protected": [{ "host": "prod-db", "note": "production" }],
  "workFolders": [{ "path": "~/git", "mode": "auto" }]
}
```

- **The trust rule of the project file.** `.workflow/permissions.json` is yours alone: it must be untracked and ignored by git (`git ls-files --error-unmatch` fails and `git check-ignore` succeeds) and neither the file nor `.workflow` may be a symbolic link. Only then are its widening keys honoured (`additionalDirectories`, `protected`). Otherwise the file is tighten-only (`classifier.deny`) and one notice says why. Add `.workflow/` to `.git/info/exclude` to make it trusted. A file anyone can push cannot widen what the gate allows.
- **The tracked file** `.pi/permissions.json` is reviewed code that every contributor can change, so it can only tighten: `classifier.deny`. Other keys are dropped with one notice.
- **Invalid files.** An invalid user file (not JSON, wrong shapes) contributes nothing and the other files still apply; an invalid project or tracked file contributes nothing. One in-session notice names the file and the error at the first gate decision, and `/foreman doctor` warns. A bad entry inside a valid file (an unparseable rule, a sentence over 300 characters, a non-string) is skipped on its own, with a notice that names it.
- **Reading.** The files are read at the first decision and again when their modification time changes. A child re-reads them at each decision, so an edit applies to running children.
- **`floors.noteTools`** (user file only; a project or tracked file's value is dropped with the usual notice): a list of tool names whose prose fields are notes, not commands, so the command floors skip them. Built-in list, always on: `scratchpad` (note in `text`) and `memory_write` (note in `content`), the note tools of the public `pi-memory` package. The key adds to it (there is no removal), and it goes **by tool name**: any extension that registers a tool of a listed name gets the exemption. Only the prose fields (`text`, `content`, `note`, `message`, `markdown`, `brief` and the other free-text names of the gate) are exempt; path-like fields keep the secret-path floor and every other string field is read as a command (see [Notes are not commands](#floors)). Example: `{ "floors": { "noteTools": ["my_journal_add"] } }`.
- **Protected.** The agent cannot write any of the three files (floor, see [Floors](#floors)); you edit them.
- `additionalDirectories` (user and trusted project file, `~/` and relative paths allowed; relative means to the main checkout) are added to the owned roots, which widen reads and count as inside for role launches.

## Removed: pattern rules and the prose whitelist

The `allow`, `ask` and `deny` rule lists (`Bash(...)`, `Read(...)`, ...) and the allow sentences (`classifier.allow`, `A1..`) are gone. No rule decides a call any more: the default is allow, and the judge-first list names what is looked at. A file that still sets one is read and the key is ignored with a doctor INFO. To stop a call, use a [protected target](#protected-targets) or a `classifier.deny` sentence (which only the protected-target check reads). The remember step of the dialog is gone too: there is nothing to remember into. This stub stays until the docs that still describe the old rules (Built-in allows, Config keys, Migration) are cleaned up.

## The steps

Every call goes through these steps, in this order. Each step ends the call or passes it on.

1. **Parse.** `shellast.ts` parses `bash` input with `unbash` into segments: the commands of chains, pipelines, `$(...)`, backticks and subshells, the operands of `[[ ]]` and the word lists of `select` (with the substitutions inside them), `bash -c`/`sh -c`/`eval` with a literal string, and the wrappers `env`, `timeout`, `nice`, `nohup`, `xargs`, `time`, `command`, `stdbuf`, `setsid`, `watch`, `flock -c`. Each segment has its argv, redirect targets, heredoc presence and effective cwd. Variables resolve only through the closed grammar of [Variables in bash lines](#variables-in-bash-lines). A segment the walker cannot state exactly is **opaque**: an unresolved variable, a glob in a target, a process substitution, a runner with a non-literal script, nesting deeper than 4, a parser error, `trap`, a function body with positional parameters, `shift` or a folder change (judge-first; any other body is walked at each call, and a call walks every body of that name, whatever the order of the definitions), an `alias` definition (judge-first, its text walked), an assignment outside a short allowlist of harmless names, a shell fed by heredoc or stdin, and PowerShell or cmd. The `powershell` tool is one opaque segment; its words are checked as write targets (see Install roots below), and they never make it free. Quoted string arguments of a parsed segment are data, not commands.
2. **Floors.** A deny with a reason that names the allowed alternative. No judge, dialog or owner answer lifts it. See [Floors](#floors). One kind of floor hit asks instead of denying: a text match on an opaque line (below).
3. **Self-modification rules.** Writes that change how Pi or pi-foreman runs (the project's `.pi/settings.json`, the agent `settings.json`, pi-foreman session state, the session dir) are a dialog by rule, never cleared by the judge. A child or headless session is denied with the rule name. On Windows every self-modification rule folds trailing dots and spaces of each path component (`.claude.\settings.json` is `.claude\settings.json`). Known limit: a stream suffix on a folder component (`.claude::$INDEX_ALLOCATION\settings.json`) is not folded.
4. **Install roots and protected targets.**
   **Install roots (`install-root-write`).** Directly after the self-modification rules, before the protected check, the built-in allows and the judge-first list, a write the gate can name into the Pi install folder, the global npm root, a bundled package folder or the pi-foreman package folder opens the owner dialog (cause `install-root-write`, no remember choice). No judge verdict clears it, and a headless session or an owner who is away is denied. A child is refused earlier (`child-write-outside`). It sees the write and edit tools, `foreman_move` and `foreman_copy` destinations, and the write targets of a shell line: redirects, `cp`, `mv`, `rm`, `tee`, `sed -i`, `dd of=`, `tar -x -C`, `unzip -d`, `patch -d`, `perl -i`, `rsync`, and a run that changes "somewhere under" a root through `cd`, `-C`, `make -C` or `--prefix`. Newly asked, because the built-in rules accept a test run only at the worktree root and reject `-C` and `--prefix`: `cd <root> && make`, `cd <root> && npm test`, `git -C <root> pull`, `git -C <root> fetch`, `npm --prefix <root> test`. Not asked: reads (`cat`, `ls`, `grep`, the read tool), a segment with no redirect into a root that a built-in read, git-read, plain `git fetch` or build-test rule accepts (`cd <root> && git fetch origin`), and forms that name no folder (`npm install -g x` runs). The package root is wherever the harness runs from: a session that works in another worktree and changes that checkout (`git -C <checkout> pull`) is asked; a session whose own worktree is that checkout is not, nor is a path inside the session's own worktree. The test is by path spelling, so no symlinked spelling is followed: neither a symlink inside the worktree that points into a root, nor a symlinked spelling of the round worktree or of a root (a temp folder reached through two spellings), and `pushd <root>` is not tracked (`cd` is). These are known limits; the read-only role fence (`child-readonly-write`) compares the worktree by spelling in the same way. A `powershell` line is split into words with no cmdlet knowledge (quotes and backtick escapes honoured; `;`, `|`, `&`, `<`, `>`, brackets, `,` and `=` end a word; `~`, `$HOME`, `$env:USERPROFILE`, `${env:USERPROFILE}` and `%USERPROFILE%` at the start of a word are the home folder; both separators), each word is resolved against the cwd, and every word counts as a write target of this step (the session's own worktree is exempt): the owner is asked, a child is refused as `install-root-write` in every mode. The same words meet the secret-path floor and the self-modification rules, each with the outcome a bash write to that path gets: the owner is asked, a child is refused, and what bash may write stays free (`.pi/scratch`, `.pi/tasks`, the child's own handoff files). A child's word inside a `.git` folder is refused as a bash write there is (`child-write-outside`); for the owner it is no verdict. A child's `powershell` word outside its worktree is not refused by the gate except inside `.git`, an install or package folder, a secret path and the self-modification paths (the rules of step 3 above, "Self-modification rules"; among them the agent `settings.json` and `extensions/`, the pi-foreman `state/` folder and the project's `.pi`); it runs (the `danger-opaque` label is gone; bash refuses these with `child-write-outside`), and the same holds for a read-only child's word in `.pi/scratch` and `.pi/tasks`. A file inside a session folder, another session's folder, the `handoffs` folder itself, a file in another session's handoff folder and other files under the agent folder stay free for a child's `powershell` word, apart from the auth file and a handoff's `live.json`, `parent` and `child` files; the session's own folder and its parent folders up to the agent `sessions` folder, the agent folder itself and the harness folders and files the rules name (`extensions`, `npm`, `agents`, `intercom`, `claude-config`, `foreman.json`, `claude-bridge.json`) are not free. The own-ruling refusal runs on the line as before. A word never earns an allow. Because every word counts as a write, a read of an install or package folder asks the owner and is refused for a child, and a search pattern that looks like a protected path is treated as one. Not seen: words built from variables or string joins, here-strings, quoted nested scripts (`pwsh -c "..."`, `iex '...'`, `cmd /c "..."`, encoded commands), provider prefixes and `\\?\` paths, environment folders other than the home spellings, and a relative word after a directory change.
   **Protected targets.** A call that touches a [protected target](#protected-targets) (and passed the floors and the self-modification rules) goes to the protected check instead of the built-in allows and the judge-first list.
5. **Floor asks.** An opaque-line floor ask (an opaque line that names a permissions file, a child push, a remote, a force or protected-branch push, or the foreman config next to a gate key) opens the dialog here.
6. **Built-in allows.** A call that a [built-in allow](#built-in-allows) names runs.
7. **Judge-first list.** What is left is checked against the [judge-first list](#the-judge-first-list). A hit goes to the [judge](#the-judge): a clear runs the call, anything else opens the dialog (a child asks its parent). One exception: a child's line whose judge-first labels are only `danger-write-outside` and `danger-unknown-write-target` is refused with the judge's reason when the judge does not clear it, and nobody is asked. **No hit: the call runs** (default allow).
8. **Dialog or deny.** An escalation opens the [owner dialog](#the-owner-dialog), in a child's case in the parent's pane. The dialog waits for the owner. With nobody to ask (no pane) it is a deny that says nobody is at the session.
9. **Decision log.** Every decision is one JSON line. See [Decision log](#decision-log).

**Path spelling.** For the tools `read`, `write`, `edit`, `ls`, `grep` and `find`, the gate reads the path fields the way Pi's tool does (`pathnorm.ts` `toolPath`, the same steps as Pi's own function): a leading `@` is dropped, `~` and `~/` mean the home folder, `file://` is a path, unicode spaces become a space, then the path is joined to the cwd. The result is what the floors, the self-modification rules, the child fence, the path allows and the judge-first list see, so a tilde, at-sign or file-link spelling gets the verdict of its plain spelling, in both directions (a child's `~/…/result.md` of its own handoff folder is allowed; `@/tmp/x` is refused as `/tmp/x` is). A malformed `file://` link cannot be read and is denied (`tool-path-unreadable`). Words in a shell line are not changed (`@` and `file://` stay literal, `~` stays unresolved), and the `foreman_move` and `foreman_copy` fields are read as written. Known limits: symlinked and `..` spellings of the handoff folder, and the extra spellings that the read tool accepts.

A handler failure denies (fail safe). A call with no session to decide it in is denied. When the session could not start (a reload after the install moved loads a changed module), the owner gets a "Restart Pi" notice and the refusal names that start failure instead of the generic reason; the start is not retried.

## Default allow

There are no permission modes. The old `auto`, `ask`, `allow` and `deny` modes, the `/foreman perms mode` command, the footer mode and profiles are gone. The gate is one fixed flow:

1. A floor refuses (no judge and no dialog lifts it).
2. A self-modification rule, an install-root write, a floor ask or a protected target asks the owner (a protected target runs the protected-target check first).
3. A built-in allow runs the call.
4. A call on the [judge-first list](#the-judge-first-list) goes to the [judge](#the-judge): a clear runs it; unsure, invalid or failed asks the owner (the foreman gets the dialog, a child asks its parent). A child's line with only the labels `danger-write-outside` and `danger-unknown-write-target` is refused instead, with the judge's reason.
5. Everything else runs.

The dialog has two answers: **allow once** (nothing is stored) and **deny** (with a comment, or with "stop"). Nothing is remembered.

A leftover `mode`, `profiles`, `allow`, `ask`, `deny` or `classifier.allow` key in a permissions file is accepted and ignored; `/foreman doctor` prints one INFO line per key. The `gate.mode` and `permissions.profile` config keys have no effect (see [Config keys](#config-keys)). The `--profile` option of the session launcher is accepted, ignored, and prints a notice on stderr.

## The judge-first list

A built-in list (`JUDGE_FIRST` in `defaults.ts`, plus the judge-first hits in `floors.ts`). A call that falls into one entry goes to the judge before it runs. The first entry names the call in logs, dialogs and the judge prompt.

A line that falls into several entries carries every label (`dangers`, e.g. `danger-inline-code+danger-remote`). The labels `danger-remote`, `danger-remote-command`, `danger-delete-unknown-target` and `danger-unknown-write-target` keep the task text from the judge (see [the judge](#the-judge)).

| Id | What it matches | Example |
|---|---|---|
| `danger-git` | Losing local work or changing git history: `reset --hard`, `clean -f` and `clean -e`/`--exclude`, a `checkout` or `restore` that discards changes, `switch -f`, `branch -d/-D` (except a merged branch: `default-git-branch-merged`), `rebase`, `commit --amend`, `stash drop\|clear`, `worktree remove\|prune`, `filter-branch`, `filter-repo`, `reflog expire`, `gc --prune`; for both roles the program-running options `--upload-pack` on `fetch`, `pull` and `clone` (and clone's `-u`), `--receive-pack` and `--exec` on `push`, and the verbs `send-pack`, `http-push` and `credential fill`; for a subagent only, the forms that move, overwrite or delete a branch, ref, tag or worktree entry shared with the main checkout: `update-ref`, `prune`, `reflog delete`, `tag -d\|--delete`, `branch -f\|--force\|-m\|-M\|--move\|-C`, `switch -C\|--force-create`, `checkout -B`, `worktree add -B`, `worktree move`. Not a complete list | `git reset --hard HEAD~3` |
| `danger-git-config` | Git settings and remotes: `git config` writes (any scope, `-c k=v`, `clone -c`, `--config`, `--config-env`, `GIT_CONFIG_*`, editing `.git/config`) to the keys in `git-floor-keys.json` (hooks path, ssh command, credential helper, `url.*.insteadOf`, remote urls, push configuration), a computed key, `config --edit`, `git remote add\|set-url\|rename\|remove\|set-branches\|set-head`. It used to be a deny | `git config core.hooksPath x` |
| `danger-inject` | Typing into another terminal pane (`herdr pane send-keys\|send-text`, `tmux send-keys`, `osascript` keystrokes): a line that starts with `/` (a slash command), a payload of 2 characters or fewer (a dialog answer), a key name (`Enter`, `Escape`, `C-x`, ...). Ordinary text is judged like the rest. It used to be a deny | `herdr pane send-text 2 '/clear'` |
| `danger-fs-scan` | A whole-filesystem scan: `find /`, `grep -r ... /`, `du /`, `ls -R /` with a root at `/`, the home folder or a parent of the workspace. A relative or in-worktree root is none. It used to be a deny | `grep -r token ~` |
| `danger-delete-unknown-target` | A delete whose target the harness cannot read: a variable, a glob without a readable directory, an empty or substituted operand, a changed directory it cannot resolve, a remover under `xargs` or `find -exec`, a variable command word with a recursive flag, `find $X -delete`, `git clean` with a variable operand, a computed or `eval`/`sh -c` string, nesting deeper than the gate reads, a recursive PowerShell or cmd delete outside the worktree, scratch and `/tmp`, `Remove-Item @list`, a recursive-listing pipe into `Remove-Item`, `-EncodedCommand`, `iex` of a computed string. A resolved variable or glob inside the worktree, scratch or `/tmp` runs. Home, root and system targets are a [floor](#floors) first | `rm -rf $DIR/build` |
| `danger-unknown-write-target` | A write, truncation or recursive permission change whose target is a variable: `dd of=$X`, `chmod -R`/`chown -R` with a variable operand, `truncate -s 0 $X`, a `>` or `&>` redirect whose whole target is a variable (`echo > $F arg` runs). For a child that also carries `danger-write-outside`: when the judge does not clear it and no other label is on the line, it is refused, not asked (see that row) | `truncate -s 0 $LOG` |
| `danger-remote-command` | A command on another machine or in a container that would be refused if it ran locally: `docker`/`podman`/`kubectl` `exec`/`run` and `ssh` carrying `shred`, `find -delete`, disk tools, `git clean -e`, a variable redirect, a recursive `chmod`, `truncate`; a recursive `rm` in a container. (`danger-remote` already sends every such call to the judge; this entry names the kinds a floor-like reason covers) | `docker exec c rm -rf /data` |
| `danger-inline-code` | Code the harness cannot read: an interpreter one-liner (`python -c`, `python3 -c`, `node -e`/`--eval`/`-p`, `perl -e`, `ruby -e`, `php -r`, `deno eval`, ...), a `bash -c`/`sh -c`/`eval` script built at run time (`bash -c "$X"`), a program fed on stdin to an interpreter or a shell (`python3 - <<EOF`, `bash <<'EOF'`, `echo code \| node`, `echo cmd \| bash`, `busybox sh <<'E'`, `echo cmd \| toybox sh`), and a script run by a shell the walker does not parse (`zsh -c`, `fish -c`, `pwsh -c`, `cmd /c`, `script -c`). A literal `sh -c 'cmd'` is read by the walker, not labelled. Plain `python script.py` and `node file.js` run. Known gaps (no structured source, so they run): an unquoted variable that splits into words (`V='rm -rf x'; $V/bin/ls`, a literal last path part names the program), and `osascript -e` code other than keystrokes; a variable or substitution program (`$PY -c ...`, `$(which rm)`) is judged as `danger-unknown-program` | `python3 -c "import os; ..."` |
| `danger-unknown-program` | The shell parse cannot say which program runs in a segment, for every role (a read-only reviewer or explorer too; the judge asks the owner or the parent when it does not clear). Marked by the parser (`programUnknown`, not from text): a program word with a non-literal last part (`E=sh; $E -c 'rm ...'`, `"$E" x`, `${E}h`, `$(echo ls) -la`, `{rm,-rf,x}`; `$V/bin/pip` and `~/bin/tool` name their program and run), a wrapper option or argument the walker does not read (`env --ign rm ...`, `env -S '...'`, `timeout $T ...`, `command --x rm ...`, `ionice`, `chroot`, `unbuffer` and `parallel`, whose wrapped program is not read; `busybox` reads a literal applet word as the program, so `busybox sh -c '...'` is walked as `sh -c` and `busybox ls` runs), `env` settings whose name is no shell identifier (`env 'BASH_FUNC_x%%=...' sh -c ...`; every operand with an `=` before the program is a setting, as `env` itself reads it), `builtin exec -c sh -c ...` (a `builtin` with an argument; `builtin` is not unwrapped), `find ... -exec $C {} +`, and arithmetic or a subscript on a value not shown to be a number (`echo $((a+1))`, `(( x + $(id) ))`, `read x < f; : $(( x ))`, `unset "$x"`, `${!x}` on an unknown name). A value is shown to be a number when it is a literal, `$?`/`$#`/`$$`/`$!`/`$-`, a counter such as `RANDOM`, or a name with a lowercase letter whose every binding on the line is a plain decimal or arithmetic assignment (`n=0; n=$((n+1))`, `for ((i=0;i<3;i++))`); a name the environment sets (`COLUMNS`, `start` read from nowhere) is not. An earlier label wins (`E=env; $E -i rm -rf ~/x` stays `danger-delete-unknown-target`) | `E=sh; $E -c 'rm x'` |
| `danger-kill-pattern` | Stopping processes by name or pattern: `pkill`, `killall` (program basename, also behind `env`, `nohup`, `busybox`, a function body or a `$V/bin/pkill` path), for every role. `kill <pid>`, `kill $!`, `kill %1`, `taskkill` and `pgrep` run with no judge call | `pkill -f node` |
| `danger-remote` | Any command on another machine or in a container: `ssh <host> ...`, `docker`/`podman` `exec`/`run`, `kubectl exec`/`run`, whatever the command is. The judge reads the line; a clear runs it, anything else asks the owner (a child's parent) | `ssh host uptime` |
| `danger-write-outside` | A **child's** shell write whose target cannot be resolved (a variable, a substitution, `~`, a brace list, a changed directory), so it may lie outside its worktree. A resolved target outside the worktree and scratch is the floor `child-write-outside`. The foreman's shell writes are decided by the shell-write guard. The judge reads the line; a clear runs it. When it does not clear it (unsure, timeout, invalid verdict, provider error, no model) and the line's only labels are this one and `danger-unknown-write-target`, the call is refused with the judge's reason and the way out (a literal path in `$FOREMAN_SCRATCH` or `$FOREMAN_OUT`, the worktree for a role that may write it, or report the line); the parent is not asked, and one gate-log record (layer `rule`, rule `danger-write-outside`, verdict `deny`) is written. A line that also carries another label (inline code, git, a remote command) keeps the parent's question | `echo x > $OUT/f` (child) |

**Floors that stay.** `git show`/`git cat-file` of a revision path `<rev>:<secret>` or `:<secret>` (`git show HEAD:.env`: `floor-secret-path`); a variable push destination with a colon (`git push origin HEAD:$B`; a colon-less `git push origin $B` runs); literal system deletes and the rare forms of them (`busybox`/`toybox rm -rf ~`, a shell function body, a `sh -c`/`eval` literal string, `Remove-Item -Recurse -LiteralPath:C:\Windows`: `floor-rm-system`); force, protected-branch, mirror and delete pushes; every push by a child that is not a builder; package publish; secret and key paths; the policy and config files; `sudo`, disk tools and `dd` to a device; a download piped into a shell; deletes outside the roots with a literal target. See [Floors](#floors).

**Forms the walker now reads.** Each form below is judge-first (a clear runs the call, anything else asks), and none is a new allow. A plain form next to it is unchanged.

- `[[ ... ]]` operands and `select` word lists are walked, so a command or process substitution in them is seen: `[[ -n $(rm -rf $HOME/x) ]]` is refused; `[[ -n $x ]]` and `select x in a b; do echo $x; done` run.
- Sourced streams: `. <(...)`, `source /dev/stdin`, `source -`, `source /dev/fd/0` and a `source` or `.` of a file a variable names (`. $HOME/.cargo/env`) are judge-first; `source ./env.sh` runs. `source <(curl ...)` is refused.
- `eval '(( x = $(...) ))'` (arithmetic on a value not shown to be a number, inside an `eval` text) is judge-first, as the same arithmetic written on the line is; `eval '(( x = 1 ))'` runs.
- Aliases: any alias definition is judge-first and its text is walked (`alias x='rm -rf'; x $HOME/y`, and the same after `shopt -s expand_aliases` or inside `eval "..."`); a plain `alias` listing runs. A dangerous alias text that a floor reads is refused (`alias x='rm -rf $HOME/y'; x`).
- Functions: a call walks every body of that name, whatever the order of the definitions (fail closed), so a redefined dangerous body is seen, also one defined later. A body with positional parameters, `shift`, or a folder change is judge-first at the call (`f(){ rm -rf "$1"; }; f $HOME/x`, `f(){ cd /outside; }; f; touch a`). `f(){ echo hi; }; f a` runs. The work is bounded: at most 64 body walks and 500 commands walked inside bodies per line, counted as they are walked (one large body is cut at 500 too); the floor side reads at most 1500 segments of bodies per line, and the judge-first rules read at most 1500 nested segments, bodies defined inside bodies included; past that a body is not read in full but is still held to the refusals (the delete, `chmod`, disk and PowerShell-delete floors, through a flat read of the body and of the bodies and wrapper words below it, capped at 1500 segments per line; the first body of each check is always read), so a refusal that a body gives stays a refusal whatever came before it, and the rest of the line is judge-first (never an allow). Nesting the parser rejects (`if`, `( )` or definitions nested past its limit of about 255 levels) and a line that overflows the walker's stack (`echo $((1+1+…))` with about 1,500 terms or more; a `(( ))` command survives 200,000) are not a syntax error, since a shell runs it: the line is unread and judge-first (`danger-delete-unknown-target`), and the text floors still run on the raw line, so `rm -rf ~` inside 300 nested blocks is refused or judged and a harmless `echo hi` in 300 nested `if` is judged. Other parse errors (an unbalanced quote, a stray `fi`) are unchanged: a shell runs nothing of them, the text floors and the restored checks of the statements before the error apply, and a harmless one is not judged. The gate has no timer: a call that runs long is not cut, and an error in it is a refusal (`gate-error`).
- `xargs` whose program or script comes from its input is judge-first: `xargs -I{} {}`, `xargs -I{} sh -c '{}'`, `xargs env`, `xargs sh -c`, `xargs bash`. `xargs grep foo`, `xargs -n1 echo` and `xargs -I{} cp {} dst` run.
- Look-behind: the words after a program the walker does not model (`caffeinate`, `taskset`, `strace`, any unknown name) are read as a command of their own. A floor hit or judge-first entry in them judges the line, and so does, for a child, a write outside the worktree. More than 32 words after such a program is judge-first, and so is a line that starts more than 1000 such reads in all. `caffeinate -i make` and `strace -c ls` run.
- `toybox` is read like `busybox`: `toybox rm -rf $HOME/x` is refused, `toybox ls` runs, and `toybox -x ...` (an option the walker does not read) is judge-first.
- An assignment before a command (`env X=1 git ...`, `X=1 git -C <outside> ...`, `X=1 touch /outside/f`) no longer hides the git, outside-write and checkout-write checks of the command after it. `env X=1 git status` runs.
- A relative script run after a folder the walker cannot state (`cd $D && ./x.sh`, `pushd $D; ./x.sh`, `eval 'cd $D'; ./x.sh`) is judge-first, and so is an `eval` that changes folder (`eval 'cd /outside'; rm -rf build`). `cd sub && ./x.sh` runs.

**What runs with no judge call.** These kinds used to be the "dangerous class" and went to the classifier. They now run: deploys (`kubectl apply`, `terraform`, ...; `ssh` and `docker`/`kubectl exec` are judged: `danger-remote`), forge writes (`gh pr merge`, `gh api` writes), network writes (`curl -X POST`, `nc`), installs (`npm install x`, `pip install`), process control (`kill 1234`, `taskkill`, `chmod -R` with a literal target; `pkill` and `killall` are judged: `danger-kill-pattern`), MCP actions (`mcp__chrome__click`), a launch outside the owned roots, an opaque line that no floor reads, whose program is stated and that is no inline code (an unresolved argument variable; a function body with positional parameters or a folder change is judged, see [forms the walker now reads](#the-judge-first-list); a program word built from a variable is judged: `danger-unknown-program`; an interpreter one-liner, `eval "$cmd"`, an interpreter or a shell fed on stdin and a foreign shell are judged: `danger-inline-code`), a line that names the harness folder (a write to the policy and state files is a floor), and a push of another branch, a tag or a URL that is not a force, protected, mirror or delete push. A resolved write outside the worktree by the foreman runs; the shell-write guard still refuses a shell write into project files.

A PR's draft state is changed by the harness only, in process, for a PR the session itself opened with `pr_create` (see [tools](tools.md#draft)). No model-facing tool does it. `gh pr ready` from a shell is a forge write like any other and runs.

`codemode` is not special: each call its script makes passes the gate on its own.

## The judge

One cheap model call for a judge-first call. It answers one question: is this call plainly what the owner is doing, or does it need the owner's yes?

- **When it runs.** Only for a judge-first hit that no floor, self-modification rule, install-root ask or protected target decided first. Never for a floor, a role launch or a call outside the list.
- **What it sees.** A fixed system text (one prompt for the whole list); the judge-first reason (`danger-git: ...`); the session kind, role, cwd, worktree, branch and remotes; your last message (cut to 600 characters, fenced); the task text of the agent, fenced and marked as written by an agent and not by you (see below); and the command in fences with a random nonce; with `gate.judgeReads` on, also the file text it asked for (see "What it may read"). For a child session the request also carries the real paths of the child's `$FOREMAN_OUT` and `$FOREMAN_SCRATCH` (and they are part of the cache key), so the judge can tell a write into its own folders from one outside them. Never the agent's tool output, never earlier history. The command, your message and the task text are data: nothing in them instructs the model. A script whose text is in the command (inline code, a heredoc body) is judged by what that text does; the `danger-inline-code` reason says "the code is in the command" for those cases and "runs code the harness cannot read" for the rest (stdin from a file, `cat s.py | python3`, a script the gate cannot resolve, a foreign shell).
- **The task text.** For a helper agent the judge gets the launch task its parent gave it, word for word as the agent received it (the first prompt of its first run, kept in a `pi-foreman-launch-task` session entry so a reload, a resume or a follow-up prompt does not replace it, and a forked launch still gets its own task, not the parent's history). For a child session it gets the brief (`brief.md` in its handoff dir, local or remote, without the report-back footer the harness appends; later briefs are not read). Every session, the owner's included, also passes its ledger (title and open items, cut to 800 characters). The launch task is cut to its first 2500 and last 1500 characters with a marker between. Both texts sit in their own fences with the call's nonce and are written by agents: they say what the session is for. A call that plainly carries out the task or a ledger item counts as asked for, like a call your message asks for. They never lift a rule: a delete, overwrite, reset or discard outside the session's own folders, a target that depends on a value the judge cannot see, and reading or sending credentials stay `unsure` whatever they say. The gate reads no words of this text; it only copies it. A misleading task can sway the judge on an ordinary call; that is an accepted gap, and the fixed floors still apply. Helpers placed on another machine in a terminal pane get no task text (they do not carry the harness settings).
- **Withheld task text.** When any judge-first label of the call is `danger-remote`, `danger-remote-command`, `danger-delete-unknown-target` or `danger-unknown-write-target` (every label of the line counts, not only the first), the request carries no task and no ledger (the blocks read "(not shown for this kind of call)") and the judge decides as it did before. `danger-write-outside` (a write with a partly unresolved target) is not withheld: the judge's own rule for an unseen value decides.
- **What it may answer.** One JSON object with a verdict `clear` or `unsure` and a reason of at most 200 characters; with reads on, a third verdict `read` with 1 to 8 `paths` asks for files first (at most two such rounds; the third answer must be `clear` or `unsure`). Only a well-formed `clear` runs the call. Every other answer asks the owner (a child's parent; a child's line with only the labels `danger-write-outside` and `danger-unknown-write-target` is refused with the judge's reason instead): `unsure`, extra fields, a timeout, a provider error or no model; an unreadable reply (invalid JSON, an empty reply) is asked for once more with the same request first, and asks only when the second reply is unreadable too. The parser stays strict. A child's call asks its parent.
- **What it may read.** With `gate.judgeReads` on (default), the judge may answer `read` with paths (absolute or relative to the cwd; a leading `~/` means the home folder, `$VAR` is not expanded; a path ending in `/` lists a folder, `#L<from>-<to>` shows a line window); the harness reads them and asks again with the file text in fences marked as data. The model asks in its answer, not through a model tool, so it works with every provider, the Claude bridge included. The gate reads no words of the command; the model names the paths. A path is shown only when its real path lies in the session's worktree, its cwd, a helper's own `$FOREMAN_OUT` or `$FOREMAN_SCRATCH`, or one of these parts of the Pi agent dir: `sessions/`, `agents/`, `skills/`, `prompts/`, `pi-foreman/`, `pi-subagents/`, `missions/`, `AGENTS.md`, `foreman.json`, `settings.json`. The agent dir rule wins when a project root contains the agent dir (so `extensions/`, logs, installs and backups there stay closed). The home folder, a folder above it and the disk root are never a readable place. A symlink or `..` that leads out is refused; a `..` is answered only when the path before it lies in a readable place and is not withheld (otherwise the answer is "outside", whether that folder exists or not); a file is opened without following a link as the last part of the path and checked again after the open. Never shown: secret and key paths (the secret-path floor), `.env` files, `auth.json`, `models.json`, `trust.json`, `mcp.json*`, bridge login and config data, `.git` and `.claude` folders, shell histories, `.pgpass`, `.vault-token`, `.htpasswd`, `kubeconfig`, `token.txt`, `*.token`, `secrets.*`, `secret.*`, `.secrets`, `token`, `service-account*.json`, `service_account*.json`, `client_secret*.json`, `*.tfvars`, `*.tfstate*`, `pi-foreman/remote/`, any file that is not a regular file and any file with more than one hard link. Caps: 16 KiB and 400 lines per file, 64 KiB of file text per decision, 16 paths per decision; a session transcript (`*.jsonl`) shows 40 lines of at most 1000 characters per slice; a binary file is not shown. All file text is masked for secret-looking values. The calls that withhold the task text get no reads, and the [protected check](#protected-targets) does not read files. The gate log row of a decision with reads lists the paths (root label and relative tail, with the outcome when the file was not shown; never content), the file text size and the rounds; the trace has only the number of reads and rounds. A cleared decision that used reads is reused only while every path asked for gives the same result again. Accepted gaps: a script can change after the judge read it and before it runs (the same holds for the command text); a process that swaps a parent folder for a link at the right moment can get a file outside the allowed folders read (the open refuses a link only as the last part of the path; the contents are masked, and only the judge's masked reason of at most 200 characters goes back to the agent); a file can contain text that tries to sway the judge (it is marked as data, and a file that tells the judge what to answer is a reason for `unsure`); masking finds common secret shapes only; a helper's judge can read other sessions' state in the allow-listed agent dir parts, and only the judge's short masked reason reaches the dialog. A worktree that lies inside the agent dir outside the allow list gets no reads there.
- **Cache.** A cleared call is cached for the session by tool, exact payload and the task and ledger text as sent. The [protected check](#protected-targets) has its own prompt, verdicts and cache.
- **Timeout.** `gate.reviewTimeoutMs` (default 15000, minimum 100). Each round's model call has this timeout (a decision with reads can take two or three calls). A timeout asks (a child's unreadable write is refused), with no retry.
- **Thinking level.** The `thinking` field of `providers.<p>.roles.review`, else the `:level` suffix of the model, else `high`; capped by `maxThinking`. The trace and the log row record the level actually used.
- **Model.** The `review` rung of the role map (`providers.<p>.roles.review.model`, `roles.review`), the inexpensive rung by default. The call uses no prompt cache and its usage is logged with role `classifier`.
- **No model configured.** The judge-first calls ask you directly. `/foreman doctor` and `/foreman setup` print `WARN no classifier model for provider <p>: ...` and the first judge-first call of a session shows the same text once. A child or headless session denies such a call; so does a child's unreadable write (`danger-write-outside`), and its refusal names that cause.
- **Your deny sentences.** `classifier.deny` sentences are read by the protected-target check only; the judge does not read them.

## Built-in allows

A built-in allow is a named rule that allows without a model. Since the default is allow, a built-in allow only matters before the judge-first list: it runs a call the list would otherwise judge (a merged branch delete, for example). This section stays until the table is removed. A shell line is allowed by built-ins only when every segment matches one and none is opaque; a segment on the judge-first list never matches. The shipped rules (`defaults.ts`):

| Rule | Allows |
|---|---|
| `default-own-tool` | pi-foreman's own tools that carry no file path and no shell or message payload: `plan_mode_question`, `plan_mode_complete`, `ask_user_question`, `foreman_ledger`, `review_verdict` (a reviewer child's verdict call; it writes only its own record folder), `foreman_triage`, `foreman_checkpoint`, `foreman_dialogs`, `foreman_script` (its own owner dialog is the control), `foreman_wait`, `foreman_hold`, `foreman_report` and `foreman_reports` (each writes only the report store, see [retro](retro.md#reporting-at-the-source)), `contact_supervisor`, `subagent_supervisor`, `bg_wait`, `bg_status`, `bg_logs`, `bg_kill`, `pr_status`, `pr_checks`, `pr_comments`, `pr_watch`, `pr_unwatch`, `git_status`, `git_log`, `git_diff_stat`, `git_branch_state`, `subagents_enable` |
| `default-role-launch` | the foreman session's own single `subagent` launch of one of `explorer`, `builder`, `reviewer`, with no `action`, `tasks`, `chain` or `workflow`, and a `cwd`/`worktree` inside the owned roots. The adapter's role, ceremony and spawn gates run after the gate and still refuse a launch they refuse. A launch outside the owned roots, a workflow script and the `tasks`/`chain` forms are not covered; they run with no judge call |
| `default-read` | the read class of `effects.ts` (`ls`, `cat`, `head`, `tail`, `wc`, `stat`, `grep`, `rg`, `find`, print-only `sed`, ...) on paths inside the session's roots |
| `default-build-test` | the project's own build and test commands from its manifest, run from the worktree (not a dependency install) |
| `default-write-in` | `mkdir`, `touch`, `cp`, `mv`, `rm`, `tee` inside the worktree, scratch and `/tmp` (`gate.tmpAccess`, default on) |
| `default-git-read`, `default-git-add`, `default-git-commit` | read-only git; `add`; `commit` with a message (secrets-in-commit still runs; an amend of a branch with an upstream is dangerous) |
| `default-git-fetch`, `default-git-pull` | `fetch`; `pull --ff-only` |
| `default-git-switch` | `switch`/`checkout` of the own branch |
| `default-git-branch-merged` | `git branch -d\|-D <b>` (one plain name, no other flag) when `<b>` is merged (its tip is in `origin/<default>`, or its PR is `MERGED` at that tip), is not the default or a protected branch, and the repo is not a work folder outside the worktree. No current-branch condition, because the gate judges a post-merge chain before it runs. Never for a child |
| `default-git-push` | `git push [-u] origin <own branch>\|HEAD` with an empty environment prefix, and no force, delete, mirror, tag, `:` refspec, `-o`, `--repo`, `--receive-pack`, `--exec`, `-c`, or `remote.origin.push`. The own branch is the branch checked out in the worktree the push runs in: the cwd after a `cd`, or the `-C <path>` of `git -C <path> push ...` (its branch, protected-branch and push-config facts are those of that worktree). That worktree must be the session's own checkout or a worktree this session created (the session manifest); a linked worktree it did not create is not own, and a push from it is no default. A push from a second worktree of the session (`cd <wt> && git push -u origin <b>`, `git -C <wt> push origin <b>`) is routine even when `<wt>` lies outside the session's roots. A branch checked out in another worktree of the session stays own. A builder from a single launch gets it like the main session; never for any other child (floor) |
| `default-gh-read` | read-only `gh`/`glab` (`run view\|list`, `pr view\|checks\|diff\|list\|status`, `issue view\|list`, `repo view`, `api` with no method, no GraphQL and no `-f/-F/--input`; `run download` only into scratch) |
| `default-assign` | the closed allowlist of harmless assignments |
| `builtin-web-read` | a plain download, see [Web reads](#web-reads) |
| `path-read-*`, `path-write-*` | the path tools, computed from the session's roots, see [Owned paths](#owned-paths) |

Children get the same built-ins minus parent `.workflow` writes and anything outside their worktree.

Details of the read and write rows:

- **Quoted pattern words.** A `grep`, `egrep`, `fgrep` or `rg` segment is still a read when its only unknown words (`$PAT`, `$(...)`) are double-quoted strings in a pattern position or the value of an option that does not name a file (`grep -n "$PAT" src/a.ts`, `rg --type "$T" foo src/`). A `$(...)` word there is no longer opaque, but the line is not a default read either: the inner command is judged on its own (`$(sudo id)` still hits the `privilege` floor). An unquoted unknown word, an unknown path operand or redirect target, a file option (`-f`, `--file`) and a wrapper keep the segment opaque. `sed` and `awk` are excluded: their script text is the pattern position and the gate cannot tell a read-only script from a writing one when it is unknown. The floors read the line as written; only the allow step relaxes the words.
- **The null device.** A redirect to `/dev/null` (`>/dev/null`, `2>/dev/null`, `&>/dev/null`) is no write on every platform. `NUL` in any case (`>NUL`, `2>nul`) is the null device on win32 only; on macOS and Linux it names a file, so it is a write like any other.
- **`rm` of a symlink.** A plain `rm`, `unlink` or `rmdir` (no `-r`, no trailing slash) is judged on the link itself, not on its target, wherever the write roots are checked.
- **Local `npx`.** `npx <bin>` is a local run, not an install, when it runs a bin that is already installed: the segment's directory is known, the nearest ancestor holding a `package.json` has `node_modules/.bin/<bin>` (or `<bin>.cmd`), and the line has no `-p`/`--package`, no `@version`, no `--yes` and no path-like bin name. It is never a built-in allow: like any other `npx` it runs.

### Read tools

The path tools `read`, `grep`, `find` and `ls` are judged on their path field. An extension tool that reads files is an ordinary tool to the gate until the user names it in `gate.readTools`, a map from the tool name to the name of its path field (`null` when it has no path field and reads the cwd). A mapped tool is then judged like `read`/`grep` on that field: `Read(...)` rules cover it, the secret-path floor applies to the field (search patterns such as `pattern` or `patterns` are not paths and are not floored; `glob` is), and a path inside the session's roots or an owned path gets the `path-read-*` allow. Example for pi-fff:

```json
{ "gate": { "readTools": { "ffgrep": "path", "fffind": "root" } } }
```

The key is user or overlay config only; a project value is dropped with the usual warning. The names of the built-in tools (the path tools including `foreman_move` and `foreman_copy`, the shell tools and pi-foreman's own tools) cannot be remapped: such an entry is ignored and named in the same `config_warning` record (`ignored`). A mapped tool keeps the secret-path floors on all its other path-like fields (`paths`, `root`, `file`, arrays), exactly as when unmapped. A name in the map that no registered tool carries (for example `ffgrep` while pi-fff runs in `override` mode, which registers `grep`, `find` and `multi_grep`) is ignored and leaves one `config_warning` trace record per session; it never fails a call.

### Owned paths

Path tools (`read`, `write`, `edit`, `grep`, `find`, `ls`, `foreman_move`, `foreman_copy`) go through `pathrules.ts`. The allowed places are computed at runtime from the session's roots:

- the worktree, the session's scratch dir and the OS temp dirs (`gate.tmpAccess`; for a child only its own `$FOREMAN_SCRATCH` and its kept output folder `$FOREMAN_OUT`, `<agent dir>/pi-foreman/child-out/<session>/<launch>`, which the harness keeps 7 days; [safety](safety.md#kept-output-folder));
- reads of the Pi install dir, the global npm root, the bundled package roots and the owned roots (state dirs, handoffs, sibling worktrees, your `additionalDirectories`);
- the registered parent's `.workflow` dir, read-only, for a session opened by another session;
- the session's own handoff dir: through the path tools the session may write `plan.md` and `result.md`; a session that is the child side of a handoff dir (and a subagent child) may also write `ask.md`/`ask-<n>.md`, `.steer-last-read.json` and anything below `work/` in its launch's handoff dir; everything else there (the bare `work` entry included) belongs to the parent. The session's own shell guard (`shell_write_guard.py`) applies the longer list to the handoff dir where that session is the child side (its `PI_FOREMAN_HANDOFF_DIR`), when it has one. On Windows names are compared case-folded; streams and 8.3 names are refused;
- a child never writes a handoff dir's `parent` or `child` files, the parent's `.workflow`, or anything outside its own worktree, scratch dir and those handoff names, and never opens a pull or merge request (`pr_create`, `gh pr create`, `glab mr create`) or merges one (`gh pr merge`, `glab mr merge`, a `gh api` PUT on `.../pulls/<n>/merge`; rule `child-pr-merge`). These child denies run before any built-in allow or judge verdict.

A path write outside every root is `danger-write-outside`, except into an install or package folder, which asks the owner (`install-root-write`, [steps](#the-steps)). Secret paths are floors and never reach this step.

**Read-only roles (`child-readonly-write`).** A child whose role is not `builder` and whose round worktree is readable but not writable for it (a reviewer or explorer in a round; the flag is `roundReadOnly` of the gate roots, set from the round manifest) never writes that worktree. The gate refuses, as `child-readonly-write` and before any judge verdict: write and edit tool paths and `foreman_move` and `foreman_copy` destinations in the worktree; a shell segment whose write target the gate can name in the worktree (a redirect, `sed -i`, `cp`, `mv`, `rm`, `touch`, `mkdir`, `tee`, `dd of=`, `tar -x -C`, `unzip -d`, `patch -d`, the inner call of `bash -c` or `xargs`, also behind `cd sub &&`); and every git subcommand in the gate's write set (`commit`, `add`, `reset`, `checkout`, `stash`, `tag`, `config` in a write form, `clone` run from the worktree, `fetch` with a refspec). Allowed: reads, test runs (`npm test`, `npm run lint`, `npm run test:node`, `make test`, `node --test`), `git status|log|diff` and a plain `git fetch origin`, the scratch folder and the child's own handoff files (`cd <scratch> && git clone <worktree> c` is the way to get a copy). A git output option or default output into the cwd that lands in the worktree (`archive -o`, `format-patch` without `--stdout`, `bundle create`, `checkout-index`) is refused too (the forms that get past this fence are listed under "Read-only roles" in [safety](safety.md)). The refusal text names the rule, the target and the way out. This is a known limit, not a sandbox: it stops the writes the gate can name. It does not stop git subcommands outside the write set (`symbolic-ref`, `replace`, `sparse-checkout`, `maintenance`, `commit-tree`), writes by known programs that the write-target code does not name (`chmod`, `xargs` with names on stdin), build tools and package manager runs (`make`, `npm run <script>`: they are not counted), a `powershell` line (it runs after the floors; its words are checked for secret, `.git`, self-modification and install-folder paths, but a word in the worktree is not refused), and a write hidden in an unknown program, a script run from the scratch folder or inline interpreter code. These are known gaps: a judge step for these lines (the label `danger-readonly-run` and its role question) was removed, and the planned state check after each command is meant to cover them. Later rounds revisit this line.

**Run-end hint and the scratch `.git/config` read.** Beside this fence the foreman compares the checkout of a reviewer or explorer run at its start and end and names a difference in one notice; it blocks nothing (scope, blind spots and cost: [safety](safety.md#the-tool-gate), "Run-end state hint"). The read exemption for the `.git/config` of a clone in the child's scratch dir resolves a relative token by the cwd of the segments that hold it; a mixed or unknown cwd, or a token that sits in no segment, stays a hit (a secret-path refusal).

**The foreman's checkout (`child-write-foreman-checkout`).** A child launched through a single `subagent` call knows the foreman's checkout (`FOREMAN_CHECKOUT` in its launch binding). A shell write of the child that lands inside that checkout, its `.workflow/` included, is a deny named `child-write-foreman-checkout`: a redirect, a write-class operand (`cp`, `mv`, `tee`, ...), a git write verb run from it or given `-C`, `--git-dir` or `--work-tree` for it, and `git clone` into it. The reason says the foreman's files change through the foreman and points the child at its own worktree and `$FOREMAN_SCRATCH`. Reads are never fenced (`cat`, `ls`, `grep`, `git status`, `git log` on the checkout pass the fence). The read-only `git branch` list forms (`--show-current`, `-a`, `-r`, `-v`, `-vv`, `--list`) and `git stash list|show` without `--output`, `git worktree list` (`--porcelain`, `-v`, `-z`), the `git config` read forms (`--get`, `--get-all`, `--get-regexp`, `--list`, `<key>`) and the `git tag` list forms (bare, `-l`, `-n[N]`, `--contains`, `--points-at`, `--merged`, `--sort`, `--format`) name no write target, also under `git -C <dir>` or after `cd <dir> &&`, so they are no `child-write-outside` either; `git stash` alone, `stash push|pop|drop|clear|apply`, `branch -d|-D|-m|-f`, `branch <name>`, `worktree add|remove|prune`, `config <key> <value>`, `config --unset`, and `tag <name>`, `tag -d|-a|-s|-f` still do. The child's own worktree and scratch dir are never part of it, so a worktree nested inside the checkout stays the child's own. Write and edit tool paths into the checkout are not named separately: they get the general `child-write-outside`.

**Realpath comparison.** The child's scratch dir and the checkout are each compared in two spellings, the one in the launch binding and its realpath (a symlinked temp dir such as macOS `/var` -> `/private/var`), and the target of a write is compared in its real spelling too. A `cd` or redirect through either spelling of the scratch dir is a write-in; a link inside the scratch dir that leads out of it is not. A scratch dir or target that does not exist yet is compared through its deepest existing ancestor plus the missing tail, on both sides, so `mkdir -p` into a run dir not yet created is a write-in in either spelling. A `cp` source is a read: only the destination (the last operand, or `-t DIR`) is a write target, while an `mv` source is deleted and stays a write. On Windows the comparison folds case and treats `\`, `/` and the `C:` drive forms alike; on Linux it compares case exactly.

### Work folders

`workFolders` in the **user** file names folders you work in (`~/git`, `~/notes`). A project or tracked file cannot set it (the dropped-key notice names it), and neither can a profile.

```json
{ "workFolders": [{ "path": "~/git", "mode": "auto" }, { "path": "~/notes", "mode": "read" }] }
```

- **Reads.** Every read inside a folder (either mode) is a built-in allow, `.git` included; floors still guard secret files. Path tools and shell reads (`cat`, `ls`, `grep`) alike. Children get none. Folders relax reads only: `git add`, `commit`, `push`, `pull`, `fetch` and `switch` in a repo inside a folder keep their usual rule (no built-in allow outside the worktree and scratch).
- **`mode: "auto"`** (default when omitted) also relaxes a write that no other root covers. `mode: "read"` leaves writes as they are. Any other value warns and counts as `read`. (This is the folder's own mode, not a permission mode.)
- **Protected places stay as they are**, in every spelling (symlinks, `.GIT`): a `.git` directory, `.pi` (except its `scratch` and `tasks` subtrees), the agent dir, the Pi install dirs and the pi-foreman package root.
- **Shell writes** relax only when every segment is a built-in default with the folders as extra write roots: `touch`, `mkdir` and `cp` into a folder. Output redirects (`echo x > <folder>/notes.txt`) keep the worktree's parity, like a redirect into the worktree. `tee` and `tar -x -C` / `unzip -d` / `rsync` / `patch -d` / `make -C` are never defaults, and `rm` and `mv` keep today's behaviour, so they keep their own rules.
- **Never consulted** for a judge-first call or a path in two folders or in one folder and outside it. Nested folders: the innermost entry wins. A worktree inside a folder keeps its own rules.
- **Validation.** `~` expands; a relative path, the filesystem root, your home dir and any parent of it are dropped with a warning; a folder outside your home dir is kept with a warning. `/foreman perms list` prints a Work folders block with the folders, modes, the real spelling when it differs, and the warnings. The allowed trace event reads `mode:folder:auto` with `mode` and `source: workFolder` and no path.

### Web reads

A plain download needs no dialog. `fetch` GET/HEAD, or `curl`/`wget` writing into scratch (or to stdout read by a reader such as `head`, `grep`, `jq`), passes four deterministic checks:

- (a) GET/HEAD only: no body, no upload, no other method, an http(s) URL;
- (b) no auth or cookie material (`-u`, `-n`, `@file` headers, `Authorization`, `Cookie`), no userinfo in the URL;
- (c) nothing runs the download: no pipe or substitution into a shell or interpreter, no config file;
- (d) the output goes into scratch (`-o` with `--output-dir` is resolved), or to a non-executing reader.

A candidate that passes is a read: it runs. A candidate that fails runs too (a network write has no judge call); the web-read allow is the only built-in rule here. There is no host list. Loopback hosts (`127.0.0.1`, `::1`, `localhost`, any port) are plain URLs here: a GET to them is a read. Starting a local app is a different call and follows the normal rules. Running a downloaded file is a normal call too.

### Variables in bash lines

`shellvars.ts` resolves `$NAME` / `${NAME}` only when every statement of the line is in a closed grammar: a sole `NAME=literal` assignment of a plain absolute path (or a `$FOREMAN_SCRATCH` prefix), or a simple command from a fixed list of programs with plain words, `$NAME` words, `2>&1`, `>/dev/null` or one plain redirect target. Anything else leaves the variable unresolved and the segment opaque. The cases are pinned by `tests/fixtures/shellvars-grammar.json` and `tests/fixtures/shellvars-cases.json`.

For a **child session** with a scratch dir, two more cases resolve outside that grammar, so a line with a heredoc, a pipe or other statements is no longer opaque for these variables alone:

- **One literal assignment.** `NAME=/abs/path` or `NAME=$FOREMAN_SCRATCH[/sub]` at the start of a statement (line start, after `;` or a newline, or after `&&` following another such assignment: not in a pipeline, subshell, group, loop, function, `$(...)` or after `||`) resolves later `$NAME` and `${NAME}` words. `NAME` is assigned exactly once and the line mentions it in no other way (no `export`, `read`, `for NAME`, `${NAME:-x}`, no use before the assignment). It does not apply when the line runs `eval`, `source`, a function definition, a runner or a computed program name. `$PWD`, `~` and `$HOME` are not forms of it.
- **`$FOREMAN_SCRATCH` and `$FOREMAN_OUT` themselves** resolve on a heredoc or pipe line too, as long as the line mentions the name only as `$NAME` or `${NAME}` and never rebinds it (quoted or escaped spellings, namerefs and env-clearing wrappers count as a rebind or a cleared name and leave it unresolved), under the same code-running guard. They are the harness folder only up to the first run unit of the line that may rebind them, in run order and failing closed: an assignment, `export`/`declare`/`unset`/`read`/`printf -v` on the name, a loop variable, a plain word that is the name, `eval`, `source`, `.`, `trap`, a nameref, a computed or expanding argument, an `IFS` assignment anywhere earlier on the line, a login or interactive shell (`-l`, `--login`, `-i`, `exec -l`, `exec -a -name`, which reads startup files), `BASH_ENV=` or `ENV=` in front of a command or as an operand of any `env` layer (`env env ...`, `env -i env ...`, also behind `timeout`, `nice` and the like), an `env` setting whose name is no shell identifier, a parse failure, or arithmetic on a value not shown to be a number puts the name in the set for that unit and every later one (`harnessRebound` on each segment). The set of the outer line flows into every nested `-c` string (`sh -c`, `bash -c`, `env ... sh -c`). Ordinary loops, `read` into plain names and arithmetic on numbers set on the line do not. A line nested past the parser's depth limit (4 levels) is judged whole, also a harmless one such as `echo hi` six `bash -c` deep; it fails closed, and such lines are rare. After that unit a write through the name is a write to an unknown place: a builder's goes to the judge (`danger-write-outside`; unsure or no clear refuses it with the judge's reason), a reviewer's or explorer's is `child-readonly-write`, and a session's own ruling file is refused (`FOREMAN_SCRATCH=/tmp/q; echo x > $FOREMAN_SCRATCH/ruling.md`). A write in the units before the rebind still resolves.

The foreman and an opened session never get these two.

### Split literals

The gate does not read a script file a child runs, so it denies nothing for a split literal in one: `node x.mjs`, `python3 x.py` and `bash x.sh` are judged by their words. The scan (`splitliteral.ts`) has one use left: a line whose text joins string fragments with `+`, `..`, `.concat(...)`, `[...].join(...)` or `.replace(All)` (or spells `String.fromCharCode` or base64 literals) into a whole guarded command token (`rm`, `dd`, `git`, `push --force`, `reset --hard`, ...) is never given a built-in allow. Cases: `tests/fixtures/split-literal-cases.json`.

## Floors

Floors deny with a reason and no model call, for every session kind. No config key turns them off, and there is no dialog. A shell line is floored on its raw text before parsing and again on the parsed segments, so an unparseable command can be denied but never allowed by default. The string fields of any other tool are read as commands instead (below).

- secrets and key paths (`~/.ssh`, `~/.gnupg`, `~/.aws`, cloud and kube credentials, `.env`, `.npmrc`, `.pypirc`, `.netrc`, git credential stores, key files such as `*.pem`, `*.key`, `*.p12`, `*.pfx`, `*.jks`, `*.keystore`, `*.kdbx`, `id_rsa*`, `id_ecdsa*`, Pi's auth file) for read and write; the key-file name globs are one list, `config/secret-paths.json` (a JSON array of globs, `*` is any run of characters inside one path segment), read by this floor and by `scripts/foreman_sync.py`; overlays can read the same file. The one exception is a read of an SSH public key: a `*.pub` file directly in `<home>/.ssh` (not in a subdirectory), whose real path is also directly in the real `~/.ssh` and whose content is a regular file of at most 16 KiB with every line starting with an OpenSSH public key type. A symlink or hardlink to a private key, a missing file or any other content stays denied, and so does every write, move, remove or copy onto it. It passes the floor and the built-in `*/.ssh/*` path rule (a rule that names `.pub` still denies) and is traced as `floor-pubkey-read`. When the file cannot be read, both fall back to the same list built into the code;
- writes to the three `permissions.json` files (matched by the basename below a `.workflow` or `.pi` directory too, so `mv x .workflow/permissions.json` is caught), pi-foreman's config files when the line carries a `safety.permissions*`, `safety.policy*` or `gate.*` key, `managed.json`, `state/round-parents.json`, `state/bridge-trust.json`, `state/approvals/**`, `state/gate/**`, Pi session files, and (for any child tool write) `state/child-asks/**`. Reading `permissions.json` is not a floor, and a read-only look at the config file is fine;
- force, mirror and delete pushes, pushes to the default or a protected branch, and **any `git push` from a subagent child that is not a builder from a single launch** (a reviewer, an explorer, an unbound child, and a builder from a `tasks` or `chain` launch never push; the foreman pushes; a builder from a single launch pushes its own branch, and its force and protected-branch pushes stay refused). Only parsed `git push` segments count: the word inside a quoted string, a heredoc body or a read-only interpreter snippet is data;
- a `git push` of a `src:dst` refspec whose destination is a variable (`HEAD:$B`) is `floor-git-push-force` for every role (the old Python delete check refused it); a colon-less `git push origin $B` runs. A git verb that is itself a variable (`git ${V:-push} origin main`) gets the force and protected-branch push checks;
- home, root and system deletes in rare forms are `floor-rm-system`: `busybox`/`toybox <applet>`, a shell function body (and the bodies of `select`, `coproc` and `for ((;;))`), `sh -c` and `eval` literal strings, and `Remove-Item -Recurse -LiteralPath:C:\Windows`. The other forms the old delete check refused or asked on (an unreadable delete or write target, `git clean -e`, container and `ssh` commands, hidden PowerShell commands) are [judge-first](#the-judge-first-list) now, for the foreman and a child alike;
- a delete (`rm`, `unlink`, `rmdir`, `find -delete`, `rsync --delete`) outside the worktree, scratch and `/tmp` is `floor-delete-outside`. A plain `rm`, `unlink` or `rmdir` of a symbolic link is judged on the link, not on what it points to: removing the `node_modules` link of a worktree is inside the worktree even though the link leads out;
- *(judge-first `danger-git-config`, not a deny)* `git config` of the keys listed in `extensions/core-adapter/git-floor-keys.json` (hooksPath, sshCommand, credential helpers, `url.*.insteadOf`, remote urls, push configuration), in every form: `git config` in any scope, the `-c key=value` prefix, the values of `git clone -c` and `--config` (shortened and clustered spellings included), `--config-env`, `GIT_CONFIG_*` environment words (only the exact bare `GIT_CONFIG_GLOBAL=/dev/null` passes; a quoted spelling (`'/dev/null'`, `"/dev/null"`) stays floored (the line scan sees a quoted word masked, so it fails closed)), and `git remote add|set-url|rename|remove|set-branches|set-head`; a reviewer or explorer in a round may read the `.git/config` of a clone inside its own scratch dir (see [safety](safety.md)); `core.attributesFile` outside `.workflow/` or with a verb other than `merge`;
- deletes and recursive overwrites outside the session's worktree, scratch and `/tmp`; `rm` of `/`, home or a system dir, in bash and in PowerShell/cmd units (`Remove-Item`, `del`, `rd`; `floor-rm-system`);
- **`chmod-system`**: a recursive `chmod`, `chown` or `chgrp` on `/`, the home directory or a system dir;
- `sudo`, `su`, `doas`; shutdown, disk formatting, `dd` to a device;
- *(judge-first `danger-fs-scan`, not a deny)* whole-filesystem scans (`find /`, `grep -r ... /`, `du /`, `ls -R /`);
- a download piped into a shell; package publish (`publish`, `twine upload`, `docker push`, `gh release create|upload|edit|delete`, ...);
- *(judge-first `danger-inject`, not a deny)* typing into another terminal pane (`herdr pane send-keys|send-text`, `tmux send-keys`, `osascript` keystrokes); see the judge-first list;
- the guards that exist next to the gate: the shell-write guard, secrets-in-commit, and the literal self-ruling refusal in the `tool_call` hook (a session never writes `ruling.md`, `ruling-<n>.md` or `brief-<x>.md` in a handoff dir where it is the child; see [sessions](sessions.md#ask-by-file-parent-that-is-not-a-pi-session)). The gate's own path rules keep a child's **writes** out of foreign session dirs, sibling worktrees and other children's scratch dirs (`child-write-outside`); a child's reads of them are not fenced (see [safety](safety.md#owned-paths)).

**Opaque-text matches.** On a line the parser could not state exactly, a text match for a push by a child that is not a builder, a git config key, a remote change, a force or protected-branch push or a policy or config file (`policy-file`, `config-keys`) cannot be told from quoted prose, so what happens depends on the session kind:

- **Child:** a deterministic deny with the hint "Rephrase without a variable or loop, or let the foreman do it." A child never asks its parent about a text-only hit.
- **Owner or an opened session:** a dialog (never the judge).

`policy-file` and `config-keys` have a narrower rule. A protected or config word that only cleanly read segments carry is no hit, when every segment of the line is a clean read, a loop word or a bare assignment. The `~`, `$HOME` and `${HOME}` spellings count as clean. On a line that writes nothing the parser can see (a `sed` without `-i` or a `jq` beside the read, a loop variable, an assignment, a pure read before a parse error), the word goes to the judge as `danger-policy-file` or `danger-config-keys`, for owner and child alike. A line with a visible write keeps the dialog (owner) or the deterministic deny (child). A protected path inside another segment's argument (`sed -n "w <path>"`) goes to the judge or stricter (a split-off path such as that usually keeps the dialog or deny, but not always). A here-document body that is data is skipped for `policy-file` too, except on a line with a command substitution or process substitution (`$(…)`, backticks, `<(…)`, `>(…)`): the body or its output can become another command's arguments, so that body is no data for the `policy-file` scan. The `config-keys` scan still skips such a body.

The same words on a parsed segment are a deny for every kind. The `rawFloors` list (download piped into a shell, privilege, shutdown, disk, `GIT_CONFIG_*`, `--config-env`), publish and `rm` of system dirs stay denies on the raw text of a shell line, with one rule for the three program floors below.

**`config-keys` and reads.** On a line the parser could not state exactly, a config file word next to a `safety.permissions*`, `safety.policy*` or `gate.*` key word is a hit only when a segment that is not a plain read carries the file: a cleanly parsed read (a read-class program such as `cat`, `grep`, `diff`, `find` without an action; `git status|log|diff|show` without a program or output option; no write redirect) that names the file, for example `git diff -- config/foreman.schema.json && echo "gate: $(git rev-parse HEAD)"`, is no hit. A write, a `git add`, a redirect or an unreadable word that names the file stays one. Where the line writes nothing the parser can see (for example a `sed -n` or `jq` beside the read), the word goes to the judge as `danger-config-keys` instead of the dialog or deny.

**Restart, privilege and disk tools: one rule.** `sudo`, `su`, `doas`, `pkexec`; `shutdown`, `reboot`, `halt`, `poweroff`; `mkfs*`, `fdisk`, `sfdisk`, `parted`, `wipefs`, `diskpart` are judged by the **program of each parsed segment** (wrapper-stripped: `env`, `xargs`, `nohup`, `timeout`, `nice`, `command`, `time`, `sh -c`, `eval`, subshells, `$( )`, backticks, `if`/`while`/`for`/`case` bodies, absolute paths, `.exe`, quoted or escaped spellings). The command-position word match for these three groups applies only to a line that is **not clean**: the parse failed, a segment is opaque (`exec`, `coproc`, `[[ ]]`, a function definition with any body, a variable as the program), a segment feeds text to an interpreter (a shell or runner given code, `-exec`), or the line carries a here-document or here-string whose body the text scan below does not blank (any program but `cat`/`tee`: a shell, `at`, `docker exec -i c sh`, `make -f -`, `git commit -F -` alike; no list of interpreters is kept). A clean line is read by its programs alone, so a search such as `grep -rn a\|reboot src` (an escaped pipe before a word) passes. The price: on a clean line there is no second net against a parser mistake. Lines no judge reads as the program stay open (`telinit`, `eval "$x"`, text piped into a shell); the delete and system-removal checks of the removed Python guard do reach `ssh`, `docker exec`, `find -exec`, `busybox <applet>`, `powershell -Command` and `cmd /c` text (`floor-rm-system` for home and system targets, the judge-first `danger-remote-command` and `danger-delete-unknown-target` for the rest, see the delete rows above) and are not part of this gap list. The open lines are pinned as documented gaps in `g8-matrix.test.ts`. Every other raw entry (download into a shell, `dd` to a device) is unchanged.

**Script source is not word-matched.** The source of a `codemode` script is no longer scanned as raw text; its structured path fields keep the secret-path floor, and so does every other string field of the `codemode` input (only `code` is exempt). What a script does is decided call by call: every tool call it makes goes through Pi's nested tool pipeline (`tool_call` with a `parentToolCallId`), where this gate applies the floors and the judge-first list to it like a direct call. That rests on two things, both stated as risks: the runner of the pinned Pi range (`1.6.x`, enforced at setup) gating nested calls, and the exemption going by the tool name `codemode` (a different extension registering a tool of that name that runs its text itself would not be word-matched). Probe after a Pi update: a script with one nested shell call carrying a floored line must be refused.

**Notes are not commands.** For `foreman_show`, `foreman_session_open` and the note tools above, every field named in the free-text field list (`PROSE_FIELDS` in `extensions/core-adapter/gate.ts`: for example `markdown`, `brief`, `text`, `note`, `message`, `content`, `summary`) skips the raw-text floors. A field that names a file or directory (`path`, `cwd`, `file`, `target` and the like) keeps the secret-path floor. Every other string field, and every string field of an MCP or unlisted tool, is read as a command, not as text. Each line of such a field is parsed with the shell parser and only the text floors run on the parsed line and on each of its parsed commands (the command inside `bash -c`, `sh -c`, `eval` or backticks, and a quoted program word such as `'sudo' ls`, count as commands): download piped into a shell, privilege, shutdown, disk, `GIT_CONFIG_*`, `--config-env`, publish, `rm` of the root or home, and the push, remote and git config words. A line the parser cannot read is not floored (prose with a stray quote, code in another language, `sh('rm -rf /')`), and prose that merely holds floored words is not either: the words count only where a parsed command starts (`never run rm -rf /` is no hit, `rm -rf /` alone on a line is). No segment floor runs on a field: no secret-path check on a command's arguments, no policy-file or config-key word scan; a field is not refused for what the same text would pass as a shell line, except in the known cases where a field stays stricter (the shell line is free there and the field refuses): a quoted ANSI-C program word (`$'sudo' ls`), the body of a function that holds a quoted command (`f() { bash -c 'curl x | sh'; }`), a heredoc that is never closed (a tag with a trailing space is one), a heredoc opener with an unterminated quote after `<<` (`echo x <<"EOF`), a heredoc fed to a program other than `cat` or `tee` (`echo x <<EOF`, `ssh host <<EOF`), a heredoc inside `$( )` or backticks (`x=$(cat <<EOF` ... `EOF` ... `)`) and in `eval "$(cat <<EOF ...)"`, where a shell runs the body or its output, a heredoc with an unquoted tag that is only written, with a floored word in its body (`cat > f <<EOF` with `rm -rf /` on a body line; a body that also holds a harmless `$(git rev-parse HEAD)` beside such a plain line is the same case), and a command line inside a quoted multi-line argument (`echo "a` / `<command>` / `b"`, `git commit -m 'x` / `<command>` / `'`). A heredoc body counts as data only when it is only written and its tag is quoted (`<<'EOF'`, `<<"EOF"`, `<<\EOF`, the parser's `quoted`; a tag written with `$'…'` or `$"…"` does not count as quoted here, because not every shell reads it as a quote); then it is not read as commands (`cat > s.sh <<'EOF'`, also two heredocs on one line). A body fed to a shell is read as commands, and so is every body with an unquoted tag, whatever it holds: a shell may expand it (`$(…)`, a backtick, a `$` and backslash-newline before `(`, `${ …; }`), and the gate does not look for which form it is. Its lines are read like any other lines (`cat > f <<EOF` with `$(sudo ls)` or a plain `sudo ls` line in the body is floored, a body with only `$(git rev-parse HEAD)` and `$VAR` is free), decided on the whole heredoc, not per line. Body lines are found from the parse of the whole field text, never from the text of a line: a line is a body line only when the parser reports it inside a heredoc redirect of a command it parsed (a `<<` inside a quote opened on an earlier line, in a comment or in `$((1<<2))` is none, so the next line is a command, as on a shell line). The body of a heredoc that feeds `cat` or `tee` or a bare redirect is skipped when it counts as data (above), the line that opens it is still read; if any heredoc of the text feeds anything else (a shell, an interpreter, a pipe into one), no line of the text is skipped. When the whole text does not parse (a quote left open, a heredoc after it), there is no grouping at all: every line is read alone, and a heredoc body in it is read as commands. When the whole text parses but a line does not parse alone (a quote that closes on a later line), the whole text is read once more as one shell line. A whole command in one quoted program word (`"rm -rf /"`) is no command, as on a shell line. The shell limit: a heredoc body written with a program the gate cannot see through (for example `tee`) that names a config file next to a `safety.permissions*`, `safety.policy*` or `gate.*` key word is still asked or refused on a shell line, because the unparsed-line scan reads that text whole; a field has no such scan. The verdict is unchanged: an ask for the owner on a `git push` (force or protected branch), `git remote` change or git config word, a refusal for a child, a refusal for every other floor. A floored command on a line of its own inside a multi-line field is still floored. A field also floors `\sudo ls` (a backslash before the program) as a shell line does; before this piece it passed there.

Residual risk of this narrowing, in plain words: a field is no longer refused for prose that holds floored words, for text inside a quoted argument of a program that is not a shell (`echo 'git push --force origin main'`), for a leaf the parser cannot read (an unbalanced quote, a carriage return inside a word), or for JSON or code in another language (`{"cmd":"rm -rf /"}`, `sh('rm -rf /')`). A command run through `powershell -c`, `cmd /c` or `pwsh -Command` inside a field (a git push, remote or config word in it is still asked or refused), and an environment assignment before a command inside `bash -c` (`bash -c 'GIT_CONFIG_COUNT=1 git status'`), are no longer floored in a field; the shell line is not floored for them either. A full program path such as `/usr/bin/sudo` is floored on a shell line but not in a field (unchanged). A written heredoc body that other means run later is free in a field as on a shell line: process substitution into a shell (`tee >(sh)`), `xargs … sh -c`, a read-eval loop, a shell the gate does not know by name (`zsh`, `busybox sh`, `$SHELL`), and writing the file and running it afterwards. If a tool behind such a field runs that text as a command itself, the floors do not see it there; its own call, if it makes one, goes through the gate.

**Denial text.** A floor denial keeps its sentence and appends the tool and the matched fragment: `... No review, policy entry or dialog lifts this floor. (tool: bash; matched: reboot)`. The fragment is the regex match (raw and opaque-text floors), the program and the operand that decided (segment floors) or the path as written (path and secret-path floors, never file content). The text is redacted first, as in the gate log (secrets shown as `[redacted]`, the home directory as `~`, long letter-digit path parts masked), then cut to 80 characters with control characters, Unicode format characters and line and paragraph separators removed. It is the agent's text after redaction, not the raw text. The decision log carries it as `fragment`, written through the same redacting field writer as `tool`.

What the text floors read, so that data is not mistaken for a command:

- **Masked text.** Every text floor reads the line with its data blanked: the body of a `cat` or `tee` heredoc (the `privilege` floor included, so a `sudo` inside a note is no hit even when the same line then runs the file it wrote), and quoted strings. A heredoc body fed to a shell or interpreter (`bash <<EOF`, `python3 - <<EOF`, `cat <<EOF | bash`) stays visible. Quoted strings stay visible when a segment of the line runs text: a shell or interpreter with `-c`/`-e`, a runner such as `xargs`, `awk`, `ssh`, `osascript`, `deno eval|run`, `find -exec`.
- **`git` in command position only.** A `git push`, `git config` or `git remote` counts at the start of a statement, after a shell keyword (`do`, `then`, `if`, ...) or a wrapper (`env`, `xargs`, `timeout`, `sudo`, ...), with git's own options (`-C <dir>`, `-c k=v`, `--git-dir`) before the verb. A line that runs text or builds its program through `$(...)` has no known command position, and there `git` counts anywhere.
- **Search patterns are not paths.** The secret-path floor skips the pattern of `grep`, `egrep`, `fgrep` and `rg` (the first operand and `-e` values), and the script of `sed` and the program of `awk` only when it can only read (a sed script with `w`, `r`, `e`, `a`, `i` or `c` commands, or an awk program with redirection, a pipe, `getline` or `system`, is not skipped). `-f`/`--file` values and every other operand stay paths. `rg --files` and `rg --type-list` take no pattern, so every operand of those is a path.

**The honest gap.** A non-opaque script or snippet that *itself* deploys (a `./deploy.sh` that calls `kubectl apply`, a Python file that posts to an API) is just a command the parser reads: the gate judges the line, not the file's contents, so it runs. The same holds for a build or test command whose scripts do something dangerous. Keep such a script out of the agent's reach, or name its target as a protected target, if that matters to you. This is an owner decision, not a bug: a script the agent runs (`./x.sh`, `npm run x`, `make x`) is routine, and the gate and the floors read only the command text, never the script body. The gap is still open. Beside it there is one approved path for a change the guards close to every agent: `foreman_script`, where the owner approves a script in a dialog and the harness runs it (see [safety](safety.md#owner-scripts)); it does not close the gap, and nothing reads that script's body either.

## The owner dialog

When a call escalates and a human is at the pane, `pi-foreman: <tool> asks` opens a select dialog. The title carries the cause, the judge's reason if it was unsure, the cwd and the **full command**, heredoc bodies included. The cause is one of: `danger-<name>: <reason>`, `self-modification <rule>` or a floor-ask text.

A command of up to 12 lines is shown whole. A longer one shows its first 8 and last 3 lines around a line `... [N lines omitted; the full text is in <agentDir>/pi-foreman/state/gate-ask-<n>.txt]`. A line over 300 characters shows its first 200 and last 80 characters around `… [N characters omitted] …`. Whenever anything is cut, the full text goes to that trace file and the display names it (with only characters cut, the last line is `... [the full text is in <file>]`). Without a state dir, or when the trace file cannot be written, the cap still applies and the display names no file. Control characters are shown as `?`. The text that reaches the agent never hides anything.

| Option | Result |
|---|---|
| allow once | the call runs; nothing is stored |
| deny with comment | the call is denied with `pi-foreman: denied by the user: <your text>`, which the agent reads |
| deny and stop | the call is denied and the agent is told to stop and ask what to do next |

A dismissed dialog is a deny. A repeated identical deny is handled as before (`repeatedDeny`).

A dialog offers no remember option: nothing is stored, so the next identical call asks again (a judge clear is cached for the session).

## Presence

Presence (`presence.*`, the same idle-input probe that gates cache warms; see [cache](cache.md#presence-gate)) never closes or refuses a permission dialog. Your absence never answers a question; it waits for you. A child's protected-target check does not read presence either: the child counts as present when it has a route to its parent (an ask dir and `gate.childAsk: parent`).

- A dialog opens whether you are at the machine or not, and it stays open until you answer it. Dismissing it denies. Nothing else closes it except an abort of the call or the end of the session; such a close is no answer and denies nothing you did not decide.
- The dialog opens with no presence probe and no watchdog. `presence.enabled: false` only affects the cache warms.
- In a session with UI that is not a child, and in a child with a route to its parent, the [protected-target judge](#protected-targets) decides the same way whether you are present, away, or presence is off, not sampled or stale.
- No other judge has an away rule, so children and sessions without UI are unchanged there; a session without UI has nobody to ask.
- A floor decision (a deny, or a built-in or rule allow) is deterministic and runs no presence probe.

## Session kinds and who answers

| Kind | What it is | Who answers an escalation |
|---|---|---|
| owner | a pane with a human and no parent | a dialog in the pane |
| session opened by another session | a session started with `foreman session open` | a dialog in its own pane |
| child | a subagent run (builder, reviewer, ...) | its parent, see below |
| headless | no UI (print or json mode) | nobody: the call is denied at once |

With nobody to ask, the agent reads: `pi-foreman: denied: nobody is at this session (no pane). The owner is absent; do not wait or retry, report this line and continue with what you can.` A child whose parent has a pane but whose asks are off reads a different text (see Child asks). A floor is never asked.

### The read question

Removed. A second model call used to clear a shell line whose only dangerous-class entry was `danger-opaque`. Opaque lines now run (the floors still read the raw text), so there is nothing to clear. `gate.readClear` has no effect.


### The role question

Removed. This step used to put the label `danger-readonly-run` on a shell segment of a reviewer or explorer that the gate cannot see into and to ask a model five questions about the line. It asked about plain reads (`sed -E 's/x/y/'`, `printf`, a read outside the project) and made reviewers wait for the parent, so the label and the call are gone. A read-only role's line goes the way a builder's does (a line whose program is unknown goes to the judge for every role, `danger-unknown-program`): those labels (`danger-opaque`, `danger-install`, `danger-net-write`, `danger-forge`, `danger-deploy`, `danger-process`) are gone, so such a line runs with no judge call (owner decision 2026-11-18, widened by the judge-first change). What stays: the write fence (`child-readonly-write`, see the read-only roles above), the secret floor and the child path fence. The gaps the label covered are known gaps until the planned state check after each command: git forms outside the write set (`symbolic-ref`, `replace`, `sparse-checkout`, `commit-tree`), `--out=` and `-vo` git output, `make` and `npm run`, `powershell` lines, a script a reviewer wrote in its scratch folder. The setting `gate.readonlyClear` is still accepted and has no effect. This anchor stays for the schema link.

### Child asks

`gate.childAsk` is `"parent"` (default) or `"deny"`. A child's gate runs the same steps. When a child's call escalates (a judge-first call the judge did not clear; a self-modification hit is denied outright for a child) and `gate.childAsk` is `parent`:

1. When the parent adapter launches a child it creates an ask dir `<agentDir>/pi-foreman/state/child-asks/<parent session id>/<launch id>/` and passes it in the launch binding. The child gate writes `ask.md` there with `fs`, never through a tool: the cause (`danger-<name>`), the reason line, tool, cwd, role, run and the **whole** command. It then waits for `ruling-<n>.md`.
2. A floor denies any child tool write under `state/child-asks/`, so a child can never write its own ruling. A ruling is accepted only as `ruling-<n>.md` for an `n` the child gate itself wrote, with an mtime not before its ask. A stale ruling is ignored.
3. The parent adapter polls the ask dirs of its running children (500 ms) and opens **one dialog in the parent's own pane** naming the child role and run, the tool, the full command, the cause and the judge's reason. A parent that has no UI writes `DENY`.
4. Dialogs from several children queue, one at a time. The dialog stays open until you answer it.
5. `ALLOW` lets the call run once. Anything else denies. The parent model never answers a child ask.

**No deadline.** The child waits for the ruling without a time limit, and the parent's presence does not end the wait. The wait ends on a ruling, on an abort of the child's call, or when the starting session is gone. The starting session is gone when its ask dir is missing, or when its live file is missing or its heartbeat is older than 90 seconds on two checks in a row. The child checks once a minute by its own clock. A check counts only if the clock moved by less than two minutes since the check before; a larger jump (the machine slept) starts the count again. The child never creates the ask dir: writing an ask into a missing dir is the gone case. A gone starting session denies the call with `pi-foreman: denied: the session that started this helper has ended or no longer watches it, so nobody can answer. Do not retry; report this line and continue with what you can.`

**Reload and other shutdowns.** A parent reload keeps the ask dirs and the new session watches them again at its start: an ask that has no ruling is shown again, an answered one is not. Any other shutdown ends the open asks: the dialog closes without a ruling, the dirs are deleted and a child that still runs gets the gone denial.

**A run that ends mid-wait.** A run can end while its question is open (the run's time limit, or the limit on one tool call). The question then stays open and the dialog stays. The run's result says so: `the run ended while waiting for the owner on <tool>: <command>; the question is still open, do not work around it.` Your answer is kept once, in the starting session's memory only, for the identical call of the resumed run. The key is the launch, the tool, the cwd and a hash of the child's whole tool input; any difference gives a normal dialog. When you answer, the ask dir is deleted; a recognised resume creates it again, and a child whose resume is not recognised finds no dir and gets the gone denial. The entry is used once and ends with the session. An ask without the hash is never kept. The starting session is told with a notice (data, not an instruction) that you answered and the run can be resumed. A kept answer passes nothing a dialog could not: the child's own gate runs the floors and rules before it asks.

`gate.askTimeoutMs` has no effect. It stays only so that existing configs load.

A child denied because child asks are off (its own `gate.childAsk` is `"deny"`, or its parent launched it with them off) reads `pi-foreman: denied: this call needs the owner's answer and child asks are off (gate.childAsk is "deny"). Report this line to the foreman, who can run it or ask the owner. The call was: <cause>.` A child whose parent has no pane (a headless parent) reads the no-pane text above, followed by `The call was: <cause>.` Both are denies; nothing else about the decision changes.


A line the judge does not clear takes the route above.

**What a child never asks about.** A child's parent is never asked about a text-only floor hit on a line the parser could not read (a push, a git config key, a remote, a policy or config file): that is the deterministic deny (for a push, only for a child that is not a builder; a builder's unparsed plain push is decided like main's) with the rephrase hint described under [Floors](#floors). A line that only reads (every program in the read class, no runner, no inline code, no output redirect except an fd dup or the null device) is not stopped by the `policy-file` and `config-keys` text floors, so `ls -la config/` is decided locally and does not ask. On a line that writes nothing the parser can see but has a `sed` or `jq` beside a placed read, those two words go to the judge (`danger-policy-file`, `danger-config-keys`) and not to a child deny; only a visible write is the text-only deny; a protected path in another segment's argument goes to the judge or stricter (a split-off path such as `sed -n "w <path>"` usually keeps the dialog or deny). A loop (`for f in config/*.json; do grep -n foo "$f"; done`) binds no variable: its body stays opaque and runs, for a literal list and for one the gate cannot read (`for f in $(ls)`) alike, and it opens no dialog. A heredoc into the child's own scratch dir that names `git config` in its body is data and does not ask either. Only the case in the list above (a judge-first call the judge did not clear) opens the parent's dialog, except a child's write whose target the gate cannot read and whose only labels are `danger-write-outside` and `danger-unknown-write-target`: that one is refused with the judge's reason and asks nobody.

## Profiles

Removed. A profile was a named set of rules and a mode that an owner picked with the session launcher's `--profile` option, `PI_FOREMAN_PERMS_PROFILE` or `permissions.profile`. The option is still accepted, ignored, and prints one notice on stderr; the `profiles` key of a permissions file is ignored with a doctor INFO; the built-in `steward` profile is gone (its `herdr pane send-text` and `ps` calls run under default allow, and `danger-inject` judges typed text first). The `perms-profile` floor is gone too: the policy-file and self-modification floors protect the files.


## Commands

All in the owner pane of the session:

- `/foreman perms list` shows the protected targets, the `classifier.deny` sentences, the additional directories and the work folders.
- `/foreman perms protect add|remove ...` edits the protected targets (see [Protected targets](#protected-targets)). The files are re-read when their modification time changes; there is no reload command.
- `/foreman doctor` prints the classifier model, the counts, the decision-log path, one INFO line per removed key still set, and warns about an invalid user file and a tracked or unignored project file.

## Protected targets

A protected target is a host, a path or a command glob that you want a small model to judge call by call instead of a block that interrupts every time. Entries live in the `protected` list of the user file and of the trusted project file (`.workflow/permissions.json`); every other file ignores the key.

```json
{ "protected": [ { "host": "prod-*.example.net", "note": "production" }, { "path": "ops/playbooks/**" }, { "command": "deploy-*" } ] }
```

Each entry has exactly one of `host`, `path`, `command` (1 to 300 characters), an optional `note` (200 characters) and an optional `check` (`model`, `read-only` or `ask`). Entries are numbered `P1..` in file order. A bad entry is skipped with a notice. An invalid `check` keeps the entry and treats it as `ask` (it never removes the protection), with a notice; an unknown key in an entry gives a notice and is ignored.

A production note example: `{"host": "prod-db", "note": "production: reads and diagnostics are fine, anything that changes state asks", "check": "read-only"}`.

- **The note is your policy.** The judge follows the note of a matched entry. On a note that marks the target as production, calls that only read or diagnose (logs, status, versions, listings, counts, queries that change nothing) pass even when the task does not name them. Reading secrets (key files, password or token files, credential stores) asks. Every call that changes state asks: config edits, restarts, deletes, queue operations, credential changes, installs. This is an instruction to the model, not a harness rule.
- **Per-entry check.** `check` on an entry can only tighten `gate.protected.check`: the effective mode of a call is the strictest of the global value and the `check` of every matched entry (`model` < `read-only` < `ask`). It can never be looser than the global setting. To change the `check` or the note of an entry, remove the entry and add it again.
- **What the check sees.** The matched entries with their notes and check modes, the session task (the bound ledger's title and open items, else in an owner session the first user message, cut to 800 characters), the task the parent gave this agent (a helper's launch task or a child session's brief, fenced as written by an agent and cut like the judge's; withheld for a match with remote classes or a `host` entry, and never allowed to override an entry's note), the effect classes of the call and the `deny` sentences (`D1..`). The command is fenced as data.
- **What it may answer.** `{"verdict": "allow"|"ask"|"deny", "effect": "read"|"write"|"deploy"|"network"|"unknown", "confidence": "high"|"low", "entry": "D1"|null, "reason": "..."}`. An accepted `allow` runs the call. Floors still come first.
- **What is accepted.** In this order, the first row that applies wins; every `ask` has a cause that the trace names:

  | Step | Condition | Result (cause) |
  |---|---|---|
  | 1 | effective mode `ask` | ask (`mode`) |
  | 2 | no effect class computed | ask (`no_classes`) |
  | 3 | verdict `allow`, confidence low | ask (`low_confidence`) |
  | 3 | verdict `allow`, a local segment the harness cannot state (opaque) | ask (`local_opaque`) |
  | 3 | verdict `allow`, remote command opaque (see the transport list) | ask (`remote_opaque`) |
  | 4 | verdict `allow`, a remote segment classed as a write | ask (`remote_write`), for every effect |
  | 5 | `allow`, effect `read`, a local segment classed as a write | ask (`local_write`) |
  | 5 | `allow`, effect `read`, otherwise | allow |
  | 6 | `allow`, effect `write`, `deploy` or `network`, mode `read-only` | ask (`read_only`) |
  | 6 | the same, owner away (a child with no route to its parent, or a session with no UI) | ask (`away`) |
  | 6 | the same, otherwise (a session with UI that is not a child, or a child with a route to its parent; any presence) | allow |
  | 7 | `allow`, effect `unknown` | ask (`unknown_effect`) |
  | 8 | `deny` citing an existing `D` entry | deny |
  | 9 | anything else (verdict `ask`) | ask (`judge_ask`) |

  A failure of the check (an invalid or extra-field reply, asked for once more with the same request and a failure only when the second reply is unreadable too, an `allow` or `ask` that cites an entry, a `deny` with no entry or citing an entry that is not a `D` entry, a timeout, a provider error, no model) asks with its own cause (`invalid_verdict`, `wrong_entry`, `timeout`, `provider_error`, `no_model`). A remote segment the harness sees as a write always asks, even when the judge says write, you are present and the mode is `model`; local writes keep the older behaviour.
- **The remote command of `ssh <host> <cmd>`.** The harness parses the remote command and classes each segment. **The general rule: on a protected host, any part of a remote command the harness cannot read is decided by the judge alone, and such a write runs on a read verdict.** That covers a program the harness does not unwrap, a builtin that evaluates its arguments, an expansion or construct it does not walk and a parser limit. The harness only adds asks for the closed list below; the table shows the classes:

  | Remote segment | Class | Read verdict, high confidence |
  |---|---|---|
  | an output redirect (`>`, `>>`, `&>`, `&>>`, `<>`, `>\|`) whose target is not the literal `/dev/null` (a non-literal target counts as not `/dev/null`); an fd dup (`2>&1`, `>&2`, `2>&-`) never counts | write-out | ask |
  | `tee`, `script`, `flock <file>` and the other writing wrappers | write-out | ask |
  | the direct write classes `cp`, `mv`, `rm` (with literal paths), `touch`, `mkdir`, in the plain forms the harness knows (ask as `remote_write`); judge-only exceptions: a write verb called by path (`/bin/rm /etc/x`; `tee` by path still asks) an `rm` with an editor-backup operand (`~`, `.bak`, `.orig`, `.swp`, `.#…`), and any operand starting with `~` (a home-directory path such as `rm ~/x`, `touch ~/x`, `cp /etc/a ~/b`; the parser marks it as an unresolved variable); each of these makes the segment unknown. `$variables` and globs in a write do the same. `echo a > ~/x` and `tee ~/x` still ask | write-in or write-out (by path) | ask |
  | the effect classes write-in, write-out, build-test | as classed | ask |
  | the effect classes read, net-read | as classed | allow |
  | effect class unknown (for example an unknown program) | unknown | the judge decides |
  | anything else the harness cannot read; for example a write command with an option it does not know (`cp -r`, `rm -i`, `touch -d`, `rm --force`), `$variables` and globs in a write, `eval "$X"`, `sed -i`, `trap '…' EXIT`, `alias`, a function definition, `zsh -c '…'`, and a runner (`sudo journalctl -n 5`, `su -c '…'`; the harness does not read the wrapped command) | unknown | the judge decides |
  | a shell on the host that reads its program from input (`sh < /opt/x.sh`), a remote command with a syntax error, the constructs `[[ ]]`, `(( ))`, C-style `for ((i=0; i<n; i++))`, `select` and `coproc`, command substitution nested past 4, any parser reason not listed here, a remote command with no segment | remote opaque | ask |

  The write rows hold only for a segment the harness reads directly, and "a segment the harness reads" relies on the bundled shell parser. Anything it does not read is judge-only: `ssh prod-db 'cp -r a b'`, `ssh prod-db 'sudo tee /etc/app.conf'`, `ssh prod-db 'su -c "rm /etc/f"'` and `ssh prod-db 'X=1 touch /etc/app.conf'` run on a read verdict. A redirect the remote shell itself performs is still seen after `sudo` (`sudo echo a > /etc/app.conf` asks), but the program's own write is not. An assignment prefix hides only a direct write class; a redirect or `tee` after it still asks (`X=1 echo a > /etc/app.conf`).

- **Input into ssh.** What is sent into ssh is not in the call text, so any input always asks (remote opaque): a pipe in front of ssh, a heredoc or here-string, a `<` or `<>` from anything but `/dev/null`, and an fd dup onto stdin (`<&3`; `ssh x >&2` reads the same and also asks). An empty input (`< /dev/null`) and `ssh -n` send nothing and are exempt.
- **Transport opacity.** These also always ask: ssh with no remote command, a command-running option (`-o ProxyCommand=`, `LocalCommand=`, `RemoteCommand=`, `-F`), rsync `-e` or `--rsh`, scp `-F` or `-S`.
- **Owner away.** The judge treats a session without UI, and a child with no route to its parent, as away; presence is not read. A child has a route when its launch binding names an ask dir (a single `subagent` launch from a parent with a pane) and its own `gate.childAsk` is `parent`; then it is not away and decides as the owner's session does (a confident write verdict allows). A child launched in a group or a chain, one with `gate.childAsk: deny` and one whose parent has no pane stays away. Away, only read-only verdicts allow; the rest asks (a child's ask goes to the parent pane per `gate.childAsk`; a session without UI has no pane and refuses). In a session with UI that is not a child the judge decides the same whatever presence says.
- **The ask.** `P2 (production) is protected. The check rates this write with high confidence: <reason>.` There is no remember option.
- **Cache.** A read-rated allow is cached for the session by tool, cwd, role, payload and entries; the owner-away rule is re-applied on every hit, the check-mode test comes before the cache, and a permissions change or a protect change clears it.
- **Editing.** The foreman calls `foreman_protect {action, kind, glob, note?, check?, file?}` when you ask it to protect a target; you confirm in a dialog (a timeout, a cancel or no pane is a refusal) and the adapter writes the file. A child never has the tool. You can run `/foreman perms protect add|remove <kind> <glob> [--check model|read-only|ask] [--note <text>] [--user]` yourself (`--check` is for add only; an invalid value or `--check` on remove prints the usage and writes nothing). An untrusted project file, a duplicate add (same kind and glob, whatever the mode) and a missing remove are refused; the refusal says to remove the entry and add it again. The confirm dialog names the entry's check mode.
- **Log and trace.** Decision log layer `protected` (an accepted allow carries the model's reason); trace event `protected_check` for every verdict, with the redacted command, the matched rule (`protected:P<n>`), the entry, the matched globs, the effective check mode (`mode`) and, when the gate asks, the `cause` from the table above (`exception` when the check itself threw). A guard block (`deny`, `blocked`) in the trace carries the redacted command, the guard name as `rule` and the matched rule text as `reason`.
- **Cost and latency.** An uncached check is one call to the small review model: about 1.2k to 2k input tokens, roughly 0.1 cent on a small model, 1 to 4 s, capped by `gate.reviewTimeoutMs` (a timeout asks). Read-rated allows are cached per entry set until the next permissions reload, so a repeated identical read costs nothing (a read verdict never reads the owner as away, so a child's cache hit needs no ask route). Writes are never cached.
- **What matches.**

  | Entry kind | Matches | Effect classes added |
  |---|---|---|
  | `host` | the hosts of `ssh`, `scp`, `sftp`, `rsync` (also after the host: `ssh prod -o X cmd`, combined flags such as `-vp 22`, `--`, `-J` jump hosts), `curl`, `wget`, and a `fetch` call that is not a plain GET or HEAD | every non-ssh shell host match carries `write-out`; ssh adds the classes of its remote command |
  | `path` | the write targets of write-class segments and the path tools (`write`, `edit`) | `write-out` |
  | `command` | the program basename of any segment, regardless of effect class | those of the segment |

  A plain GET or HEAD never matches. A read-class segment (`cat`, `grep`, `git log`, ...) never touches a host or path entry. A command-running ssh option (`-o ProxyCommand=`, `LocalCommand=`, `RemoteCommand=`, `-F`) makes the remote command opaque, so only an ask is possible.
- **Known limits.** The general rule: on a protected host, any part of a remote command the harness cannot read (a program it does not unwrap, a builtin that evaluates its arguments, an expansion or construct it does not walk, a parser limit) is decided by the judge alone, and such a write runs on a read verdict. Examples, not a list: `ssh prod-db 'sudo tee /etc/app.conf'`, `ssh prod-db 'su -c "rm /etc/f"'`, `ssh prod-db "trap 'rm /etc/f' EXIT"`, `alias`, `ssh prod-db 'eval "$X"'`, `ssh prod-db 'unset "a[\$(rm /etc/f)]"'` (bash evaluates a quoted array index in builtins such as `unset`, `local`, `read`; the exact set depends on the bash version), and `ssh prod-db 'echo ${x/$(rm /etc/f)/y}'`. The last is a known parser gap: in `${x/$(…)/y}` and `${x//$(…)/y}` the inner command's arguments and redirects are lost, so a write there is judge-only. Most remote commands that change state class `unknown` (a service restart, `sed -i`, `rm` with a glob or variable, flushing a queue), so only the judge stands between the call and the host. If it wrongly says read, the call runs: `ssh prod-db 'vendorctl status; vendorctl queue flush'` and `ssh prod-db 'for q in a b; do vendorctl purge "$q"; done'` run on a wrong read verdict. The local `privilege` floor does not reach into a remote command, so a `sudo` inside the quoted string is not floored.

  What always asks is a closed, exact list (whatever the verdict, except a `deny` that cites a `D` entry, which denies; the two verdict-dependent items are marked; it holds only for a segment the harness reads, which relies on the bundled shell parser):

  - a remote segment the harness classes write-in, write-out or build-test (`remote_write`), by class, not by program: plain `cp`, `mv`, `rm`, `touch`, `mkdir`, `tee` and the other writing wrappers, `>` and the other output redirects (`ssh prod-db 'echo a > /etc/app.conf'`, `ssh prod-db 'sudo echo a > /etc/app.conf'`). The classing uses the local checkout's effect context, so which build or test commands count (`npm test` and the like) depends on the local manifests, and `git restore …` is write-in only when every path is a local test file inside the worktree. Judge-only exceptions (the segment becomes unknown): a write verb called by path (`/bin/rm /etc/x`; `tee` by path still asks), an `rm` with an editor-backup operand (`~`, `.bak`, `.orig`, `.swp`, `.#…`), and an operand of `cp`, `mv`, `rm`, `touch` or `mkdir` that starts with `~` (a home-directory path; `echo a > ~/x` and `tee ~/x` still ask). Variables and globs in a write are judge-only too;
  - the remote-opaque forms: every ask row of the remote-segment table above (a shell that reads its program from input, a syntax error and the rest), including `select`, `coproc`, C-style `for ((;;))`, `[[ ]]`, `(( ))` (`ssh prod-db 'for ((i=0;i<1;i++)); do echo a > /etc/app.conf; done'`, `ssh prod-db '[[ -n $(rm /etc/f) ]]'`), command substitution nested past 4 (`ssh prod-db 'echo $(echo $(echo $(echo $(echo $(echo a > /etc/f)))))'`), and any parser reason not named in the table;
  - effective mode `ask` (the global `gate.protected.check` or the entry's `check`) and a local opaque segment on the line (`local_opaque`);
  - everything in Input into ssh and Transport opacity above;
  - any failure of the judge;
  - verdict-dependent: a non-read verdict while the owner is away (a child with no route to its parent, or a session without UI);
  - verdict-dependent: under effective mode `read-only`, a non-read verdict (`read_only`).

  What denies: a `deny` verdict that cites an existing `D` entry. It wins over every item above except effective mode `ask` and a failed check, which ask.

  The floors run first. Remote commands are classed with the local effect context, so a remote relative path resolves against the local checkout. ssh port forwards (`-L`, `-R`, `-D`) are not seen by the remote classes. A future `gate.protected.*` sub-key needs its own tighten row. Exotic ssh layouts the parser does not read fall back to the older, stricter path (opaque remote), never toward allow.

## Decision log

One JSON line per gate decision in `<agentDir>/pi-foreman/state/gate/log.jsonl`: `id, ts, session, kind (owner|child|headless), role, tool, layer, verdict, rule, reason, shape, cwdHash`, plus `fragment` on a floor denial (the matched text, redacted), and `latencyMs`, `model` and `cached` when a model decided; a judge row also has `reasoning` (the level used), `promptChars` (the length of the request text) and `timeoutMs`. For a dialog the `reason` of an allow holds the answer (for example `allow-once`, `parent-allow` on the child's line); a deny keeps its deny text.

| Layer | Written when | `rule` holds |
|---|---|---|
| `floor` | a floor or a self-modification rule denied | the floor or rule name |
| `default` | a built-in allow | the built-in name |
| `classifier` | the judge cleared a judge-first call | `judge:danger-git` (the `danger-*` name); a call that needs the owner is logged by the `dialog` layer |
| `protected` | the protected check allowed or denied | `protected:P2`, or `protected:P2;classifier.deny:D1` for a deny |
| `cache` | the judge's cached clear was reused | `judge:danger-git` |
| `mode` | no floor, built-in allow or judge-first entry named the call, so it ran | `mode:no-rule` |
| `dialog` | an owner answered | the `danger-*` name or the cause |
| `child-ask` | a parent answered or timed out for a child | the run id and the outcome (an answer carries the dialog answer, for example `allow-once`) |

Lines of the older gate (`review`, `autoreview` usage role) stay readable. `shape` is the normalised, redacted command: program and option words kept, literal paths reduced to a class (`<worktree>/...`, `<scratch>/...`, `<tmp>/...`, `<home>/...`, `<parent>/.workflow/...`, `<abs>`), URLs to the host, every quoted string and secret-like value replaced by `<v>`. The log rotates to `log.1.jsonl` at `gate.logMaxBytes` (default 20 MB). Classifier calls are logged to the usage log with role `classifier`; the trace carries `guard`, `dialog` and `review` events.

| `permissions.profile` | removed: profiles are gone; the value is ignored | ignored with a notice |
| `gate.reviewTimeoutMs` | judge call timeout (default 15000, minimum 100) | lower only |

| `gate.childAsk` | `parent` (default) or `deny` | `deny` only |
| `gate.readClear` | No effect: the read question was removed. The key is kept so existing configs load | no effect |

## Known limits

A generator test (`extensions/core-adapter/test/gate-generator.test.ts`, [development](development.md#tests)) hides dangerous commands in shell constructs and fails when one runs silent; the shapes it still finds are listed with their sources in `KNOWN_GAPS` (and `PLAIN_GAPS`, for plain lines) in `_gate-gen.ts` and are known limits of the shell reading.

- Another extension loaded before the gate, or one that mutates `event.input` after it, could change the input between the decision and the execution. The gate is first in load order; the doctor warns when any extension precedes it.
- Extension-registered providers: the classifier call goes through Pi's registry, so a provider an extension registers at runtime must be loaded before the first classification.
- Subagents launched as a group or a chain, and children of a session without UI, are denied at once with the no-pane text: nobody can answer there.
- After a parent reload a resume is not recognised, because the map from run to launch is gone. The ask dir of an ended run is deleted once you answer, so the resumed child's ask gets the gone denial. The same holds for a resume by a shortened run id.
- A resume is recognised only by its full run id.
- A starting session that hangs but still writes its heartbeat keeps a waiting helper waiting; the helper's own run limits still apply.
- The `bash` tool is parsed as bash, whatever shell Pi resolves; the parser does not read another shell's syntax.
- The judge rests on the classifier model alone; no rule of the gate checks its answer beyond the shape. The fence and the instruction to treat the command as data are measured against injection, not guaranteed. The judge is a small model: a weaker model, or one without reasoning support, weakens the guard. It reads only the judge-first hits: an opaque line, an interpreter body or a deploy runs with no look at all, as the [default allow](#default-allow) says. The judge reduces accidents and is no defence against a determined agent: an agent can already write a script file and run it unasked (the honest gap under [Floors](#floors)). The trial of the old read question (2026-11-13) does not carry over.
- The decision is made on the command string, not at run time: another local user can swap a `/tmp` path for a symlink in between.
- Git config in the repository (`diff.external`, a pager) still applies to `git diff` and `git log`.
- The git floors and the judge-first list read plain git command lines. Not a complete list of what they do not read: `git clone --template=<dir>` (its hooks run during the clone), `git submodule foreach`, `git bisect run`, `git difftool -x`, `git ls-remote --upload-pack`, a one-off `-c alias.*`, `git fetch <remote> +a:b`, `git checkout <file>`, commands inside a script file, an alias or a runner, and forms that remove a config variable (`env -u GIT_CONFIG_COUNT ...`). The ref-moving entries apply to subagents only; the main session's own forms are not on the list. A subagent keeps the git credentials of its user (the harness stopped stripping them in #262), so a floor that reads command lines is no boundary against code the child runs: only an operating-system sandbox or a separate operating-system user would be one, and pi-foreman builds neither. Branch protection on the server, administrators included, is the boundary (see [safety](safety.md)).
- Windows: `/tmp` is no write base. For the foreman the system temp dir is the write target, in its real and its long spelling (an 8.3 `RUNNER~1` expands); a child's shell writes there are not a write base (an unresolved target is `danger-write-outside`).
- `tasks` and `chain` launches carry no launch binding, so their children get no `FOREMAN_CHECKOUT` and no `child-write-foreman-checkout` fence; they still get `child-write-outside` for a write outside their worktree and scratch dir.
- Known limit (D25a): pi-subagents' "repeated mutating tool failures" attention signal (`long-running-guard.js`) counts a failed bash call as a failed mutating tool, and Pi's bash marks any nonzero exit as an error. A redirected test run that stays red three times on the same file within 5 minutes therefore raises that signal, though nothing was written. The signal is upstream of the gate: the gate's null-device rule (no write) does not change it. pi-subagents 0.89 fixed the `/dev/null` exemption and the first-written-file lookup, not this.
- The gate judges a command line, not the files it runs (see the honest gap under [Floors](#floors)). The floors still apply to the command text.
- Shell forms the walker still does not read; a line with one runs unless another part of it is a floor or judge-first hit: a program named under a variable folder (`$V/bin/x` runs as the program it names; the #347 rule is kept); `cd -` and `popd` that return to a folder inherited from the session (`OLDPWD`, the directory stack) with no earlier non-literal folder change in the line; `cd */` (the glob's folder is unknown, not flagged); `cd $D && make` and `cd $D && npm test` run build files from an unknown folder; a relative literal file that resolves to a stream (`cd /dev; . ./stdin`, a link to `/dev/stdin`), and a relative script word after the look-behind (`cd $D; caffeinate ./x.sh`); `GIT_DIR=`, `GIT_WORK_TREE=` and `CDPATH=` before a command (`CDPATH=/x cd sub`); `echo 'branch -D main' | xargs git` (input-fed arguments of a known program are not read by the git checks); options that start another program (`sort --compress-program`, `tar --to-command`); positional references inside an `eval` or `bash -c` text in a body, `coproc`, `trap`; `find -exec sh -c`, `npx sh -c`; `nameref`.

## Windows

The `bash` tool on native Windows runs Git Bash, so the bash AST applies as on Linux and macOS. The optional `powershell` tool has no parser: every `powershell` call is opaque. The floors run on its raw text (with the PowerShell-aware shell-write grammar) and on its words (`pswords.ts`, resolved against the cwd), then it runs; it is never a built-in allow. Inside a bash line, `powershell`, `pwsh`, `cmd`, `cmd.exe`, `wsl` and any invocation of a `.ps1`, `.cmd` or `.bat` file are opaque segments. On win32 a path has two spellings (backslashes, 8.3 short names such as `RUNNER~1`); `effects.ts` `realSpelling()` compares the real spellings, so a read root stored by its realpath still matches, and `pathnorm.ts` is the one normaliser the floors, the path rules and the pattern rules share. `/tmp` never counts on Windows. `NUL` (any case, `>NUL`, `2>nul`) is the null device on Windows only; elsewhere it is a file name. The fence against the foreman's checkout accepts `\`, `/` and `C:` drive spellings and folds case on Windows, and `$FOREMAN_SCRATCH` resolves to the drive form of the scratch dir. The gate tests run on the three CI operating systems with path fixtures for both separators and drive letters.

## Parser and prior art

The gate parses with `unbash` 6 (pinned exact, upgraded only with the tests green). Its AST types are isolated in `shellast.ts`, because the v5 to v6 change shows node shapes can move. Where the parser cannot state a line, the floors read the raw text and the rest runs; nothing in the table below is widened for it. The parser's closed variable grammar, the quoted-pattern relaxation for `grep` and `rg` and the "line only reads" exceptions on some text floors stay, because they spare common lines a refusal; a new line shape goes to the judge-first list or a floor, not to a new parse rule.

| Option | Install | Platforms | Accuracy | Verdict |
|---|---|---|---|---|
| `unbash` 6 (ISC) | one dependency, pure TypeScript, no transitive deps | Windows-neutral pure JS | GNU Bash 5.3 syntax, typed AST with positions, tolerant parser with a partial AST plus errors; zsh, PowerShell and cmd unsupported (documented) | **chosen**: about 15x faster than tree-sitter wasm, no native or wasm build |
| `tree-sitter-bash` over `web-tree-sitter` (wasm) | grammar plus wasm runtime; what the old permission package used | wasm, any platform | full grammar | not chosen: wasm dependency, about 15x slower |
| a regex or quote-aware splitter (the old `shellchain.ts`) | none | any | splits on `&&`, `||`, `;`, `|`; refuses `$(`, backticks, subshells and heredocs | not chosen: refuses most real lines; kept only as a thin layer over the AST |

Packages that build on `unbash` were considered and not used (`pi-bouncer`, `@cad0p/pi-steering` with `@cad0p/unbash-walker`, `pi-access-guard`, `pi-guards`): each pins an older `unbash`, none covers the rule files, role-aware built-ins, parent reads or the ask-to-parent flow, and running one beside the gate would double the dialogs. Two designs come from `pi-bouncer` as reference: its always-deny set and rule names, and its rule that an unparseable command is never allowed. pi-foreman writes its own small walker (`shellast.ts`) instead of depending on `unbash-walker`. The pattern-rule syntax follows the Claude Code permission rules.

## Developing pi-foreman itself

When the session's working directory is the package root or inside it (symlinks resolved; case-insensitive on Windows and macOS), the write protection of the package root narrows to the config files (`config/permissions*.json`, `config/foreman.defaults.json`, `package.json`); other writes in the checkout (docs, extensions, tests, scripts) pass. The session writes a `protect_selfhost` trace event.

## Migration

### From the review-model gate

The gate that asked a review model to judge every undecided call against policy prose is replaced. What changes for you:

| Before | Now |
|---|---|
| `<agentDir>/pi-foreman/policy.md`, `config/permissions.policy.md`, `<cwd>/.workflow/policy.md` with `## allow/deny/ask` entries | not read. Deny sentences can go to `classifier.deny` (read by the protected-target check); allow sentences and ask rules are gone with the rule lists |
| `gate.policy.userFile` | removed |
| `safety.policy.files[]` | removed |
| the review model judged every undecided call | undecided calls run; only the [judge-first list](#the-judge-first-list) goes to the judge, and a clear runs it |
| `foreman perms candidates`, `export-eval`, the live eval, the remember step and the rule workshop (`foreman perms suggest\|adopt\|review`) | gone |
| `ask.md` from a session opened by another session to its parent for a gate ask | gone; such a session asks in its own pane. The handoff files `plan.md`, `ruling.md`, `result.md` and `brief-<n>.md` stay; a `ruling.md` is a note from the parent and approves nothing |
| `gate.mode: "floors-only"` | no effect (there are no modes; default allow). Remove it |

`foreman setup` prints one line per removed key it finds: `<key>: removed (policy files are no longer read)`, and names a leftover user `policy.md` once: `<path>: policy.md is no longer read; move its entries into permissions.json classifier.allow/deny`. `/foreman doctor` prints a `FAIL` line for a leftover key and warns about an invalid `permissions.json` and a tracked project file. A key whose target is already set is dropped with the reason `<target> is already set`.

**Backups.** Before it changes anything, setup writes `<agentDir>/pi-foreman/state/migration/foreman.json.pre-gate` (your config) and `permission-system-config.json` (the package's rendered config), then removes the rendered config file.

**The package entry in `settings.json`** is a separate, explicit step that setup never runs. Preview it, then apply it:

```
node scripts/foreman_migrate_gate.mjs settings --dry-run
node scripts/foreman_migrate_gate.mjs settings
```

It backs up `settings.json` to `state/migration/settings.json.pre-gate` and drops the package entry. The doctor prints a `FAIL` line per leftover (a leftover key, the rendered permission config, the package entry, a package install) with the fix.

**The way back** is the previous pi-foreman release: install it (`npm install pi-foreman@<previous>`), copy the backups back (`foreman.json.pre-gate` over your `foreman.json`, `permission-system-config.json` back to `<agentDir>/extensions/pi-permission-system/config.json`, and `settings.json.pre-gate` over `settings.json` if you ran the settings step), and run its `foreman setup`. The previous release rejects `gate.*` keys, so the backup copy is the way back, not an automatic restore.
