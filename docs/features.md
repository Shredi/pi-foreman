## Install

Verbatim from [install](install.md#install):

```text
Needs Node 22+, Pi 1.4.x on `PATH` and Python 3.13+.
pi install git:github.com/Shredi/pi-foreman            # global; pin with @<tag-or-commit>
pi install -l git:github.com/Shredi/pi-foreman         # project scope (.pi/settings.json)
/foreman setup --dry-run   # inside Pi: show the planned changes, write nothing
/foreman setup             # inside Pi: apply
bin/foreman setup          # from a checkout (or: node setup.mjs)
```

Then map your models ([model-map](#model-map)), run `/foreman doctor` in Pi and check this inventory.
Enable snippets below go into `<agent dir>/foreman.json` or an overlay's `pi.foreman.config`.

## Layers

Config merges in this order, later wins (maps deep-merge, leaves and lists are replaced):

1. package defaults (`L1`): `config/foreman.defaults.json`. May set: every key.
2. packages and overlays (`L3`): each installed package's `pi.foreman.config` (an organisation overlay), plus `--l3 PATH`. May set: every key.
3. user (`L2`): `<agent dir>/foreman.json` (`PI_CODING_AGENT_DIR`, default `~/.pi/agent`). May set: every key.
4. project (`project`): `<repo>/.pi/foreman.json`, read only once Pi's project trust is resolved. May set: tighten-only keys only stricter, ignored keys dropped with a warning, no new role ids.
5. session (`session`): `--session-json` and launch flags, not persisted. May set: the project rules, and loosening keys are dropped.

The per-key layer rule in the tables below is read from `scripts/foreman_config.py` (`TIGHTEN`, `LOOSEN_ONLY`, `IGNORED_KEYS`, `LAYER_TIGHTEN`, `ROLE_RULES`, `CODEMODE_FALSE_ONLY`, `TRACE_DIR_IN_WORKSPACE`): `any layer`, `tighten-only (<rule>)` or `not in project/session (<reason>)`. A project or session value that would loosen a tighten-only key is dropped with a warning.

## Profiles

`foreman setup --profile <name>` assigns every toggleable feature: the ones a profile names as given, all others their shipped state. `--enable`/`--disable` adjust single features afterwards. `full` switches safety relaxations on.

| Profile | Summary | On | Off |
|---|---|---|---|
| `orchestration` | The ceremony, ladder and review machinery without the extra UI, PR tools, herdr integration, idle cache keepalive, idle downshift, retro and trace. | shipped states | `pr-ops`, `herdr`, `footer-ui`, `idle-cache`, `idle-downshift`, `retro`, `trace` |
| `standard` | Every toggleable feature in its shipped state; the package defaults. | shipped states | none |
| `full` | Every toggleable feature on, safety relaxations included (git tools, children may push, workflow scripts, remote intercom). | `codemode`, `reviewer-climb`, `plan-review`, `orientation`, `git-tools`, `pr-ops`, `review-required`, `children-may-push`, `workflow-scripts`, `remote-intercom`, `idle-cache`, `idle-downshift`, `herdr`, `footer-ui`, `retro`, `trace` | none |

## Overlay quick start

What a private or organisation overlay usually sets, in this order (see [overlays](overlays.md)):

1. [model-map](#model-map): Map every role you use to a model per provider (or apply a preset first and adjust it). Example: `{"providers": {"<provider>": {"roles": {"foreman": {"model": "<provider>/<big-model>"}, "builder": {"model": "<provider>/<mid-model>"}}}}}`
2. [ladder](#ladder): Give the builder and reviewer a strong rung so the ladder has somewhere to climb. Example: `{"providers": {"<provider>": {"roles": {"builder": {"strong": {"model": "<provider>/<stronger-model>"}}}}}}`
3. [sessions](#sessions): pi-intercom ships with the package; keep it unless you set up with --no-intercom, and leave remote intercom off.
4. [sync](#sync): List the repositories `/sync` may pull, commit and push; user or overlay config only. Example: `{"sync": {"repos": [{"path": "<absolute path of a repository you trust>", "branch": "main", "paths": ["<glob of paths to sync>"]}]}}`
5. [repo-backlog](#repo-backlog): Point the retro backlog at a directory or repository store you keep; user or overlay config only. Example: `{"retro": {"repoBacklog": [{"path": "<absolute path or glob>", "commit": false}]}}`
6. [review-panel](#review-panel): Add a second vendor's model as a silent shadow before a PR; user or overlay config only. Example: `{"ladder": {"reviewPanel": {"shadows": ["<other-provider>/<other-model>"], "gates": ["pre-pr"]}}}`

## Invariants

An overlay or a setup agent must not break these:

- One-way flow: an overlay consumes a pinned pi-foreman release and never patches the harness; nothing from an overlay is copied back into this repository.
- Public-repo rule: pi-foreman is generic and public. Hosts, names, private paths and model-map details of one installation belong in that installation's overlay, never in this repository.
- Tighten-only safety: the project and session layers may only make `safety.*` and the keys marked tighten-only stricter, so a cloned repository cannot loosen your guards.
- Project trust: the project layer `.pi/foreman.json` is read only after Pi's project trust is resolved; project packages also load only after trust.
- Role ids stay neutral (`foreman`, `planner`, `explorer`, `builder`, `reviewer`, `senior-reviewer`, `finalizer`); display names come only from config.
- Setup owns the `subagents` block in `settings.json`: put your rules into `foreman.json` and your policy file, a hand edit of the generated block is overwritten.
- Children never open PRs and reach the foreman through `contact_supervisor`, never through pi-intercom.
