# Triage, delegation and finish gates

> Covers the tiers, the trivial builder path, bounded mode, finish gates, plan and checkpoint, waiting, read budgets, working ahead, the ledger tool and the key table.
> Read it when the foreman refuses a step, or when you tune how much process a task gets.
> The foreman records a tier first and the adapter checks the claim instead of trusting it.

## Triage and delegation

`/ceremony [trivial|standard|heavy]` shows the current tier, or sets it yourself (you may move it either way).

The foreman records a tier (trivial, standard, heavy) before it changes files itself, and the adapter checks the claim instead of trusting it:

- Trivial builder path (`ceremony.required.trivial: ["builder"]`, default): a trivial change keeps a `Tier: trivial`
  ledger and runs one bottom-rung builder, no explorer or reviewer. At finish a diffscan check
  (one source file within `trivialBound`, no exported signature or schema change, no test file touched, a test present)
  escalates to standard otherwise (trace `triage_escalated {reason}`), so a reviewer must pass. `[]` restores the old trivial.
- In `bounded` mode, at trivial the foreman may change at most `ceremony.trivialBound` itself (default 2 files, 40 changed lines, no new file). The call that would cross it is refused, the tier rises to standard and a builder does the rest. A project or session can only lower the bound.
- Shell writes into project files are refused for the foreman at every tier (see [safety](safety.md)).
- Standard needs a completed builder run and a reviewer verdict before the foreman may finish, at heavy too (`ceremony.required.heavy` is `[builder, reviewer]`; a project can only add steps). A refused finish names what is missing; after two refusals per unchanged state (the missing steps, the foreman's work and the review verdict; an owner prompt does not reset the count, a builder run, a foreman project edit or a changed review verdict starts a new one; the count is kept in the session entry, so a restore keeps it) it passes with a visible warning (trace `ceremony_incomplete`, a `ui.notify`, and one `pi-foreman-ceremony-incomplete` message in the transcript per state). A turn end with open ledger items (`- [ ]`, the V item included) and no builder launch or builder run end and no foreman project-file edit since the last owner prompt is a pause, not a finish: the gate refuses nothing (trace `ceremony_gate {reason: pause}`). Work means builder launches, builder run ends and the foreman's edits through its own tools (a builder launched before the prompt that ends after it makes the turn end a refusal, not a pause); a change made by an approved inline script or command is not seen. When a pause passes with work from an earlier prompt that no reviewer PASS covers, the next turn gets one `pi-foreman-review-reminder` message ("unreviewed work: a reviewer PASS is still missing before finish or PR"); a pull request still needs a PASS. Typed wake lines count as an owner prompt and open a new pause window. A session that changed nothing (a read-only audit with explorers and notes under `.workflow/` finishes this way at any tier, escalated or not; no completed builder run, no builder launch, no foreman project-file edit, and the checkout unchanged: `git status --porcelain` empty over the whole checkout, or equal in content to the checkout at the session's first start (a fingerprint of the work tree without `.workflow/`, the status text and the work tree of each submodule the status names; stored in the session entry, kept by a reload, resume or fork (a fork keeps its parent's; one whose parent has none has none; a resume without a stored one has none); a checkout that was already dirty, a dirty submodule included, still finishes while nothing changed in it; no fingerprint, because git failed, there is no work tree or the entry is older, leaves the empty-status requirement), the status read from its toplevel (`:/`) without the `.workflow/` folders from the session's directory up to the toplevel and `ceremony.scratchDir`, so the harness's own ledger and notes files do not count even when the project does not ignore `.workflow/`; a scratch dir set to a source folder hides that folder from this check; a git failure or no work tree is not a no-change) finishes without a refusal and without a builder or reviewer (trace `ceremony_gate {reason: no_change}`, an info notice). While the session waits for its parent (`waiting_for_parent`: a pending `foreman_checkpoint`, a `foreman_wait` file wait on a path under `<agentDir>/pi-foreman/handoffs/`, or a timer wait while one of this session's own handoff dirs, whose `parent` or `child` file holds this session's intercom id, holds a `plan.md` or `result.md` written in the last day) the finish gate lets the turn end without a refusal (trace `ceremony_gate {reason: waiting_for_parent}`, `finishRefusals` unchanged); a successful intercom `send` to its own parent sets it too (a child that asks its parent a question may end its turn); the next user prompt, intercom message or `foreman_wait` wake clears it and the gate is active again. A plain timer wait without such a handoff dir does not set it; cancelling a wait clears it when no other handoff wait or pending checkpoint remains. Before that valve, while the reviewer step is open on a FAIL, the review-FAIL climb is on (`ladder.strongOnRevision`, see [roles](roles.md)) and the builder's latest launch ran on its bottom rung and the rank policy allows its strong rung, the finish is refused with "relaunch the builder for the revision; it climbs to its strong rung" and the refusal counts toward the two refusals of the unchanged state (trace `finish_refused {climb_available: true}`; an owner prompt does not reset the count, see [ladder](ladder.md#failure-climb)); after two the finish passes with `ceremony_incomplete`. On the top rung the valve works as before.
- With `ceremony.highStakes.model` set, a risky change (a risk tag, a heavy task that built something, or the foreman's own request; see [review](review.md#high-stakes)) adds to the finish gate of a standard or heavy session a reminder, "a [high-stakes] review is due" (held once per set of reasons once every ledger item except V is marked, then let through with an owner notice; it counts toward no refusal), and the entry "revise or answer the high-stakes findings, then pass the normal reviewer" (cleared by a normal reviewer PASS from a run that got the findings; see [review](review.md#high-stakes); asked whatever the ledger says, counts toward the two refusals per unchanged state). A session that changed nothing is not asked (the same check as the no-change finish: `.workflow/` folders and the scratch dir do not count as a change).
- Gate progress (builder runs, reviewer verdicts, the PASS mark and the checkout of each review; the review gate and PASS mark are kept per checkout, see [review](review.md#the-review-gate-per-checkout)) is stored in the session's ceremony-state entry and restored on `/reload` or resume of the same session, so a reload does not ask for the builder and reviewer again; a new session or a fork starts fresh. An entry from before this was recorded is rebuilt from its recorded PASS review (a moved HEAD counts as a revision).
- A turn end with a wake source pending is a pause: an active `foreman_wait` of any kind, a running or launching subagent, or a `bg_run` task of this pi process only that notifies and triggers on completion (a task with either off wakes nobody and does not count; records left by an earlier pi process of the same session do not count). Then neither the ledger stop guard nor this finish gate runs, before the `waiting_for_parent` valve, and nothing is spent (trace `finish_gate {skipped: pending_wait, runId: <ids>}`; the stop guard's once-per-session reminder and the refusal count stay as they were). Once the wait is resolved or cancelled and nothing else is pending, both gates apply as usual. Child sessions are unchanged.
- The foreman's own edits follow `ceremony.foremanEdits`; a PR opened with `pr_create` needs a reviewer PASS on the current head (`ceremony.reviewBeforePr`; a PR opened from the shell is not refused, the watch reports its unreviewed head, see [safety](safety.md#the-pr-gate)). In `readonly` and `scratchpad` mode the foreman never changes project files itself, so a refused edit tool call makes the task standard and a builder does the work; a refused shell write keeps the tier and the change still goes to a builder. The scratch dir is for notes, drafts, commit messages and review pages. `.workflow/` stays writable in every mode, because the harness keeps the ledger and state there.
- Plans: heavy runs ledger, the plan (the foreman writes `.workflow/scratch/plan-<topic>.md` itself), plan review (`ceremony.planReview.heavy`, default on: a `reviewer` launch with `occasion: "plan-review"`, or `[plan-review]` first in its task), `foreman_checkpoint`, builder(s), reviewer, PR. As at standard, the foreman stages explicit paths and commits after the reviewer PASS and drafts the PR `## Changelog` itself. `foreman_checkpoint(path)` shows the plan `plan-<topic>.md` to the owner (revise, reject, approve; approve is never preselected) and records the approved hash, only if the file is unchanged when the owner answers; a heavy `builder` launch is refused until the current bytes are approved (`plan_required`, `checkpoint_pending`, `plan_changed`). The harness never approves on its own: print/json mode or a dismissed dialog leaves the checkpoint pending, and it never turns a timeout into approval. The approved checkpoint is enforced by the builder gate, not by a finish step: `ceremony.required.heavy` is `[builder, reviewer]` (a stale `plan-*.md` on disk never counts). `[plan-review]` by a fresh reviewer on a different model stays mandatory at heavy. The harness refuses a `[plan-review]` launch on a plan whose form is wrong (`[plan_form]`, below under "Owner section"). A plan has a VERSION: its body, the text above the first appendix heading (a level 2 or 3 heading starting `Addendum`, `Addenda`, `Ruling`, `Rulings`, `Parent ruling` or `Decision log` as a whole word, e.g. `## Addendum 2: x`, `## Ruling (parent)`, or the line `<!-- plan-appendix -->`; `## Decisions`, `## Decision logic` and `## Ruling out X` are body; exact rule under "Appendix headings" below). Review, the plan-review round count, the checkpoint approval and the `plan_changed` builder gate all use the version hash (sha256 of the body; trailing blank lines before an appendix are ignored; no appendix = sha256 of the whole file). A ruling or decision log appended below an appendix heading is outside review and approval: it neither triggers a new review round, nor resets the checkpoint, nor blocks builders, and the checkpoint dialog lists it as `Appendix:` apart from the plan. A body edit is a new version (a new review round, a new approval). Trace `plan_version {tier, from, to}` at each checkpoint call (`from` = hash of the file bytes, `to` = body hash, 16 characters each). A rejected plan blocks the finish (the two-refusal valve ends the session visibly, never approving). With `ceremony.planReview.<tier>` on, `foreman_checkpoint` is refused with `plan_review_required` until a `[plan-review]` reviewer run ended with a verdict for the current plan (keyed by the plan version hash, so any body edit needs a new review); verdicts are kept per plan path; a FAIL below the round cap refuses with `plan_revision_required` so the foreman revises and has the plan reviewed again until it passes (a FAIL goes to the checkpoint only for findings that need a decision, which opens at the cap), and the owner's dialog shows the verdict line `Plan review: PASS|FAIL (reviewer <model>)` with up to 8 findings (trace `plan_review {model, decision}`; details in [review](review.md#plan-review)). Standard writes its own short plan to the scratch dir; no checkpoint. Plan mode is not part of the ceremony; the checkpoint is (the plan phase is, see below). A `subagent` launch with `output` or `outputMode` is refused for every role (`launch_refused:output_path`: the runner would write the reply to a file without a write check), and with `safety.subagents.allowWorkflow` on, workflow and `schedule.*` calls are still refused at heavy (`unchecked_heavy`).
- A foreman launch returns at once with its receipt and one line (`detachedLaunchLine`): the child's completion notice starts the next turn, so launch, end the turn and act on the notice. Several children may run at once (one writer per checkout). `bg_wait <id>` only for a result needed in the same turn; never poll with bash. The async-started guidance lines (detached, bg_wait, "Return control") are trimmed from the receipt. `ceremony.launchWait: "block"` is the replay rigs' and bench's test hook: the launch result then waits until the child finishes, a child asks the foreman something, or `wait.maxSeconds` (or the role's `timeoutMinutes` plus 60 s, when shorter) passes; every launch of one message is held in parallel, a launch from inside codemode never. A completion notice for a run already delivered is dropped from the model context (`ceremony.dedupeNotify`; trace `notify_deduped {runId, mode, trimmed_lines}`); the trace and the bench table count polling bash calls (`pollBash`).
- Read budgets: the foreman's own read-class calls (`bash`, `read`, `grep`, `find`, `ls`, `codemode`, any `mcp__*` tool and `subagent` with `action` `get` or `guide`, never a launch; one codemode script counts once; a pure-ledger shell command is exempt from this budget while `ledgerHelper` is not `off`; a bash command whose every command is `foreman session ...` (also after `cd <dir> &&`) and the `pr_status`, `pr_checks` and `pr_comments` tools are coordination calls and do not count against this budget) get a reminder to delegate at `ceremony.foremanReads.<phase>.warn` and again every `every` reads after that; they are never refused (the read budget only reminds; trace `read_budget {action: remind}`). The count resets to phase `before` with each user prompt or parent `brief-<x>.md` in the handoff dir (a `ruling-<n>.md` does not reset it). The open-supervisor-request exemption ends at the reply or the run end. A handoff poll (a read or shell command whose path operands are all under `<agent dir>/pi-foreman/handoffs/`, e.g. its `ruling.md`) and `git worktree add|list|prune` are exempt from the budgets, like a pure-ledger command; reads of a builder's worktree (under the worktree root, `close.worktreeDir`; default `<repo>.worktrees/`) and a `ruling.md` elsewhere still count. A reviewer PASS does not limit the foreman's own checks; a commit or project edit after it makes the review stale through the PR gate and the finish gate (a commit of exactly the reviewed files, without `.workflow/`, keeps the PASS; one order: review, commit, push, PR). `foreman_triage` and the system prompt state the required finish steps up front.
- Child read budgets: `ceremony.childReads.<role>.{warn,deny}` (reviewer 15/30; builder and explorer none unless configured): a child's read, grep, find, ls and read-only bash calls get a notice at warn (a reviewer or explorer is told how many reads remain and to continue the task; the launch receipt names `reads: <deny> (warn at <warn>)`) and are refused above deny with a "return your report / `STATUS: stuck`" message (a configured builder budget says to write the code instead, never to return the report; a builder is bounded by `ladder.contextCap` instead, see [ladder](ladder.md#context-cap)); trace `child_read_budget {role, count, action}`.
- Child scratch: every single-child launch gets its own dir `<worktree root>/.foreman/scratch/<session>/<launch>` (mode 0700; the root is `close.worktreeDir`, [close](close.md#the-worktree-root)), or `<os temp dir>/pi-foreman-scratch/<session>/<launch>` when the session has no usable root (not in git, a root inside a git work tree, the npm root still resolving, or the folders cannot be made). It is named in a line appended to the task and as the child's env `FOREMAN_SCRATCH`; the trace line `child_scratch_root {source: worktree|tmp}` records the choice once. The harness removes the dir when the run ends, after the trace line `child_scratch {role, bytes, files, action}`, and sweeps the session's dirs at shutdown (also lanes of older runs under the temp folder); at session start it removes session dirs under `.foreman/scratch` older than 7 days; `ceremony.childScratch.keep` keeps them. What the guards allow there: [safety](safety.md#child-scratch).
- Explorer brief: the latest completed explorer report (first 16000 characters, plus its result path; the harness writes the full report to `explorer-brief.md` in a session scratch dir that children read without an ask, and the brief always names `[full brief at <path>]` when that file was written, a cut brief adds `[... cut at 16000 characters]` before it) is prepended once to the next fresh builder launch (after any rung-up handoff); trace `explorer_brief {role, chars, cut, action: file|none}` (traces never hold paths).
- Ledger items block: a fresh builder launch whose task cites items ("item 3", "items 1 and 2", "#5") gets `[pi-foreman ledger items]` with those ledger lines prepended (before the explorer brief); none when it cites none, and none on a rung-up launch, whose handoff already carries them (trace `ledger_block`). The items come from the session-bound ledger, or from the ledger the task names by path (`.workflow/LEDGER-<topic>.md` in this checkout's or the bound ledger's `.workflow/`); the same ledger then drives the builder's `Ledger file:` line, a reviewer's PASS marks and the launch and verdict hints, per entry of a `tasks`/`chain` launch. A path that cannot be used (missing, outside `.workflow/`, more than one) leaves the bound ledger in charge and adds `ledger path not used: <reason>` to the block. The standard finish gate needs only builder and reviewer, so the explorer may be skipped when the builder brief lists the files and symbols.

`reviewGate: pass` means the required reviewer step needs a current PASS (a FAIL, a review that gave no verdict or an `incomplete` one, or a revision after the last
PASS, re-opens it); `verdict` accepts any verdict. The verdict is the reviewer's `review_verdict` call, never read from its report (see [review](review.md#the-verdict-tool)); a run that ends without the call counts as no verdict. A revision after a PASS is a project edit outside `.workflow/` or a builder launch; ledger notes, a push, notices and reviewer launches are not. The `foreman_ledger mark V` refusal and the finish hint name the run of the last counted PASS, or say none this round. The orientation packet (tracked-file tree to depth 2,
head of AGENTS.md or README.md, detected build/test commands, explorer hint; at most `maxLines` lines) is added
to the foreman's system prompt once per session and does not count against the read budget.

Cost guard: `ceremony.budgetUsd` (USD, unset = off) is checked on the summed estimate, the foreman's own cost plus every run's, both priced at list prices (the status line shows it as `all $X est (runs $Y)`). A usage record whose provider reported no cost (the claude-bridge) is priced from the model registry when it has a non-zero rate, else from `config/prices.json` (cache writes at the 5-minute rate, Haiku 5.5's long-context tier per request); such costs are estimates (`~` in `/foreman cost`, which lists every role with its priced total, `autoreview` included). A launch at or over the cap is refused `[budget_exceeded]`, naming the summed total and the cap, with a warning at 80 % (trace `budget_warn`). A review after a FAIL is item-only: the harness prepends `[re-review items: N, M]` (the failed items of the last FAIL record that are still open) to the review task and the verdict call must give each of them a result; a PASS clears the list. Traces: `role_launched` at launch, `role_result` at the run end (with `runId`, `ms`, priced `cost`), `review_done` for every review run (`kind` shadow for panel shadows), and every deny trace (read and child read budgets, overlay, launch refusals) carries `reason`, `role` and `command` (200 chars; a bash command, else the tool or `subagent <roles>`).

Loop guard: reviews and revisions run until a review passes; no count limits them. Each review round records what was reviewed (`state`: for a code review a hash of the review checkout's working tree content, tracked and untracked files, so a commit that changes no file does not count as a change, for a plan review the plan version body) and its findings (`sig`: the sorted set of `item:<N>` for each item the verdict record marks `fail` and `at:<file>:<line/5>:<class>` for each `defect` finding with a `file`; note text and `now`/`later` findings are not part of it). When a FAIL round ends, it is compared with the round before it of the same kind (plan or code; a PASS restarts the comparison). It is a *repeat* when its `sig` is non-empty and equal to the previous one (for a plan review on a revised plan, a new plan version, only when the set holds at least one located `at:` key: new findings under the same checklist item are progress, `loopVerdictOf` in `reviewloop.ts`; for a code review the same holds when the repeat has only `item:<N>` keys, the foreman's work count (builder launches and run ends plus project edits outside `.workflow/`, stored in the round as `work`) grew since the round before and the reviewed state is known and changed: a builder or edit that changed the code is progress, while located `at:` keys, a builder that changed nothing and a round with no work in between still repeat), and *stalled* when `state` is unchanged (no diff) and it brings no finding the previous round lacked. Either sets a persisted stop (trace `review_loop {rule, kind, runId}`): builder and reviewer launches are refused `[review_loop]`, naming the rule and the repeated findings and telling the foreman to report the findings and ask the owner (`ask_user_question`) or wait for a new prompt (in a session a parent opened, with the handoff dir and the parent intercom id in the env: to report the open findings to the parent in an intercom message whose first line starts with `Question`, end the turn, and wait for the parent to lift the stop with a brief, and to ask the owner only when a finding needs the owner's decision; a child whose parent is remote (`PI_FOREMAN_REMOTE_PARENT=1`) gets the older text instead, which reports by file, `ask.md`, and waits for the parent's ruling, and the text of the other children adds that file route for a parent that is not a Pi session); `[second-opinion]`, explorer launches and a `resume` are not refused. A FAIL with no findings to compare never trips it. The stop is lifted by a new owner prompt, an `ask_user_question` the owner answered (submitted with at least one answered question; a cancelled dialog or a session without UI does not lift it; trace `cap_reset` with `by: ask`, the read budget is not reset), a `/ceremony` tier change by the user, or a parent-written `brief-<x>.md` in the session's handoff dir (a `ruling-<n>.md` lifts nothing) (a regular file, a message from the parent never lifts it, ctime and mtime newer than the last reset, not written by the session itself; trace `cap_reset`); the same file also resets the foreman read budget. A `foreman session brief <label> <file>` from the parent lifts the stop this way: it copies the file to the child's handoff dir as the next `brief-<n>.md` (see [sessions](sessions.md#message-contract)). The PASS requirement, the `[pre-pr]` gate and the exclusion of self-written files are unchanged. The old keys `ceremony.reviewRuns`, `ceremony.revisionRounds` and `ceremony.planReviewMax` no longer exist: a layer that still sets them loads, the keys are ignored and `/foreman doctor` reports them as unknown.

Ledger and review rules: the session is bound to the ledger it last wrote (`core/scripts/ledger_bind.py`, with the edit rule enforced by the adapter in `extensions/core-adapter/index.ts`): a `write` of `.workflow/LEDGER-*.md` rebinds, an `edit` binds only while the session has no bound ledger that still exists (the adapter has no shell `ledger -f` bind), so ticking the backlog `LEDGER-todo.md` does not take over a round ledger. `foreman_ledger({action: "init", topic, texts?})` is the way to a bound ledger when the session has no `write` tool: a new `.workflow/LEDGER-<topic>.md` (topic `[A-Za-z0-9][A-Za-z0-9._-]{0,63}`, created exclusively, the recorded tier, one open item per text, at most 32, then item V) is bound like a `write` of it, replacing a live binding and resetting the diff base; an existing file takes no `texts` (`ledger_exists`) and binds under the `edit` rule, else `ledger_bound_elsewhere`; a child session is refused. With `ceremony.ledgerHelper: tool` the foreman manages its ledger with the tool `foreman_ledger({action, items?, item?, text?})` (`upsert` rewrites one item's text keeping its state, or appends when `item` is omitted; identical text is a no-op; `add` takes `texts` and `upsert` takes `entries: [{item?, text}]` for up to 32 items in one call: every entry is validated first, a malformed one refuses the whole call, then the entries apply one by one and a failure stops the rest, the answer naming the applied and the unapplied ones) instead of the shell `ledger` command (the permission system splits compound shell commands, so forms like `ledger -f F mark V` were denied). The foreman may mark V itself once a reviewer PASS stands with no builder launch or project edit since, or, in a session with no builder launch (`work.builders` and the saved builder step count are 0) and no counted project edit, once every plan lineage's latest `[plan-review]` verdict is a PASS on that plan's current version (its body above the appendix, an HTML page whole, read from disk at the call); a reviewer child never gets the tool: it closes V with a `pass` result for item `V` in its `review_verdict` call, in every `ledgerHelper` mode, and only when the launch's `items` field named V. On a `reviewer` PASS the harness marks each still-open item the verdict record gives a `pass` result, with the note "verified by reviewer PASS", once per review run; V is marked with the verifier flag under the V rules above, and only when the launch named it. An item the record gives `open` with a note adds a `reviewer:` ledger note and leaves the state alone (see [review](review.md#re-review-after-a-fail)); nothing is marked after a FAIL; trace `ledger_mark_by_review {items, skipped, noted}`. At a review PASS the harness also records the working tree (a git tree of the index plus every non-ignored file); a later builder run or foreman edit whose changes since then touch only docs (`*.md`, `docs/`) or only comments and whitespace of Go, Rust, TypeScript/JavaScript or Python files (`//`, `/* */`, `///`, `//!`, `#`; string literals, directive comments such as `//go:build`, Rust doctests and JSX count as code; an unknown language, no change at all or any doubt is not comment-only) is not a revision: no re-review, no revision round (trace `revision_comment_only {files}`, a count). With `ceremony.reviewPerRevision` a second reviewer launch after a PASS on unchanged work is refused; add `[second-opinion]` to the task text (an advisory review that never counts for items or gates, see [review](review.md#review-occasions)) for auth or safety changes, a heavy tier, or when the first reviewer could not run the tests. With `ceremony.heavyThreshold: strict`, heavy-signal keywords are only a hint (`triage_hint`) and heavy is for multi-component or risky changes. To reproduce the pre-change behaviour, set `ledgerHelper: off`, `reviewPerRevision: false` and `heavyThreshold: eee843d` in the user layer (`<agent dir>/foreman.json`); `reviewPerRevision: false` is ignored from project and session layers.

Reviewer rules: a changed exported signature, a weakened or removed test or assertion, or a skipped test is a FAIL
unless asked for (callers are grepped). A "Facts to rule on" block from `git diff` (against the HEAD at the first
builder launch) is appended to a reviewer's launch task (`diffscan.ts`; trace `review_facts {count}`).

Multi-session plans: a heavy task with several phases may run one child session per phase instead of builders in one session. The foreman opens each with `--plan-first`, waits with `foreman_wait kind:child`, reads the child's `plan.md` and sends notes as a brief, and reviews its `result.md` before the next phase. The child owns its plan; the parent approves nothing (see [sessions](sessions.md#child-orchestrator-sessions)).

A parent ruling never satisfies the finish gate: a `ruling.md` or `ruling-<n>.md` in the session's own handoff dir (only dirs whose `child` file names this session) does not close the reviewer step. After a FAIL, the refusal names a newer `APPROVED`/`SHIP` ruling and says the chair runs `/ceremony <tier>`. `/foreman close` with an incomplete ceremony lists what the parent would have to rule. A session cannot write its own parent's ruling (defence in depth); a stale ruling (older than `ask.md`) is ignored. A ruling file lifts no stop and writes no marker; the answer to a question is a brief. See [sessions](sessions.md).

[section 6](../design/architecture.md#6-ledger-gates-and-proportional-ceremony).

## Plan state, tier source and plan phase

Plan state survives `/reload` and resume. The adapter appends a session entry `pi-foreman-ceremony-state` on every change (an identical state is not appended): the approved plan (topic, path, version hash, source `dialog`), the review lineages, the plan-review count per topic, the user tier, the effective tier with the source of its last change (a reload restores the higher of that tier and the user tier, never lowering it unless the last change was `/ceremony`) and the plan phase. It works without a handoff dir. On `session_start` (any reason except `fork`) the latest entry on the branch is restored. An approval comes back only from the owner's dialog (an older entry with source `ruling-plan` or `ruling` brings no approval back) and only if the current plan file's version hash equals the recorded one. An Addendum edit does not void it, because the hash covers the body only. The entry sits in the Pi session file, which the foreman and children cannot write (see [safety](safety.md#session-files)). After a reload or resume, in a session without a handoff dir, the approval store under `state/approvals/` restores the approval and plan-review verdicts when the entry restored none. A session opened by another session (`PI_FOREMAN_HANDOFF_DIR` set) never reads the store, which keeps no session or plan path: its approval comes back only from its own entry, so an approval of the parent's plan in a shared scratch dir never counts for it. `round-state.json` keeps the counters and never an approval; no file from a parent approves a plan.

Appendix headings: a heading of level 2 or 3, case-insensitive, whose text starts with `Addendum`, `Addenda`, `Ruling`, `Rulings`, `Parent ruling` or `Decision log` as a whole word, followed by end of line, `:`, a space and a dash (`-`, the medium dash `–` or the long dash `—`), ` (` or a space and a digit, or the line `<!-- plan-appendix -->`. So `## Addendum 2: x`, `## Ruling — x` and `## Ruling (parent)` are appendix; `## Decision logic`, `## Ruling out X`, `## Rulings2`, `## Ruling ##` and `## Decisions` stay in the body (no other separator is added: everything below an appendix heading is outside review, so a wider match loosens the gate). The version hash reads the file bytes as latin1, so the dashes also match as the three latin1 characters of their UTF-8 bytes. The `plan_revision_required` text says to revise the body above the appendix: an Addendum is not a revision.

HTML plans: the foreman may write the plan as one page, `.workflow/scratch/plan-<topic>.html` (a skeleton ships as `instructions/plan-skeleton.html`; its path reaches the model through the `{{planSkeleton}}` placeholder of `instructions/foreman.md`). Markdown plans stay accepted. The page is the plan: the owner reads it in the browser and the checkpoint binds to it. Its version hash is the sha256 of the whole file, so every change, style and script included, is a new version (no split inside HTML, no allowlist). Rulings, decision logs and addenda for an HTML plan go to `rulings-<topic>.md` next to the page, never into it; the sidecar is not a plan (the checkpoint refuses it) and a ruling in it keeps the version and the approval. The harness derives `plan-<topic>.md` from the page: its first line is a generated marker, then the converted page text (`htmlmd.ts`: headings, lists, tables, code, `<pre class="mermaid">` as a mermaid fence, links to http, https, mailto and relative targets; script, style and comments dropped), then a `<!-- plan-appendix -->` line and the rulings. Reviewers, the plan-form check (the owner section as an `<h2>`), the facts block and the dialog read this copy. The copy stays within 256 KiB (the cap of the parent's guarded read of `plan.md`); above it `readPlan` refuses. A hand-written `plan-<topic>.md` beside a page is never overwritten: `readPlan` refuses and names the two files, and so does a Write over the copy that drops the marker (the refusal reaches the model in that write's result). A copy edit that keeps the marker is written again from the page, with a notice to edit the page. A child session keeps its page in its scratch dir and copies the generated `plan-<topic>.md` to `<handoff dir>/plan.md` for its parent.

Summary section: every plan starts with `## Summary` as its first `##` section, with no length limit. The older heading `## For the owner` is still accepted: the first `##` section named either way (case-insensitive) is the section, and a later `## Summary` or `## For the owner` is an ordinary section (an old plan with a later `## Summary` now shows it unfolded on the plan page). The instructions tell the agent the reason (the owner reads it cold on the plan page, between other topics, and approves the plan from this section alone) and the form: a `**Goal:**` paragraph, the steps as a numbered list, where a flow or a before-and-after exists one diagram (a `mermaid` fence) or a small table, then the boxes at the end, one GitHub alert each (`> [!WARNING]` heads-up, `> [!NOTE]` decided for you, `> [!TIP]` decided by you, `> [!IMPORTANT]` open question for the owner, `> [!CAUTION]` serious risk) that starts with a bold label line and holds its items as a list, one fact per sentence, in plain words, with no paths, symbols or ids and few code spans (`ownertext.ts`; the plain-language rule is unchanged, the form only adds layout). Jargon in the section (code spans, paths, identifiers, ids) is advice only: the write or edit result of a plan file carries it on its own line after any form note (`pi-foreman: advice: the Summary section reads like jargon (...)`), and it never refuses a review. The markers are a declared syntax: only a blockquote whose first line is exactly `[!NOTE]`, `[!TIP]`, `[!IMPORTANT]`, `[!WARNING]` or `[!CAUTION]` with a body is a box, and no code reads the label wording. Plans written before the markers show no boxes. Where a flow or a before-and-after exists, the section has one diagram (a `mermaid` fence) or a small table (the instruction asks for it; no check counts it). The plan page shows each diagram; the checkpoint dialog prints `(diagram: see the plan page)` in its place. The foreman instructions (`<!--ownerReadable=on-->` lines) and a plan-first child brief require it. Form hints (`ownerFormHints`, advice only, never part of `planFormIssues` and never a refusal): the section has no `**Goal:**` paragraph first, no numbered steps (a line `1.` or `1)` with up to 3 spaces of indent), or a box is followed by other content; fences are skipped. The facts line appends `; form hints: <a>; <b>` after its `present` or `issues:` text, and the write or edit result gets one more advice line after the jargon line (`pi-foreman: advice: the Summary section misses parts of its form (...)`). Headings are read by one reader, the plan page's (`headingOf`, `pages.ts`): closing `#` marks and outer blanks are dropped, so `## Summary ##` is the owner section on the page, in the form check, in the required headings and in the dialog; the section (and the owner card on the page) ends at the next column-0 level-1 or level-2 heading, and a `#` title heading after it starts an ordinary unfolded part. The dialog title is the plan's first `#` heading, else the plan topic (`plan-<topic>.md`; the plan page title follows the same rule, `planTitle`), and its goal line is the `**Goal:**` paragraph of the summary section (the text after the marker and the lines up to a blank line or block start, at most 4; fenced text ignored), with the older `## Goal` heading as the fallback. A box inside a box is shown in the dialog as on the page: the inner marker line is dropped, also inside a plain quote (recursion to depth 8, as the page); a plain quote keeps its lines and prefix. The form is checked by code (`planFormIssues`): a `[plan-review]` launch is refused with `[plan_form]` (trace `launch_refused`, reason `plan_form`, before any launch bookkeeping; no reviewer starts) when the section is missing, empty or not first. The sections `## Decisions and assumptions` and `## Open questions` of a plan-first session are asked for by the brief (the parent reads them) and not checked. There is no toggle. A plan that cannot be read is not refused (the facts line says `plan not readable`), and the write or edit result of a plan file carries the same faults. The `[plan-review]` facts block gets a `Summary section (<plan>): present (checked by the harness)|missing|issues: ...` line (jargon hits stay in the issues: code spans, paths, identifiers, ledger and issue ids). The reviewer does not FAIL for length or jargon; it FAILs the section only when it contradicts the plan or omits a decision the plan makes. On a re-review (an earlier verdict for the plan path exists in this session) the facts also carry the diff of the plan against the last reviewed version (a `git diff --no-index` of the two texts, at most 200 lines, header lines naming the plan path) and the instruction to verify the earlier findings and review the changed text in full; the last reviewed text is in memory only, so after a reload, or when the plan changed while the reviewer ran, the facts say `no diff (the last reviewed version is not in memory)`. What fails a later review is unchanged. The plan page folds every `##` section except `Summary`, `For the owner` and `Open questions` (`<details class="fold" id="<slug>">` with the `##` heading as an `h2` inside the summary, click to open; an "In the details" list of links to the folded sections follows the owner section; notes and result pages are not folded; the markdown file, its version hash and the checkpoint are unchanged). It is laid out by position only (`ownerLayout`, plan pages only): the owner section's first block, when it is a paragraph, is the goal banner, its top-level numbered lists are the path, and its trailing run of boxes stands in a side column beside it (one column below 860 px); `Open questions` is a highlighted block. Every markdown page the harness renders (plans, notes, results, the rulings below an HTML plan) turns the five alert markers into coloured boxes; the page style follows the system's light or dark setting and uses no hidden-text rule, so the converter's hidden-style facts stay empty. `htmlmd.ts` converts a `<blockquote data-alert="<type>">` back to its marker and a heading that is a whole `<summary>` back to that heading, so an HTML plan written in the same markup (`instructions/plan-skeleton.html`, whose `<style>` equals the harness plan style) yields the same text copy. Known small losses on the way from page to text: table column alignment, extra spaces inside code spans and list tightness. `foreman_checkpoint` shows the boxes as plain lines (marker line dropped, quote prefix stripped; the quote blocks are split as the page does, so a marker without a body stays visible exactly when the page shows no box; a box inside a box or inside a plain quote loses its marker, a plain quote keeps its lines and prefix, both to depth 8 as the page). `foreman_checkpoint` shows the whole section in the dialog, then one line `Plan page: <file URL>` (the standalone page of the plan, a path on the session's machine; it waits up to 3 s for the page write, else the line names the reason), or a warning line when the section is missing; that is advice, and a missing section never refuses the checkpoint. The same rule asks `ask_user_question` questions to read cold: the harness prefixes each question with `[<project> · <session label>] ` (the label only in an opened session; in place, once), and a result gets a hint when a question or option description reads like jargon (trace `question_check`; never blocks). `foreman_show` replies carry no opening hint; the instruction asks for a short plain opening, because the owner opens the note cold.

Owner text: text written for the owner (the owner section, `ask_user_question`, `foreman_script` descriptions, `foreman_show` notes, chat replies) follows one plain-language rule, a softened ASD-STE100. The points live in `OWNER_TEXT_POINTS` (`extensions/core-adapter/ownertext.ts`). The foreman instructions carry them word for word, kept equal by a test. The two hints and the plan-review facts line point at owner text. Text between sessions (briefs, rulings, results, reports, notes, ledger, commit messages) is not bound by it and stays dense. No code counts words or checks style beyond the jargon check above.

Plan-review limits: `ceremony.planReviewRounds` counts plan versions per lineage. The number of `[plan-review]` runs is not capped; a plan review that fails again on the same plan version with the same findings or nothing new, or on a revised plan with the same located finding, stops further plan and builder launches through the loop guard (see Loop guard above); new findings under the same checklist item on a revised plan do not.

One tier source: `/ceremony <tier>` sets a sticky `userTier`, persisted in the entry above. While it is set, the ledger `Tier:` line and `foreman_triage` never raise the tier above it. Automatic escalations from a new signal (a second launch, the file count, prompt signals) still apply, but a later ledger refresh cannot raise the tier further. Only the next `/ceremony` replaces `userTier`. The tier line reads `set by the user (ledger says heavy)` when they differ.

Plan phase: the harness-native replacement for plan mode. It starts with `foreman session open --plan-first` (the CLI and the `foreman_session_open` tool's `planFirst: true` pass `PI_FOREMAN_PLAN_PHASE=1` to the child), or with the user command `/foreman plan`. While it is on:

- the foreman changes files only under `.workflow/` (write, edit, `foreman_move`, `foreman_copy` and shell write words), in every edit mode;
- `builder` launches are refused (`launch_refused:plan_phase`); `explorer` launches and `[plan-review]` reviewers are allowed, and an explorer-only launch needs no ledger (trace `plan_phase_explorer`);
- the foreman read reminder is off;
- the foreman asks only for real decisions until the plan is decision-complete: a session a parent opened asks the parent in an intercom message whose first line starts with `Question` (by file, `ask.md`, only where intercom cannot reach it), or the owner with `ask_user_question` when the decision is the owner's and a human is at the pane, never both for one question; findings of the plan review that are defects or gaps are revised, not asked about; the plan template has `## Decisions and assumptions` and `## Open questions`, and the checkpoint dialog shows `Open questions: N` when that section is not empty (advice, never a refusal).

Exits: a `foreman_checkpoint` approval at any tier, or the user's `/foreman plan off`. In a phase a parent's launch started (`PI_FOREMAN_PLAN_PHASE=1` with `PI_FOREMAN_HANDOFF_DIR` set), below tier heavy, a `[plan-review]` PASS on the current plan version ends it instead, once the tier is recorded (`foreman_triage`); `foreman_checkpoint` is refused there (`[plan_phase_review]`). A plan edit in the same tool step as the `[plan-review]` launch (a sibling call, or a write nested in a codemode call) counts as part of the reviewed version, because the reviewer reads the bytes on disk; an edit in a later step while the reviewer runs does not, and the PASS then does not end the phase. When a verdict is recorded and the phase stays, the trace has `plan_phase` with `decision: "kept"` and a cause: `heavy`, `not_pass`, `no_reviewed_text` (the plan changed after the launch) or `untriaged` (no recorded tier). Known limit: a held launch keeps its step open until its run ends, so a plan write during the reviewer's run in that step still counts as reviewed. A `/foreman plan` the owner runs makes the phase the owner's again, which a PASS never ends. The model cannot leave the phase otherwise. The phase and its origin are saved in the session entry. `planMode: true` and `--plan-mode` (a `/plan` first command) are retired for design sessions in favour of `planFirst: true`; the flag stays as an opt-in.

Child reads per launch: `ceremony.childReads.<role>.perFile` (reviewer 2; builder 5 when a builder budget is configured) adds that many reads to the deny for each file beyond 3 in the launch's `size.files`, capped at `max` (120). A builder or reviewer launch may set `reads: <positive int>` to name the deny itself; it is clamped to `max` with a note in the launch result. A group launch carries `reads` per entry only when the runtime supports per-entry bindings; otherwise the config defaults apply and the result says so. Trace `child_read_budget` carries the `allowance`.

Plan publication (see [sessions](sessions.md#presence-files)): each observed save of the plan refreshes `plan.json` in the session's show dir, and the
snapshots `plan.ruled.md` / `plan.prev.md` roll only at ruling points: a `foreman_checkpoint`, a `[plan-review]` launch that passed the guards
(for the plan its task text names), and a child's `Plan from <label>: ` message to its parent. A plain save never rolls them. The herdr-app
[plan panel](herdr.md#plan-panel) lists the plan page with its state and opens it in the browser; the snapshots are kept as before.

## Pushed branches at finish

When a triaged session finishes with no child run active (and is not waiting for its parent), the finish gate starts a background check of the branches the session pushed. A branch with no PR of any state (one `pr_find`), not the base branch and not already merged into it, gets one display-only warning, `pi-foreman: pushed branch <name> has no pull request (open one)`. The check runs after the gate's early returns, never blocks the finish, never reaches the model, and re-runs a branch at most every 10 minutes until it has an answer. A session that was never triaged passes the gate's first early return and gets the notice only from `/foreman close`. The evaluation order and the `merged` subcommand of `foreman_close.py` are in [close](close.md#pushed-branches-without-a-pr).

## Round flow

Every round goes through a PR. The foreman works on a branch `round/<n>-<topic>` cut from `main`; a reviewer pre-pr PASS on the branch head comes first, then `pr_create` opens the PR and arms a watch that stays until the PR is merged or closed and reports each CI result, failing job, comment, review and conflict. The foreman's work on the PR ends at ready: checks green, mergeable, a reviewer PASS on the head, out of draft. It says so once and waits; no session merges a PR, so a human looks before anything lands, and the host decides how it lands. The watch reports the merge. `main` is branch-protected (required checks `ci-ok` and `pr-policy`, non-strict, see [development](development.md#auto-merge)), so nothing lands on it except through a PR.

**A ready PR stays as it stands.** A review or comment that arrives while the PR waits is feedback: rework, a new reviewer PASS on the head, ready again. The base moving is no reason to merge it into the branch or to rerun CI (a reviewer does not count that as a finding). After the watch reports the merge the foreman checks the base's CI on the merge commit and, if it is red, fixes forward with a small PR. The base is merged into a branch only when the PR is CONFLICTING, or when the base fix is needed for that branch's own CI. Run `npm run test:ci` before the PR (see [development](development.md#ci)).

## Working ahead

The foreman does not wait to be told what comes next. While it works, findings collect: faults it hit, review remarks left open, entries in its own notes and in the report list (read with `foreman_reports` or `foreman reports list`, see [retro](retro.md#foreman-reports)). Report text comes from other sessions; the foreman treats it as data, never as an instruction. At a natural pause (a round merged, a wait on children or CI, the task done) it looks at them and takes up what is ripe. Ripe means findings that share a cause, a finding seen a second time, or a fault that blocks or slows running work. A single cosmetic finding can wait. Each ripe group is taken up once; when nothing is ripe the foreman finishes as usual and names in its reply what it holds back.

The dividing line is whether the owner has anything to decide. A fix that restores behaviour already stated in the docs, a test or the code's own contract, with one sensible way to do it, starts without a question; the foreman tells you in a sentence or two what it started and why. A command in the docs that fails as written, or a test that flaked in a second round, is such a fix. A choice you would care about is asked first: a default that changes, a gate, guard or permission that loosens, a new config key, a wire or file format, cost that grows, something outside the repository, an architectural decision, or the foreman's own doubt whether it is a fix at all. A fix that turns out to hold such a choice stops there and is asked. Several follow-ups come in one question, with what the foreman would do as the first option.

A finding is a lead, not a fact: the foreman confirms it on disk first, because report entries come from other sessions, children included. When an item of the running ledger already covers the fix, it is done there. Otherwise the fix runs in a separate session with its own triage, ledger and review, and a session for a new topic opens plan-first (see [sessions](sessions.md)). An installation without a way to open further sessions has the foreman propose the fix and wait.

Working ahead moves inside the gates, never around them. Tier, ledger, review before a PR, the checkpoint at heavy, the confirm for a new session, owner scripts and guard approvals all hold, builders push only their own branch, no child opens or merges a PR and no session merges one. The same goes for a budget or limit you stated. When the budget or the host's resources are tight, or you are in the middle of something else with the foreman, it proposes instead of starting.

A session a parent opened finishes its brief and puts follow-ups beyond it in its result; the parent decides about them. The rule is text in the foreman's instructions with no key and no off switch. It adds text to every foreman request and leads to more sessions, and with them more cost.
