# Triage, delegation and finish gates

> Covers the tiers, the trivial builder path, bounded mode, finish gates, planner and checkpoint, waiting, read budgets, the ledger tool and the key table.
> Read it when the foreman refuses a step, or when you tune how much process a task gets.
> The foreman records a tier first and the adapter checks the claim instead of trusting it.

## Triage and delegation

`/ceremony [trivial|standard|heavy]` shows the current tier, or sets it yourself (you may move it either way).

The foreman records a tier (trivial, standard, heavy) before it changes files itself, and the adapter checks the claim instead of trusting it:

- Trivial builder path (`ceremony.required.trivial: ["builder"]`, default): a trivial change keeps a `Tier: trivial`
  ledger and runs one bottom-rung builder, no explorer, planner, reviewer or finalizer. At finish a diffscan check
  (one source file within `trivialBound`, no exported signature or schema change, no test file touched, a test present)
  escalates to standard otherwise (trace `triage_escalated {reason}`), so a reviewer must pass. `[]` restores the old trivial.
- In `bounded` mode, at trivial the foreman may change at most `ceremony.trivialBound` itself (default 2 files, 40 changed lines, no new file). The call that would cross it is refused, the tier rises to standard and a builder does the rest. A project or session can only lower the bound.
- Shell writes into project files are refused for the foreman at every tier (see [safety](safety.md)).
- Standard needs a completed builder run and a reviewer verdict before the foreman may finish, heavy also a finalizer (`ceremony.required`, a project can only add steps). A refused finish names what is missing; after two refusals per prompt it passes with a visible warning (trace `ceremony_incomplete`). A session that changed nothing (no completed builder run, no foreman project-file edit, `git status --porcelain` empty) finishes without a refusal and without a builder or reviewer (trace `ceremony_gate {reason: no_change}`, an info notice). While the session waits for its parent (`waiting_for_parent`: a pending `foreman_checkpoint`, a `foreman_wait` file wait on a path under `<agentDir>/pi-foreman/handoffs/`, or a timer wait while one of this session's own handoff dirs, whose `parent` or `child` file holds this session's intercom id, holds a `plan.md` or `result.md` written in the last day) the finish gate lets the turn end without a refusal (trace `ceremony_gate {reason: waiting_for_parent}`, `finishRefusals` unchanged); the next user prompt, intercom message or `foreman_wait` wake clears it and the gate is active again. A plain timer wait without such a handoff dir does not set it; cancelling a wait clears it when no other handoff wait or pending checkpoint remains. Before that valve, while the reviewer step is open on a FAIL, the review-FAIL climb is on (`ladder.strongOnRevision`, see [roles](roles.md)) and the builder's latest launch ran on its bottom rung, the finish is refused with "relaunch the builder for the revision; it climbs to its strong rung" and the refusal does not count (trace `finish_refused {climb_available: true}`; at most two per prompt). On the top rung the valve works as before.
- The foreman's own edits follow `ceremony.foremanEdits`; a PR needs a reviewer PASS on the current head (`ceremony.reviewBeforePr`, see [safety](safety.md)). In `readonly` and `scratchpad` mode the foreman never changes project files itself, so a refused edit makes the task standard and a builder does the work. The scratch dir is for notes, drafts, commit messages and review pages. `.workflow/` stays writable in every mode, because the harness keeps the ledger and state there.
- Plans: heavy runs ledger, the plan (`ceremony.planner`: `self` by default, the foreman writes `.workflow/scratch/plan-<topic>.md` itself and no planner launch is required; `role` launches the `planner`), plan review (`ceremony.planReview.heavy`, default on: a `reviewer` launch with `[plan-review]` in its task), `foreman_checkpoint`, builder(s), finalizer, reviewer, PR. `planner` is a role (read-only tools plus `write`/`edit` limited to `.workflow/` and the scratch dir, never outside the workspace, single launch only). `foreman_checkpoint(path)` shows the plan `plan-<topic>.md` to the owner (revise, reject, approve; approve is never preselected) and records the approved hash, only if the file is unchanged when the owner answers; it is refused while a planner run is active; a heavy `builder` launch is refused until the current bytes are approved (`plan_required`, `checkpoint_pending`, `plan_changed`). The harness never approves on its own: print/json mode or a dismissed dialog leaves the checkpoint pending, and it never turns a timeout into approval. Under `self` the heavy `planner` step of `ceremony.required` is satisfied by the foreman's approved checkpoint of this session (a stale `plan-*.md` on disk never counts), so the finish gate names no missing planner and, with review verdicts present, no missing reviewer. Under `role` a planner launch is required, except that a planner whose resolved model's rank tier number is <= the foreman's (compared directly, whatever `ladder.childPolicy` says; an unranked planner or foreman model counts as not below; with no ranks configured the check is inert) switches the session to `self` for the rest of the session at that launch attempt: the launch is refused once with "planner sits on your own rung: plan it yourself in .workflow/scratch/plan-<topic>.md; the planner step is satisfied by your approved plan" (trace `planner_self_fallback`), so a session never ends up without a plan path. `[plan-review]` by a fresh reviewer on a different model stays mandatory at heavy on both paths. A plan has a VERSION: its body, the text above the first appendix heading (a level 2 or 3 heading starting `Addendum`, `Addenda`, `Ruling`, `Rulings`, `Parent ruling` or `Decision log` as a whole word, e.g. `## Addendum 2: x`, `## Ruling (parent)`, or the line `<!-- plan-appendix -->`; `## Decisions`, `## Decision logic` and `## Ruling out X` are body; exact rule under "Appendix headings" below). Review, the plan-review round count, the checkpoint approval and the `plan_changed` builder gate all use the version hash (sha256 of the body; trailing blank lines before an appendix are ignored; no appendix = sha256 of the whole file). A ruling or decision log appended below an appendix heading is outside review and approval: it neither triggers a new review round, nor resets the checkpoint, nor blocks builders, and the checkpoint dialog lists it as `Appendix:` apart from the plan. A body edit is a new version (a new review round, a new approval). Trace `plan_version {tier, from, to}` at each checkpoint call (`from` = hash of the file bytes, `to` = body hash, 16 characters each). A rejected plan blocks the finish (the two-refusal valve ends the session visibly, never approving). With `ceremony.planReview.<tier>` on, `foreman_checkpoint` is refused with `plan_review_required` until a `[plan-review]` reviewer run ended with a verdict for the current plan (keyed by the plan version hash, so any body edit needs a new review); verdicts are kept per plan path; the first FAIL of a plan refuses it once with `plan_revision_required` so the planner revises first, after which the re-reviewed plan opens the checkpoint whatever its verdict, and the owner's dialog shows the verdict line `Plan review: PASS|FAIL (reviewer <model>)` with up to 8 findings (trace `plan_review {model, decision}`; details in [review](review.md#plan-review)). Standard writes its own short plan to the scratch dir; no checkpoint. Plan mode is not part of the ceremony; the checkpoint is (the plan phase is, see below). A `subagent` launch with `output` or `outputMode` is refused for every role (`launch_refused:output_path`: the runner would write the reply to a file without a write check), and with `safety.subagents.allowWorkflow` on, workflow and `schedule.*` calls are still refused at heavy (`unchecked_heavy`).
- A foreman launch returns at once with its receipt and one line (`detachedLaunchLine`): the child's completion notice starts the next turn, so launch, end the turn and act on the notice. Several children may run at once (one writer per checkout). `bg_wait <id>` only for a result needed in the same turn; never poll with bash. The async-started guidance lines (detached, bg_wait, "Return control") are trimmed from the receipt. `ceremony.launchWait: "block"` is the replay rigs' and bench's test hook: the launch result then waits until the child finishes, a child asks the foreman something, or `wait.maxSeconds` (or the role's `timeoutMinutes` plus 60 s, when shorter) passes; every launch of one message is held in parallel, a launch from inside codemode never. A completion notice for a run already delivered is dropped from the model context (`ceremony.dedupeNotify`; trace `notify_deduped {runId, mode, trimmed_lines}`); the trace and the bench table count polling bash calls (`pollBash`).
- Read budgets: the foreman's own read-class calls (`bash`, `read`, `grep`, `find`, `ls`, `codemode`, any `mcp__*` tool and `subagent` with `action` `get` or `guide`, never a launch; one codemode script counts once; a pure-ledger shell command is exempt from this and the recheck budget while `ledgerHelper` is not `off`; a bash command whose every command is `foreman session ...` (also after `cd <dir> &&`) and the `pr_status`, `pr_checks` and `pr_comments` tools are coordination calls and do not count against this budget) get a reminder to delegate at `ceremony.foremanReads.<phase>.warn` and again every `every` reads after that; they are never refused (the read budget only reminds; trace `read_budget {action: remind}`). The count resets to phase `before` with each user prompt or parent `ruling-<n>.md` / `brief-<x>.md` in the handoff dir. The open-supervisor-request exemption ends at the reply or the run end. A handoff poll (a read or shell command whose path operands are all under `<agent dir>/pi-foreman/handoffs/`, e.g. its `ruling.md`) and `git worktree add|list|prune` are exempt from the budgets, like a pure-ledger command; reads of a builder's worktree (`<repo>.worktrees/`) and a `ruling.md` elsewhere still count. After a reviewer PASS (not a plan-review PASS, which does not start the window) only `ceremony.recheckBudget` own checks are allowed, then the foreman is told to finish; that budget resets on a reviewer FAIL, a builder launch, a foreman change of a project file after the PASS (not `.workflow/` or scratch notes), a new user prompt, or a parent `ruling-<n>.md` / `brief-<x>.md` in the handoff dir. `foreman_triage` and the system prompt state the required finish steps up front.
- Child read budgets: `ceremony.childReads.<role>.{warn,deny}` (builder 20/40, reviewer 15/30, explorer none): a child's read, grep, find, ls and read-only bash calls get a notice at warn and are refused above deny with a "return your report / `STATUS: stuck`" message; trace `child_read_budget {role, count, action}`.
- Child scratch: every single-child launch gets its own dir `<os temp dir>/pi-foreman-scratch/<session>/<launch>` (mode 0700), named in a line appended to the task and as the child's env `FOREMAN_SCRATCH`. The harness removes it when the run ends, after the trace line `child_scratch {role, bytes, files, action}`, and sweeps the session's dirs at shutdown; `ceremony.childScratch.keep` keeps them. What the guards allow there: [safety](safety.md#child-scratch).
- Explorer brief: the latest completed explorer report (first 16000 characters, plus its result path; the harness writes the full report to `explorer-brief.md` in a session scratch dir that children read without an ask, and the brief always names `[full brief at <path>]` when that file was written, a cut brief adds `[... cut at 16000 characters]` before it) is prepended once to the next fresh builder launch (after any rung-up handoff); trace `explorer_brief {role, chars, cut, action: file|none}` (traces never hold paths).
- Ledger items block: a fresh builder launch whose task cites items ("item 3", "items 1 and 2", "#5") gets `[pi-foreman ledger items]` with those ledger lines prepended (before the explorer brief); none when it cites none, and none on a rung-up launch, whose handoff already carries them (trace `ledger_block`). The standard finish gate needs only builder and reviewer, so the explorer may be skipped when the builder brief lists the files and symbols.

`reviewGate: pass` means the required reviewer step needs a current PASS (a FAIL, or a revision after the last
PASS, re-opens it); `verdict` accepts any verdict. A revision after a PASS is a project edit outside `.workflow/` or a builder launch; ledger notes, a push, notices and reviewer launches are not. The `foreman_ledger mark V` refusal and the finish hint name the run of the last counted PASS, or say none this round. The orientation packet (tracked-file tree to depth 2,
head of AGENTS.md or README.md, detected build/test commands, explorer hint; at most `maxLines` lines) is added
to the foreman's system prompt once per session and does not count against the read budget.

Cost guard and review cap: `ceremony.budgetUsd` (USD, unset = off) is checked on the summed estimate, the foreman's own cost plus every run's, both priced at list prices (the status line shows it as `all $X est (runs $Y)`). A usage record whose provider reported no cost (the claude-bridge) is priced from the model registry when it has a non-zero rate, else from `config/prices.json` (cache writes at the 5-minute rate, Haiku 5.5's long-context tier per request); such costs are estimates (`~` in `/foreman cost`, which lists every role with its priced total, `autoreview` included). A launch at or over the cap is refused `[budget_exceeded]`, naming the summed total and the cap, with a warning at 80 % (trace `budget_warn`). `ceremony.reviewRuns` (default 3) caps the review runs (reviewer, senior-reviewer; panel shadows excluded) per user prompt; the next review launch is refused `[review_cap]` with the count. Only a new launch counts: a `resume` of a reviewer run is neither counted nor refused. A review after a FAIL is item-only: the harness prepends `[re-review items: N, M]` (the failed items of the last FAIL verdict) to the review task and the verdict must list them; a PASS clears the list. Traces: `role_launched` at launch, `role_result` at the run end (with `runId`, `ms`, priced `cost`), `review_done` for every review run (`kind` shadow for panel shadows), and every deny trace (read, recheck and child read budgets, overlay, launch refusals) carries `reason`, `role` and `command` (200 chars; a bash command, else the tool or `subagent <roles>`).

Review cap counters: plan reviews (`[plan-review]`) and all other reviews (fix rounds, `[pre-pr]`) have separate counters, each capped by `ceremony.reviewRuns`; the `review_cap` refusal (trace `launch_refused` with `kind` `plan` or `review`) names the run count, the cap and a new owner prompt as the way out. The cap resets on a new owner prompt, or on a parent-written `ruling-<n>.md` or `brief-<x>.md` in the session's handoff dir (a regular file, ctime and mtime newer than the last reset, not written by the session itself; trace `cap_reset`). Either resets both counters, the post-PASS recheck budget and the foreman read budget. A `foreman session brief <label> <file>` from the parent lifts the caps this way: it copies the file to the child's handoff dir as the next `brief-<n>.md` (see [sessions](sessions.md#message-contract)). The PASS requirement, the `[pre-pr]` gate and the exclusion of self-written files are unchanged. When a plan review still fails with no located findings after the cap, the checkpoint dialog says that the owner may override the FAIL there.

Read budget in finalization: after a reviewer PASS or a completed finalizer, and while no child run of the session is active, no read is refused (the read budget only reminds). A plain `git commit`, `git add`, `git status` or `git log` is also exempt from the post-PASS recheck budget. It is matched by an allowlist: outside quotes only letters, digits, `_./:=@%+,-`, spaces and the separators `&&`, `||`, `;`, `|`, newline; single quotes take anything but `'`, double quotes refuse `$`, backtick and `\`. Anything else (`$'…'`, `#`, `\`, a lone `&`, `<`, `>`, `(`, `)`, an unclosed quote) is not finalization. The next started launch, a FAIL, a project edit (also after a finalizer), or a new owner prompt ends finalization. A parent-written ruling or brief file resets the read budget like a new owner prompt (see above).

Ledger and review rules: the session is bound to the ledger it last wrote (`core/scripts/ledger_bind.py`, with the edit rule enforced by the adapter in `extensions/core-adapter/index.ts`): a `write` of `.workflow/LEDGER-*.md` rebinds, an `edit` binds only while the session has no bound ledger that still exists (the adapter has no shell `ledger -f` bind), so ticking the backlog `LEDGER-todo.md` does not take over a round ledger. With `ceremony.ledgerHelper: tool` the foreman manages its ledger with the tool `foreman_ledger({action, items?, item?, text?})` (`upsert` rewrites one item's text keeping its state, or appends when `item` is omitted; identical text is a no-op) instead of the shell `ledger` command (the permission system splits compound shell commands, so forms like `ledger -f F mark V` were denied). The foreman may mark V itself once a reviewer PASS stands with no builder launch or project edit since; a reviewer child can use the tool to mark V only. On a `reviewer` PASS (not `senior-reviewer`) the harness marks each still-open item the review's `N. PASS` lines name, with the note "verified by reviewer PASS", once per review run and never V (trace `ledger_mark_by_review {items, skipped}`). At a review PASS the harness also records the working tree (a git tree of the index plus every non-ignored file); a later builder run or foreman edit whose changes since then touch only docs (`*.md`, `docs/`) or only comments and whitespace of Go, Rust, TypeScript/JavaScript or Python files (`//`, `/* */`, `///`, `//!`, `#`; string literals, directive comments such as `//go:build`, Rust doctests and JSX count as code; an unknown language, no change at all or any doubt is not comment-only) is not a revision: no re-review, no revision round (trace `revision_comment_only {files}`, a count). With `ceremony.reviewPerRevision` a second reviewer launch after a PASS on unchanged work is refused; add `[second-opinion]` to the task text (an advisory review that never counts for items or gates, see [review](review.md#review-occasions)) for auth or safety changes, a heavy tier, or when the first reviewer could not run the tests. With `ceremony.heavyThreshold: strict`, heavy-signal keywords are only a hint (`triage_hint`) and heavy is for multi-component or risky changes. To reproduce the pre-change behaviour, set `ledgerHelper: off`, `reviewPerRevision: false` and `heavyThreshold: eee843d` in the user layer (`<agent dir>/foreman.json`); `reviewPerRevision: false` is ignored from project and session layers.

Reviewer rules: a changed exported signature, a weakened or removed test or assertion, or a skipped test is a FAIL
unless asked for (callers are grepped). A "Facts to rule on" block from `git diff` (against the HEAD at the first
builder launch) is appended to a reviewer's launch task (`diffscan.ts`; trace `review_facts {count}`).

Multi-session plans: a heavy task with several phases may run one child session per phase instead of builders in one session. The foreman opens each with `--plan-first`, waits with `foreman_wait kind:child`, approves the child's `plan.md` through `ruling.md` and reviews its `result.md` before the next phase (see [sessions](sessions.md#child-orchestrator-sessions)).

A parent ruling never satisfies the finish gate: a `ruling.md` or `ruling-<n>.md` in the session's own handoff dir (only dirs whose `child` file names this session) does not close the reviewer step. After a FAIL, the refusal names a newer `APPROVED`/`SHIP` ruling and says the chair runs `/ceremony <tier>`. `/foreman close` with an incomplete ceremony lists what the parent would have to rule. A session cannot write its own parent's ruling (defence in depth); a stale ruling (older than `ask.md`) is ignored, and the harness writes `.seen` when a ruling wait wakes. See [sessions](sessions.md).

## Plan state, tier source and plan phase

Plan state survives `/reload` and resume. The adapter appends a session entry `pi-foreman-ceremony-state` on every change (an identical state is not appended): the approved plan (topic, path, version hash, source `dialog`, `ruling-plan` or `ruling`), the review lineages, the plan-review count per topic, the user tier, the effective tier with the source of its last change (a reload restores the higher of that tier and the user tier, never lowering it unless the last change was `/ceremony`) and the plan phase. It works without a handoff dir. On `session_start` (any reason except `fork`) the latest entry on the branch is restored. An approval comes back only if the current plan file's version hash equals the recorded one; for `ruling-plan` and `ruling` the verdict file must also still read `APPROVED`. An Addendum edit does not void it, because the hash covers the body only. The entry sits in the Pi session file, which the foreman and children cannot write (see [safety](safety.md#session-files)). `round-state.json` keeps the counters; its approval path also reads `ruling-plan.md` and runs only when the entry restored no approval.

Appendix headings: a heading of level 2 or 3, case-insensitive, whose text starts with `Addendum`, `Addenda`, `Ruling`, `Rulings`, `Parent ruling` or `Decision log` as a whole word, followed by end of line, `:`, ` -`, ` (` or a space and a digit, or the line `<!-- plan-appendix -->`. So `## Addendum 2: x` and `## Ruling (parent)` are appendix; `## Decision logic`, `## Ruling out X` and `## Decisions` stay in the body. The `plan_revision_required` text says to revise the body above the appendix: an Addendum is not a revision.

Plan-review limits: `ceremony.planReviewRounds` counts plan versions per lineage; `ceremony.planReviewMax` (default 4) counts `[plan-review]` runs per plan topic per session, persisted. It backstops repeats of one version and reloads. At the cap a further `[plan-review]` launch is refused (`launch_refused:plan_review_cap`). `foreman_checkpoint` then opens with the latest verdict and the line `Plan review cap reached (N reviews); the owner decides`, plus `plan changed since its last review` when the plan is newer than that verdict. In parent checkpoint mode (no dialog) the same lines go into the `foreman_checkpoint` result and the plan report to the parent.

One tier source: `/ceremony <tier>` sets a sticky `userTier`, persisted in the entry above. While it is set, the ledger `Tier:` line and `foreman_triage` never raise the tier above it. Automatic escalations from a new signal (a second launch, the file count, prompt signals) still apply, but a later ledger refresh cannot raise the tier further. Only the next `/ceremony` replaces `userTier`. The tier line reads `set by the user (ledger says heavy)` when they differ.

Plan phase: the harness-native replacement for plan mode. It starts with `foreman session open --plan-first` (the CLI and the `foreman_session_open` tool's `planFirst: true` pass `PI_FOREMAN_PLAN_PHASE=1` to the child), or with the user command `/foreman plan`. While it is on:

- the foreman changes files only under `.workflow/` (write, edit, `foreman_move`, `foreman_copy` and shell write words), in every edit mode;
- `builder` and `finalizer` launches are refused (`launch_refused:plan_phase`); `explorer` launches and `[plan-review]` reviewers are allowed, and an explorer-only launch needs no ledger (trace `plan_phase_explorer`);
- the foreman read reminder is off;
- the foreman asks its questions with `ask_user_question` until the plan is decision-complete; the plan template has `## Decisions and assumptions` and `## Open questions`, and the checkpoint dialog shows `Open questions: N` when that section is not empty (advice, never a refusal).

Exits: a `foreman_checkpoint` approval at any tier, or the user's `/foreman plan off`. The model cannot leave the phase. The phase is saved in the session entry. `planMode: true` and `--plan-mode` (a `/plan` first command) are retired for design sessions in favour of `planFirst: true`; the flag stays as an opt-in.

Child reads per launch: `ceremony.childReads.<role>.perFile` (builder 5, reviewer 2) adds that many reads to the deny for each file beyond 3 in the launch's `size.files`, capped at `max` (120). A builder or reviewer launch may set `reads: <positive int>` to name the deny itself; it is clamped to `max` with a note in the launch result. A group launch carries `reads` per entry only when the runtime supports per-entry bindings; otherwise the config defaults apply and the result says so. Trace `child_read_budget` carries the `allowance`.

## Pushed branches at finish

When a triaged session finishes with no child run active (and is not waiting for its parent), the finish gate starts a background check of the branches the session pushed. A branch with no PR of any state (one `pr_find`), not the base branch and not already merged into it, gets one display-only warning, `pi-foreman: pushed branch <name> has no pull request (open one)`. The check runs after the gate's early returns, never blocks the finish, never reaches the model, and re-runs a branch at most every 10 minutes until it has an answer. A session that was never triaged passes the gate's first early return and gets the notice only from `/foreman close`. The evaluation order and the `merged` subcommand of `foreman_close.py` are in [close](close.md#pushed-branches-without-a-pr).

## Round flow

Every round goes through a PR. The foreman works on a branch `round/<n>-<topic>` cut from `main`; a reviewer pre-pr PASS on the branch head comes first, then `pr_create` opens the PR and `pr_watch` waits for its checks. When CI is green the foreman squash-merges it. `main` is branch-protected (the seven CI checks, strict), so nothing lands on it except through that merge. Run `npm run test:ci` before the PR (see [development](development.md#ci)).
