# Safety and permissions

> Covers the shell-write guard, what the gate floors cover for git and forge commands, the PR gate, the tool gate with its floors and judge, child environment stripping, bridge isolation, the known `/sync` limit and what an install runs on your machine (including the page server).
> Read it when a command is refused or asked about, or before you loosen a rule.
> A project file can only tighten these rules; the scanners work on command strings and are not a sandbox.

## Shell-write guard

Shell writes into project files (redirects, `tee`, `sed -i`, writing scripts) are refused for the foreman at every tier; `.workflow/` (and the scratch dir in `scratchpad` mode) stays open. A `NAME=value` earlier on the same line (a relative or a quoted literal, no expansion inside) resolves a later `$NAME` in a write target, and the resolved path is judged like the literal one, except that a line that uses such a relative or quoted value is allowed only when every write on it (every target and every directory it runs in, whichever word it came from) lands inside `.workflow/`, the scratch dir, the session's own handoff dir (child-written names) or an owned dir, outside the workspace included, unless the line was already allowed without resolving the value; a line outside this closed assignment grammar (for example `"$D"/rest` with mixed quoting) is treated as unresolved, so it is refused without a tier raise even when it targets a project file; a variable the guard cannot resolve (environment only, command substitution, loop variable) keeps the write refused, the refusal names the token and the two ways out (write the path literally, or use the write tool), and it does not raise the ceremony tier unless a project file is also written. A child's shell write is floored when it lands outside its own worktree and scratch dir (`child-write-outside`; inside the foreman's checkout `child-write-foreman-checkout`), for every write the gate can read: a redirect, `tee`, `cp`/`mv`, or a heredoc fed to a plain command (`cat > file <<EOF`). A `tee` is floored only when its literal path operand lies outside the worktree, scratch dir and handoff names (`/dev/null`, `/dev/stdout` and `/dev/stderr` are exempt); a `tee` inside the worktree, or with an operand the gate cannot resolve (`$HOME`, an earlier-call variable), runs unless the gate names the target. The refusal names the offending path, the worktree root it was compared with and the sanctioned targets. A session that is a child of another session (and a subagent of it) may write the child-written names of its handoff dir (`plan.md`, `result.md`, `ask.md`, `ask-<n>.md`, `.steer-last-read.json`, anything below `work/`, never a `.git` segment) by the write tool, `cp` and `mv` without a dialog; `echo >`, `printf >` and heredoc redirects carry no built-in allow and run (default allow), as the write tool and `cp` do (`cat f > result.md` is allowed too). A parent session may write `ruling*.md` and `brief*.md` into a handoff dir it opened by redirect, `cp` or `mv` as it may by tool. The one name list is sent to the shell guard in the payload (`handoff_names`); the script keeps a built-in copy only as a fallback, and a test keeps them equal. A script fed to a shell or interpreter on stdin (`sh <<EOF`, `python3 - <<EOF`) or given as inline code (`python3 -c`, `node -e`) is not read, so what it writes meets no floor; the line runs like every unreadable line. Inside its own worktree and scratch dir a readable heredoc or redirect write runs; the builder rules still tell a child to write files with the write and edit tools, but nothing enforces that inside the worktree. The scanner works on the command string and is not a sandbox; known blind spots are listed in `design/architecture.md` [section 5](../design/architecture.md#5-safety-policy). The gate's floors (secrets, deletes, disk, push, config) read `bash`/`powershell` lines for the foreman and its children; no separate destructive script runs. The bundled background-tasks add-on's `bg_run` counts as `bash` for every shell guard; a missing or non-string `command` is refused ([sessions](sessions.md#background-runs)).

The foreman may move its checkout by branch only (r29): `git switch <b>` and `git checkout <b>` to an existing local branch, `git switch -C <b> <ref>` and `git reset --hard <ref>` are allowed when the working tree has no tracked change and HEAD is an ancestor of `<ref>` or is contained in a remote branch (the clean-tree and pushed-upstream checks of `foreman_worktree_remove`). The guard still refuses them when a check fails and names the failed precondition (trace `shell_write_allow` `reason: branch_move` on an allow). Only a plain single `git` command of these shapes qualifies (no chain, quotes, globs, `-f`, paths or `--`), optionally behind one leading `cd <dir> &&` where `<dir>` is `.`, `./` or an absolute path whose realpath is the session cwd or its git toplevel (r31; any other relative word, such as `..` or `sub/..`, a missing dir or a symlink that resolves elsewhere is not). "Contained" for `switch -C` and `reset --hard` also holds when `<ref>` already has HEAD's content: `git merge-tree --write-tree` of the two gives `<ref>`'s tree (squash merge), `git cherry` shows no unmerged commit (rebase merge), or `gh pr view` reports the branch's PR `MERGED` with HEAD as its head (5 s timeout; no gh, a detached HEAD or any error means no). These moves, and a plain `switch|checkout <b>` against `<b>`, are refused when a path that the move changes against HEAD exists untracked or ignored in the tree (it would be overwritten), or lies under a path that is not a directory, and the refusal names the file. A refusal records its failed precondition in the `shell_write_refused` trace as `precondition`. Force flags (`-f`, `--force`), `--` and chains stay refused; `git branch -f <b> <sha>`, `git branch` and `git fetch` were never refused. Children get no branch moves.

One chain is allowed (after a PR merged): `git switch <default> && git pull --ff-only [&& git branch -d|-D <b>]`, optionally behind one `cd <dir> &&`, each statement plain words and nothing else. `<default>` must be the remote default branch (`origin/HEAD`) and the switch passes the same clean-tree, existing-branch and untracked-clash checks as a lone switch; trace `shell_write_allow` `reason: post_merge`. With no `origin/HEAD` set the chain is refused with a precondition that says how to set it (for example `git remote set-head origin -a`). A refused line of several statements whose first statement is `git switch <word>` or `git checkout <word>` gets a sentence appended to the refusal that names the accepted chain, so the foreman sees the exact shape; the line itself stays refused (a `;`, a flag, a further statement and a child are not widened). The harness also returns the checkout itself when a watched PR merges ([tools](tools.md#watch)), so this chain is the manual path. The branch delete in the chain, and a lone `git branch -d|-D <b>`, are the default rule `default-git-branch-merged` instead of `danger-git` when `<b>` is merged: its tip is in `origin/<default>`, or `gh pr view` reports its PR `MERGED` at that tip. The merged fact is looked up before the gate runs (the gate never spawns gh), per segment directory; no gh, no default branch or any error means not merged. `<b>` may not be the default or a protected branch, and a child never gets the rule.

Protected targets (a host, a path or a command glob you list in `permissions.json`) are judged per call by a small model that can allow reads, and, in a session with UI that is not a child and in a child that has a route to its parent (an ask dir and `gate.childAsk: parent`), writes (presence is not read; a child with no such route, such as one launched in a group or a chain, or a session without UI asks for them), (a remote write the harness reads directly asks when the model calls it a read; in mode `model` a write verdict is the model's call and the line then goes to the main judge like any other; the exact rule is in [permissions](permissions.md#protected-targets)); floors still come first, and an error, timeout or doubt refuses with a reason, while a change the code sees asks ([permissions](permissions.md#protected-targets)). The harness sees few remote writes, so for most remote commands only the judge stands between the call and the host; a wrong read verdict on one runs. The `foreman_protect` tool changes the list only after your confirmation and is never given to a child. The trace `guard` record of a guard block (`deny` or `blocked`) now carries the redacted command and the reason, like the other deny records; allows still drop the command.

## What the gate floors cover

The tool gate's floors (see [permissions](permissions.md#floors)) hold for every session and stop these git and forge commands. The harness has no separate git or commit check; what is not in this table either goes to the judge (the [judge-first list](permissions.md#the-judge-first-list)) or runs, see the known limits below.

| Command | Floor |
|---|---|
| Any plain `git push` from a child that is not a builder from a single launch (also through `-C`, `-c`, an env prefix, `bash -c '...'` or `$( )`): a reviewer, an explorer, an unbound child, and a builder from a `tasks` or `chain` launch | `floor-git-push-child`; the foreman pushes |
| Force, force-with-lease, mirror and delete pushes, a leading `+`, an empty source (`:dst`), an empty destination (`src:`) and several `:` in a refspec, `refs/for/*`, from the foreman too | `floor-git-push-force` |
| A push to `main`, `master` (a `src:dst` refspec is checked on `dst`; a leading `refs/heads/` or `heads/` is stripped first), the remote's default branch or a `safety.git.protectedBranches` pattern, and `git push --all` | `floor-git-push-protected` |
| `git remote add`, `set-url`, `rename`, `remove` and the like | the remote floor |
| `git config` writes (`-c` before the subcommand, the values of `git clone -c` and `--config` in every spelling git accepts, shortened and clustered ones included, `--config-env`, `GIT_CONFIG_*`, editing `.git/config`) to the keys that redirect hooks, transport, credentials or run a program (hooks path, ssh command, credential helper, fsmonitor, external diff, ...) | the judge-first `danger-git-config` (it was the floor `floor-git-config`; a clear runs it, anything else is a refusal or, for an `owner` verdict with a class, the owner's dialog) |
| A child's git write into the foreman's checkout or another checkout (`git -C`, `--git-dir`, `--work-tree`, `cd <dir> && git ...`), a redirect or a heredoc there | `child-write-foreman-checkout`, `child-write-outside` |
| `rm -rf` and recursive overwrites outside the worktree | `floor-delete-outside`, `floor-overwrite-outside` |
| What the old Python delete check refused, now judge-first for the foreman and for a child alike (`danger-delete-unknown-target`, `danger-unknown-write-target`, `danger-git` for `git clean -e`, `danger-remote-command`): `find $X -delete`, a recursive `chmod`/`chown` of a variable, `truncate -s 0` of a variable, a `>` redirect and `dd of=` on a variable, `git clean` with `-e`, `--exclude` or a variable operand, a `>` redirect to a variable only where it ends the command (`echo > $F arg` runs), and the same inside a string that runs as code (`sh -c`, `eval`, a function body, `busybox`/`toybox <applet>`, `pwsh -c`, `cmd /c`, a here-document or here-string fed to a shell, also behind `ssh` or `docker exec`). The parser's own walk of `$( )` stops at depth 4, the gate's unwrapping at 16 levels; deeper text is unread and goes to the judge, a harmless deep `echo $(echo ...)` included. Every command over `ssh` or in a container (`docker exec`, `kubectl exec`, `podman exec`/`run`) is judged first (`danger-remote`), a recursive `rm` over `ssh` included; the judge decides by the effect on the other machine, so reads, a clone into a new folder, an install and a test run pass and the danger classes still ask. A literal PowerShell or cmd recursive delete outside the worktree, scratch and `/tmp`, `Remove-Item @list`, a delete fed by a recursive listing, `-EncodedCommand` and `iex` of a computed string are judged too (`danger-delete-unknown-target`). Still floors: `busybox rm -rf ~`, `f(){ rm -rf ~; }; f` and `Remove-Item -Recurse -LiteralPath:C:\Windows` are `floor-rm-system`, and a `git push` of a `src:dst` refspec whose destination is a variable is `floor-git-push-force` (a colon-less `git push origin $B` runs). A literal `find ... -delete` inside the roots, `>>` and a resolved variable inside the worktree, scratch or `/tmp` run | the judge-first kinds above; `floor-rm-system`, `floor-git-push-force` |
| A recursive delete of the home directory, the drive root or a system directory, in any spelling the gate reads (literal, `rm -rf ~`, behind `busybox` or a function body) | `floor-rm-system` |
| A child's `gh pr create`, `glab mr create` and the `pr_create` tool | `child-pr-create` |
| A child's `gh pr merge`, `glab mr merge` and a `gh api` / `glab api` PUT on `.../pulls/<n>/merge` or `.../merge_requests/<n>/merge` (a GraphQL merge mutation is not looked at) | `child-pr-merge` |
| A push, remote or protected-branch word in a line the parser cannot read | the text floors: a deny for a child, a question for the owner |
| A floored command as a line of a string field of an MCP or unlisted tool (`rm -rf /`, `sudo ls`, `git push --force origin x`) | the same text floors, on the parsed line only: prose, a field the parser cannot read and `sh('rm -rf /')` are not floored; no secret-path or config-key check on a field's command words |

Restart, privilege and disk tools (`reboot`, `sudo`, `fdisk`, ...) are floored by one rule: a cleanly parsed line is judged by the program of each segment, and the word match stays only on lines the parser cannot read or that feed text to an interpreter or carry a here-document or here-string body the text scan does not blank (any program but `cat`/`tee`); see [permissions](permissions.md#floors). Two consequences are risks, not features: on a clean line there is no second net against a parser mistake, and the `code` field of a `codemode` input is no longer word-matched (its other fields are), so the floor for a script rests on Pi gating each nested call of the script through `tool_call` (read in the pinned Pi range `1.7.x`; setup refuses another range) and on the exemption going by the tool name `codemode`. Notes are exempt too: the prose of `foreman_show` and the `foreman_session_open` brief, and of the note tools `scratchpad` and `memory_write` of the `pi-memory` package plus the owner's `floors.noteTools` list (by tool name, user file only). A string field of another tool is scanned line by line as commands; text is skipped only inside a written heredoc with a quoted tag (`cat > f <<'EOF'`). Known limit: a field can be refused for text the same shell line would pass (for example a floored word in the body of `cat > f <<EOF`); the cases are listed in [permissions](permissions.md#floors). A floor denial names the tool and the matched fragment after its unchanged sentence (redacted like the gate log: secrets shown as `[redacted]`, the home directory as `~`; control and format characters removed, cut to 80 characters), and the gate log carries the same redacted fragment. A child's repeat stop counts the floor's own sentence, so the same refusal through `read` and then `cat` still stops the run.

**Text floors read structure, not data (PR C).** The floors that match words in raw text (`reboot`, `sudo`, disk tools, `git config`, `push --force`, `npm publish`) no longer fire on text that is data. Named loosenings: (1) the body of a heredoc fed to an interpreter that reads its code from stdin (`python3 - <<EOF`, `node - <<EOF`) is data, as a `cat`/`tee` body already was; (2) inline interpreter code (`python3 -c`, `node -e`) is not shell text, so a trigger word in it fires no text floor; (3) `${NAME}` inside double quotes is a plain expansion and no longer keeps the quoted text visible to the floors; (4) the pass-through wrappers `env`, `nohup`, `nice`, `timeout`, `command`, `stdbuf` and `setsid` no longer make a line a runner: the wrapped command is its own segment; (5) the `publish` text floor needs the package program at a command position (`git diff --stat | grep -c 'npm publish'` runs). The download-shell scan reads the line with its comments blanked (from the parser's node positions), and fires on a download only when it pipes into the interpreter, the interpreter has no heredoc or here-string of its own (a heredoc counts as its own stdin only when no `<`, `<>` or input dup `<&N` on fd 0 replaces it: `python3 - <<EOF < f` does not), or the download sits in a substitution; a plain download beside a `python3 - <<EOF` is not a download into it. The settings-file text rule ignores a file name only in a heredoc body that is data: the heredoc's own command is `cat`, `tee` or a bare redirect, and no shell, interpreter or variable program reads the body through a pipe or a process substitution (`tee >(python3) <<EOF` does not count). A body fed to a shell, a runner or an unknown program (`at now <<EOF`), `env sh`, and the same words as a real command keep their floor or judge-first label. Pinned by `gate-floors-data-bodies.test.ts`. The cost: a script that builds a forbidden command in a string and runs it itself meets no text floor. That is the honest gap in [permissions](permissions.md#floors): the gate reads command lines, not what a program does.

**The `--profile` option is gone.** `foreman --profile <name>`, `PI_FOREMAN_PERMS_PROFILE` and `permissions.profile` are accepted and ignored; the launcher prints one notice on stderr. A pane that was started with a profile resumes without it. No profile widens or narrows anything any more.

The protected-branch comparison is one matcher for the push floor, `pr_create`'s push check, the push default and the text floor; see the key table for the patterns. Besides the floors, a git line of the foreman is stopped when the repository's hooks or git config changed since the last snapshot (config drift, below).

### The PR gate

`pr_create` refuses unless a reviewer PASS was recorded for the head (an `item` or `[pre-pr]` review; `[plan-review]`, `[second-opinion]` and panel shadow reviews never count, see [review](review.md#review-occasions)) (`ceremony.reviewBeforePr`; a project or session cannot turn it off). It then runs the push floors on the checkout's current branch as a synthetic `git push`, so `pr_create` from a checkout on a protected branch is refused with no host call (`pr_create: a push floor refuses pushing this branch`); an explicit `head` is not checked by this step. A later commit makes the review stale unless its tree is exactly the tree the reviewer saw (the work tree without `.workflow/`, see [the head rule](review.md#verdict-file)); one order: review, commit the reviewed files unchanged, push, `pr_create`. A commit that adds or changes anything needs a new review. The PASS sha is accepted when it is the commit of the branch the PR opens from, of its same-named remote branch (`<branch>@{push}`, `origin/<branch>`, or the upstream only when its branch name equals `<branch>`), or, only when no head is named (ref `HEAD`), of HEAD in the checkout. An explicitly named head (`pr_create {head}`) opens the gate only through its own commit or its same-named remote counterpart; a PASS on the checkout's own HEAD never opens a PR for another branch at another commit. A reviewed local head whose same-named remote branch is another, unreviewed commit is refused (`stale_review`); an upstream of another name (a worktree branch created from `origin/main` tracks the base) neither refuses nor accepts. For ref `HEAD` the current branch name is used; a detached HEAD has no remote counterpart. Outside a repository the head is unknown and no PR goes through.

Sibling checkouts (a PR from another worktree or clone than the session's): a review record keeps the checkout it ran in (realpath of the git toplevel). The `pr_create {cwd}` tool opens a PR from such a checkout only when a counting reviewer PASS is recorded for exactly that checkout and equals its current HEAD (`[pr_refused:cwd_unreviewed]`, `cwd_stale`); the upstream rule applies there too, a headless PASS stays unbound, and a PASS recorded in one sibling checkout opens no other sibling (the session checkout still opens by SHA). A high-stakes FAIL holds the PRs of its own checkout only (and of a head reviewed there), not a PR from another checkout. Each refusal names `pr_create {cwd}`.

Only the harness changes a PR's draft state, in process, and only for a PR the session itself opened with `pr_create` (see [tools](tools.md#draft)). No model-facing tool does it, the PR gate is unchanged, and `gh pr ready` from a shell is a forge write like any other and runs (see [permissions](permissions.md#the-judge-first-list)).

A PR the main session opens from the shell (`gh pr create`, `glab mr create`, `hub pull-request`, `tea pr create`, a push with merge-request options) is not refused, and the rule that it needs a reviewer PASS is not enforced there. The foreman rules say to start a watch with `pr_watch` after opening one. The watch reports a head the reviewer never passed, also when there is no review record at all (`head <sha> not reviewed (no review record)`, or `head <sha> not reviewed (last PASS on <sha>)`), once per head, only while `ceremony.reviewBeforePr` is on and only for a watched PR; a PR that is only in the followed list, or has no watch, is not reported (see [tools](tools.md#watch)). A watch armed by another session on a PR whose pass is recorded in that other session reports it too. A child's `gh pr create` and `glab mr create` are refused (`child-pr-create`); a child's `pr_create` is refused with `[pr_refused:child]`.

The PR gate checks at PR creation; a head pushed later is not refused by it. The watch reports it instead (`head <sha> not reviewed (last PASS on <sha>)`).

### Known limits of the git floors

The harness no longer reads git commands for their effect beyond the floors above. These are known limits, each with its consequence:

- **Commit messages and commit shape.** The harness does not check commit messages, trailers, `--amend`, `--no-verify` or `commit -a`, and runs no commit check command. Commit messages belong to the project's commit hooks, CI or the host's own rules; an agent can commit with `--no-verify`, so a project without such hooks has no message check. `safety.git.commit.*` is accepted and ignored; the doctor prints one INFO line when a key is set.
- **Pull requests from the shell.** A main-session PR from the shell needs no reviewer PASS (see the PR gate above). From a child, `hub pull-request`, `tea pr create` and `gh api .../pulls` are not floored: `hub` and `tea` run, `gh api` meets the permission step. The child's environment keeps the forge tools' stored login, so such a call can open a PR on the server, and no watch runs on it unless the foreman starts one.
- **Discarding edits in the own worktree.** `git checkout HEAD <file>`, `git checkout <file>`, `git switch -f`, `git reset --merge`, `git rm -f`, `git checkout-index -f` and `git read-tree -u` throw away uncommitted edits without a question, for a child and the foreman; so do `git reset --keep` and `git rm -r` in a child's own worktree: they have no floor and are not judge-first, so they run without the judge. A child's `git restore` and `git checkout -- <paths>` are judge-first (`danger-git`), with no exception for modified test files.
- **Shared repository state, child.** `git stash drop|clear|pop|apply`, `git branch -d|-D`, `git worktree remove|prune`, `git reflog expire`, `git gc --prune`, `git reset --hard`, `git clean` and `git rebase` go to the judge instead of a refusal (a clear runs them, a refusal goes to the agent), and another session's stash, an unmerged local branch or another worktree's uncommitted files can be lost. For a subagent the forms that move, overwrite or delete a branch, ref, tag or worktree entry shared with the main checkout are judge-first too (`danger-git`; the floors come first): `git update-ref` (every form), `git prune`, `git reflog delete`, `git tag -d|--delete`, `git branch -f|--force|-m|-M|--move|-C` (the letter anywhere in a short cluster), `git switch -C|--force-create`, `git checkout -B`, `git worktree add -B` and `git worktree move`. Pushed work is on the server; unpushed commits of a deleted branch can be lost. The main session's own forms of these are not on the list: the foreman moves its checkout with `git switch -C` itself. Not a complete list of what still runs with no floor and outside the judge-first list (they run without the judge): `git fetch <remote> +a:b` and `a:b` refspecs, `git branch -c|--copy`, `git branch --set-upstream-to`, `git tag -f`, `git symbolic-ref`, `git worktree add` without `-B`, `git worktree lock|unlock|repair`. A child shares the repository's refs with the main checkout, so it can move or overwrite a local branch, a protected one included. Every plain `git push` by a child is floored; the indirect forms (an alias, whether `!` or a plain `alias.p=push`, `git submodule foreach`) are not read, and a subagent keeps its git credentials (since #262), see "Subagent credentials" below; the server's branch protection is the backstop (see "Protect the default branch on the server").
- **Git config keys outside the floor list.** A child can write them, `--global` included (`user.email`, aliases, `core.pager`, `core.editor`, `gpg.program`). A program set there runs later inside the foreman's and the user's own git commands with their credentials, and an alias whose value starts with `!` runs any shell command that no floor reads. The config drift check does not watch the global config.
- **Git config set through the environment.** `GIT_CONFIG_GLOBAL`, `GIT_CONFIG_SYSTEM` and similar variables can point git at a config file the child wrote. The floor catches the `GIT_CONFIG_*` words it reads on a line, not every way of setting them (an exported value from an earlier call, a script, `env` through a wrapper). This gap is documented, not fixed.
- **Redirection and unreadable lines.** `GIT_WORK_TREE=<dir> git checkout .`, `GIT_DIR=...`, `-c core.worktree=...`, PowerShell and cmd lines that are not a delete, and computed program names are no longer labelled: the floors stop reading their text (see the text-floor change below) and they run, unless the parser reads a floor or judge-first form in them. A plain assignment or `env` before git is not one of these: `env X=1 git -C <outside> ...` and `X=1 git push` keep the git checks. A literal `bash -c 'git push --force ...'` is still parsed and floored, and a push word in a line the parser cannot read stays a deny for a child. Pieces reassembled into a command (`push --force` spelled in pieces in PowerShell, cmd or interpreter code) are judged where the line is unreadable.
- **Child writes through a script on stdin.** The child write floors (`child-write-outside`, `child-write-foreman-checkout`) read only what the parser can read. A script fed to a shell or interpreter on stdin (`sh <<EOF`, `python3 - <<EOF`), piped into a shell (`cat script.sh | bash`) or given as inline code (`python3 -c`, `node -e`) is not read, so a file it writes outside the child's worktree meets no floor. An interpreter or a shell fed on stdin, or given inline code, is judge-first (`danger-inline-code`: a clear runs it, a refusal goes to the agent). The floors do not read the body as text either (see the text-floor change below). A heredoc fed to a plain command (`cat > ../elsewhere/out.txt <<EOF`) is read and floored.
- **Program-running git options.** For the main session and subagents these are judge-first (`danger-git`; the floors come first): `--upload-pack` on `git fetch`, `git pull` and `git clone` (and clone's `-u`), `--receive-pack` and `--exec` on `git push`, in every spelling git accepts, shortened ones included, and the verbs `git send-pack`, `git http-push` and `git credential fill`. A child's push still meets the push floor first, and so does a push to a protected branch. Not a complete list of what the gate does not read: `git submodule foreach '...'`, `git bisect run`, `git difftool -x`, `git ls-remote --upload-pack`, a one-off `-c alias.*`, `git clone --template=<dir>` (its hooks run during the clone) and the submodule URL rules. A `git push` inside `submodule foreach`, or a delete outside the worktree inside a runner or a `!` alias, meets no floor. A subagent's push there meets no check: it keeps its git credentials (since #262), see "Subagent credentials" below, and the server's branch protection is the backstop; the same holds for the foreman's default branch.
- **Programs named in git config.** `git ls-remote` and `git fetch` can run a program named in the git config of a repository the child can write (`core.sshCommand`, `remote.<name>.uploadpack`, `credential.helper`, `core.askPass`); the gate reads the command line and the environment words of a `git ls-remote`, not the config files.
- **Subagent credentials.** A subagent keeps the git credentials of its user (the agent socket, token variables, the credential helper and ssh): the harness no longer strips them, so a builder from a single launch can push its own branch. It only sets `GIT_TERMINAL_PROMPT=0` and `GCM_INTERACTIVE=never`, so a child never waits for a login prompt. Who may push is decided by the gate: the child push floor refuses every child that is not a builder from a single launch (a reviewer, an explorer, an unbound child, a builder from a `tasks` or `chain` launch), and the force and protected-branch floors hold for every child. That floor reads command lines only; code a child runs (an allowed test command executing agent-written code) can push with the user's credentials, so the boundary is branch protection on the server, administrators included. A child removes its launch role (the `PI_SUBAGENT_EXTENSION_BINDINGS` variable) from its own environment after reading it, so a pi it starts has no role: no builder flag, no push, and every round worktree of that session read-only. A nested pi started with `PI_SUBAGENT_CHILD` unset loads as a foreman; while a nested child launch loads in the same runner process, the variable briefly holds that launch's binding. A child that writes that variable itself, or runs any program it wrote, is not stopped in-process. `safety.children.mayPush` is accepted and has no effect. A round session is a foreman of its own and was never stripped.
- **Plumbing verbs behind `git -C <main>`.** `checkout-index -f -a`, `read-tree -u --reset` and `reflog delete` are not in the gate's write list, so aimed at the foreman's checkout they run for a child too.
- **Lines the parser skips.** Commands inside `(( ))`, `$(( ))` and arithmetic `for` headers are not read (the operands of `[[ ]]` and the word lists of `select` are walked, see [permissions](permissions.md#the-judge-first-list)); the push floors still fire through the text floors. Arithmetic or a subscript on a value not shown to be a number (a name the environment sets, `$(...)`, `$1`, text read from input) sends the line to the judge as `danger-unknown-program`, and the harness folder variables lose their meaning from that unit on; arithmetic on numbers set on the line (`n=0; n=$((n+1))`, `for ((i=0;i<3;i++))`) runs. A sum of 50,000 terms in `$(( ))` or `(( ))` is read like a short one, so the floors read the commands around it. If a line ever does overflow the stack, the parser catches it and the line is unread and judge-first (`danger-delete-unknown-target`) with the text floors still run on the raw line.
- **Windows.** PowerShell and cmd lines are not parsed for git commands: they run, with the text floors on push and remote words. A PowerShell or cmd delete of the home directory, the drive root or a system directory is refused by the floor (`floor-rm-system`); a recursive delete of a variable is refused by `floor-delete-unknown-target`; other recursive deletes of an unreadable target go to the judge as `danger-delete-unknown-target`.

## Protect the default branch on the server

The floors read plain commands only, so the server is the backstop for a push to the default branch that they do not see (written oddly, or through `push.default` or upstream config) and for the indirect forms described above. The harness cannot set it. Recommended settings, with the GitHub and GitLab names: no direct pushes (changes go through pull requests or merge requests), force pushes off, deletion off, required status checks, and the rules applied to administrators (on GitHub, include administrators in the branch rule). Agents push with the user's own credentials, so a rule that exempts administrators exempts the agents when the user is one: include administrators in the branch rule when your credentials are admin, so that a push with your credentials cannot bypass it. The limit: a subagent keeps the forge tools' stored login (see "Pull requests from the shell" in the known limits above), and with admin rights that login can change the branch rule itself through the forge's API. Such a call runs (a forge write has no judge call) and is not read inside a script. The cost: the user cannot bypass the rules in an emergency without switching the setting off first.

`node scripts/repo_automerge.mjs <owner/repo> --checks <names>` prints three report lines in its dry run about the default branch's protection: force pushes, deletion and whether administrators are included, each `OK`, or `WARN` when force pushes or deletion are allowed or administrators can bypass the rules. The lines appear only with `--checks`, because the script reads the protection only then. The report changes nothing; `--apply` behaves as before (see [development](development.md#auto-merge)).

The key table below lists `safety.git.protectedBranches`; the floors always protect `main`, `master` and the remote's default branch.

Children are not stopped from committing; a child's commits stay on its worktree's branch. A builder from a single launch pushes its own branch like the main session (force and protected-branch pushes stay refused); for every other child, including a builder from a `tasks` or `chain` launch, the foreman pushes.

The read PR tools take `repo` and `host`. `host` is an allow-rule: it must equal the current repository's host, or the host of a remote of the checkout; any other host is refused with `[pr_refused:pr_host_refused]` before the op runs, in the foreman and in children alike. `repo` is accepted for any `owner/name` on an accepted host. `pr_create`, `pr_watch`, `pr_unwatch` and `pr_follow` act, so they are foreman-only: `CHILD_DENIED_TOOLS` names them, and a child that calls one is refused with `[pr_refused:child]`. The host ops (`pr_find`, `pr_repo`, and `pr_batch`, which the watch polls through, and the harness-only writes `pr_draft`, `pr_label` and `pr_body`, which edit the draft state, the ready label and the `## Reviews` block of a PR body the session opened) are not model tools; `pr_body` can change only the text between the review markers of a body, GitHub only. See [tools](tools.md#pr-tools).

Git config drift (a changed `.git/config`, hooks, includes) asks before the foreman's next git run; a relative `core.hooksPath` names a different directory in every checkout, so its hooks-directory id is derived from the configured value (one id for the primary checkout and its worktrees) and the hook files are compared per worktree top against that checkout's own last picture; a checkout seen for the first time records its hooks as the baseline, while a changed `core.hooksPath` or a hook planted in a checkout seen before is still named; added or removed `branch.<name>.remote` and `branch.<name>.merge` keys (from `worktree add -b`, `push -u`, `checkout -b`) are routine and ignored, a changed value is still reported. Changes in a submodule's git-dir config (`.git/modules/<name>/config`) that touch only the keys git writes there itself (`core.worktree`, `core.bare`, `core.repositoryformatversion`, `core.filemode`, `core.logallrefupdates`, `core.ignorecase`, `core.precomposeunicode`, `remote.<r>.url`, `remote.<r>.fetch`, plus the routine branch keys) are grouped in one line, `submodule configs: N changed (…; +M more)`; a change with any other exec-capable key (`filter.*`, `core.hooksPath`, `core.fsmonitor`, `include.path`) keeps its own line naming the file and keys; an unknown non-exec key is silent there too.

The config part of the drift ask fires only for keys that can run a program or redirect git, matched by key shape (`gitdrift.ts`, `EXEC_SECTIONS`/`EXEC_VARS`): `core.fsmonitor`, `core.hooksPath`, `core.sshCommand`, `core.pager`/`editor`/`askPass`, `url.<x>.insteadOf`, `filter.*`, `diff.<x>.textconv`/`command`, `merge.<x>.driver`, `remote.<r>.url`/`pushurl`/`uploadpack`/`receivepack`/`proxy`, `alias.*`, `credential.*`, `gpg.*program`, `include.path`/`includeIf.*`, `protocol.*`, `hook.*` (config hooks), `gc.recentObjectsHook`, `core.bare`, `extensions.*`, `remote.*`, `http.*`, `rebase.*` (instructionFormat can inject exec todo lines) and `push.*` (where a bare push lands) as sections, `lfs.*`, `bundle.*` and the like (the class was read off `git help config`; unsure keys are in). The reader follows git's own rules (a comment runs to the end of its line and a trailing backslash there continues nothing; inside a value `\\` and `\"` are escapes and only an unescaped backslash at the line end continues it); a line it cannot place makes the file ask as `(unparsed lines)`. Any other added, changed or removed key (`branch.<b>.vscode-merge-base`, `branch.<b>.description`, `user.*`, an unknown key) updates the baseline without a dialog or notice; hooks, `info/attributes` and worktree links keep asking.

## The tool gate

Every tool call is decided by pi-foreman's own gate (`extensions/core-adapter/gate.ts`), the first `tool_call` handler: parse the shell line, floors (always on, no config switch), self-modification rules, built-in allows (a plain `git push [-u] origin <branch>` is one only for the branch checked out in the worktree it runs in, by `cd` or `git -C`, and only when that worktree is the session's own checkout or one the session created; force, `:` refspecs, `--delete`, `--all`, `--mirror`, `--tags`, protected branches and pushes from other worktrees are not), then the [judge-first list](permissions.md#the-judge-first-list) (destructive git, git config and remotes, typing into another pane, whole-filesystem scans, deletes and writes with an unreadable target, remote commands, `pkill`/`killall`, a child's unresolved write). A call on the list goes to a cheap judge: a clear runs it, and anything the judge cannot vouch for (refuse, unsure, timeout, invalid, provider error, no model) is refused with the judge's reason and nobody is asked; only an `owner` answer naming one of six danger classes asks you (a child asks its parent). Every other call runs (default allow). The rule is stated once in [Who decides](permissions.md#who-decides). The whole pipeline, the file locations, the session kinds, the child-ask flow, the config keys and the migration are in [permissions](permissions.md). The policy is `<agentDir>/pi-foreman/permissions.json`, plus a project `.workflow/permissions.json` (widening keys only when untracked and git-ignored) and a tracked `.pi/permissions.json` that can only tighten. The user file can also name `workFolders`: reads there are allowed, and an `auto` folder runs writes that no other root covers, except in `.git`, `.pi`, the agent dir and the install dirs.

The foreman session's own single launch of a role (`explorer`, `builder`, `reviewer`) is a named default allow (`default-role-launch`), so the launch needs no judge. Floors run before it, and the adapter's role, ceremony and spawn gates run after it and still refuse. Management actions that write, workflow scripts, unknown agents, `tasks`/`chain` forms and a child's own launches are not covered. Without a classifier model, `foreman doctor`, `/foreman setup` and the first judge-first call of a session warn and name the key to set (`providers.<p>.roles.review.model`); every judge-first call is then refused with the no-model reason.

The write protection (`protect`: `.git`, agent and harness configuration) checks the path arguments of a shell
command, reads included: operands, option values and redirect targets. It skips the pattern and script operands of
read commands (the grep/egrep/fgrep/rg pattern and `-e` values, a sed script without `w`/`r`/`e`/`a`/`i`/`c`
commands, an awk program without redirection, pipe, `getline` or `system`, find's `-name`/`-iname`/`-path`/`-regex`
values when there is no `-exec`/`-delete`, echo/printf text), but only when every command of the line is a read or
filter command (grep, rg, sed, awk, find, echo, printf, cat, head, tail, wc, sort, uniq, cut, tr, ls, cd, ...) and
there is no `$(...)`, backtick or process substitution: `echo .git/HEAD | xargs touch` is still refused. A `*` skips
dot entries as in bash (unless the command mentions `dotglob` or `GLOBIGNORE`) and `\` is no path separator outside
Windows. The secret path denies still check every word; the only read they let through below `~/.ssh` is a valid SSH public key file directly in it (see [permissions](permissions.md)), never a write. A Pi session file (`.jsonl`) given as an argument to a program that is no known writer goes to the judge instead of being denied; redirects and known writers stay denied.

Protected files guard against mistakes by children, not against a hostile child: a child may run its own scratch
scripts, so the rule is not a sandbox. A protected file named by a read-only unit passes only for plain readers (cat,
grep, and a strict allowlist of read-only git subcommands) with no env prefix, wrapper (`env`, `command`, `nice`), loop
(`for`, `select`) or assignment anywhere in the line; any write form on the file stays denied.

The write protection is not what keeps a reviewer out of its worktree or asks you about the harness's own folders: those are two steps of the gate (`child-readonly-write` and `install-root-write`, below), which hold on every call.

A line of any program other than the plain readers (`cat`, `ls`, `grep`, `head`, `tail`, `wc`, `jq`) that names the harness folder `<agent dir>/pi-foreman` itself, a path below it outside the session's own handoff, scratch and wait folders, or another session's handoff dir is no longer labelled (`danger-harness-folder` is gone) and runs with no judge call; the policy, selfmod and state floors and the install-root ask still cover writes to the folder. A child's read of `pi-foreman/state` is refused by the self-modification rule `selfmod-state-read`.

**Read-only roles.** A reviewer or explorer in a round never writes the worktree it inspects. A line whose program the parse cannot state (`E=sh; $E -c ...`, `env --ign ...`, `env -S ...`, `builtin exec -c ...`) goes to the judge for these roles too (`danger-unknown-program`), and a write through `$FOREMAN_SCRATCH` or `$FOREMAN_OUT` after the line may have rebound it is refused as `child-readonly-write`. The gate refuses, as `child-readonly-write`, the writes it can name: the write and edit tools and the `foreman_move` / `foreman_copy` destinations in that worktree, the write targets of a shell line (redirects, `sed -i`, `cp`, `mv`, `rm`, `touch`, `mkdir`, `tee`, `dd of=`, `tar -x -C`, `unzip -d`, `patch -d`, also inside `bash -c` and behind `cd <dir> &&`), and every git subcommand in the gate's write set (`commit`, `add`, `reset`, `checkout`, `stash`, `tag`, `config` in a write form, a `fetch` with a refspec). No judge verdict lifts it. A reviewer's `write` tool is limited by one more child rule, `child-reviewer-write`, in every launch (in a round or not): it writes only the targets a child may write outside the worktree, its scratch dir (`$FOREMAN_SCRATCH`), its output dir (`$FOREMAN_OUT`) and its own handoff files, compared by real path (a link in scratch that points into the worktree does not count); the decision reads the structured `path` field only, and a reviewer's shell lines are judged as before. The role text tells a reviewer to put probe data that holds shell lines there with the write tool, never in a heredoc body (a heredoc reaches the gate only when bash closes it). Still allowed: reads, test runs and their build output (`npm test`, `npm run test:node`, `make test`, `node --test`), `git status|log|diff`, a plain `git fetch origin`, the scratch folder and the child's own handoff files. A git output option, or a default output into the current folder, that lands in the worktree is refused too (`archive -o`, `format-patch` without `--stdout`, `bundle create`, `checkout-index`; a target word the gate cannot resolve counts as the current folder); the same forms aimed at the scratch folder are not. A git `--output=<file>` or `--output <file>` (`log`, `diff`) is refused for a reviewer or explorer when the file lands in the worktree, and with the current folder in the worktree wherever the file lands (a known over-refusal; from a scratch clone a file in the scratch folder is free, and so is a shell redirect `git log > <scratch>/x` from either folder). In these forms a read-only role's git output gets past the fence: a work tree set by `--work-tree` or `GIT_WORK_TREE` while the current folder is the scratch dir (`checkout-index`), an abbreviated long option (`--out=`), bundled short options (`-vo`), and `-o` after `--` for `format-patch`. **This is a known limit, not a sandbox.** It stops the writes the gate can name and the git write subcommands. A judge step that used to look at a reviewer's or explorer's lines the gate cannot see into (the label `danger-readonly-run` and its role question) was removed: it asked about plain reads and made reviewers stall, and no other check takes its place until the planned state check after each command. Until then these are known gaps. Those other labels (`danger-opaque`, `danger-git-secret`, `danger-forge`, `danger-deploy`, `danger-process`) are gone: such a line of a reviewer or explorer runs like a builder's, with no judge call (owner decision, widened by the judge-first change); `danger-install` and `danger-net-write` are judge-first labels again for every role. It does not stop: git subcommands outside the write set that change the repository (`symbolic-ref`, `replace`, `sparse-checkout`, `maintenance`, `commit-tree`); writes by known programs that the write-target code does not name (`chmod`, `xargs` with names on stdin); build tool and package manager runs, which are not counted (`make`, `npm run <script>`); a `powershell` line (its words are checked as in the next paragraph, but a word in the worktree is not refused); and a write hidden in an unknown program, in a script run from the scratch folder or in inline interpreter code. The worktree is compared by spelling too: a symlinked spelling of the round worktree (a temp folder reached through two spellings) is not recognised, and `pushd <dir>` is not tracked. Later rounds revisit this fence.

**Run-end state hint (reviewer and explorer).** Beside the fence, the foreman pictures the run's checkout (the gate's tree root) when a reviewer or explorer launch (single, tasks, chain, resume) starts and again when the run ends, and compares the two. It pictures HEAD and branch, the index with its flags (assume-unchanged, skip-worktree), the repository settings (common and per-worktree config with in-repo includes, `info/attributes`, the effective hooks folder; names only, URL userinfo masked, branch tracking keys only for the start and end branch), the content of every tracked file that differs from the index or HEAD, and the same for each initialized submodule (up to 50). It does not picture other refs, tags, the stash, untracked files, other worktrees or `.workflow/`. A push (the remote and `refs/remotes/*`) is outside the hint; the child push floor and the server's branch protection cover it. A difference is one notice to the foreman (`pi-foreman-readonly-state`) and a `readonly_state_diff` trace record; nothing is blocked or undone, and a launch of any other role gets no hint. If the settings, attributes or hooks differ at the end, no git runs (a planted filter could run on the parent's `git status`) and the notice says the files were not compared. A picture that cannot be read, or that takes over 20 seconds, says `not compared`, with its cause in brackets (`deadline`, `not a git tree`, `git failed, exit N` or `timeout`, `aborted`, `settings file unreadable`). It is a hint, not a boundary: a change that is made and undone, a change in untracked files, and a change by another run in the same checkout are not told apart.

*Scope and limits of the hint.* A reload (or an eviction) of the foreman session loses the start picture: the run end then gives no notice, only a `readonly_state_diff` trace with reason `no start entry`. A reloaded session cannot tell its own earlier run from another session's, so that trace may also appear for a reviewer or explorer run end this session did not launch. A resume of a run started before a restart is not checked. Workflow launches and launches that include a builder (or any role other than reviewer and explorer) are not checked. Cost: a few git calls per picture and two more per submodule; the end picture runs in the background, and the start picture waits up to 20 seconds per launch. Blind spots: files flagged assume-unchanged or skip-worktree at the start (their edits are not seen); settings outside the repository (a global filter plus an edited tracked `.gitattributes` still runs on a status call); untracked files; and a change that is undone before the run ends. Past 2000 changed paths or 256 MB of tracked content the picture falls back to `lstat` (size and time) instead of content. The git runs that the run-end review record already makes are not gated by this hint.

**Two floor narrowings.** The first holds for every session and role (main session, builder, reviewer, explorer); the second only for read-only children. First: `GIT_CONFIG_GLOBAL=/dev/null` (exactly, bare; a quoted spelling stays floored, which fails closed) no longer meets the `GIT_CONFIG_*` floor; every other `GIT_CONFIG_*` assignment still does. Second: a reviewer or explorer in a round may read the `.git/config` of a clone inside its own scratch dir (a literal path with no `..`, glob, variable or `~`, whose real path lies in the scratch dir); a live checkout's `.git/config` stays a secret path. Known limit of that read exemption: a link created in the same command line is not seen at gate time, because the floor resolves the deepest existing ancestor of the path.

**Tool path spelling.** The gate reads the path of `read`, `write`, `edit`, `ls`, `grep` and `find` the way the tool does: a leading `@` is dropped, `~` is the home folder, `file://` is a path. A tilde, at-sign or file-link path therefore gets the verdict of its plain spelling (`@/tmp/x` is judged as `/tmp/x`; a child's `~`-spelled write to its own `result.md` is allowed). A malformed `file://` link is denied. Allow rules match the normalised path; deny and ask rules match either spelling. Shell lines are read as before, and symlinked or `..` spellings of a handoff folder are not covered.

**Install folders.** A write the gate can name into the Pi install folder, the global npm root, a bundled package folder or the pi-foreman package folder always asks you (`install-root-write`): no judge verdict answers it; a headless session or an owner who is away is denied, and a child is refused as before. Reads of these folders stay allowed. The checkout the harness runs from counts as an install folder for sessions that work in another worktree, so `git -C <checkout> pull`, `cd <checkout> && make`, `cd <checkout> && npm test`, `git -C <checkout> fetch` and `npm --prefix <checkout> test` now ask; a session whose own worktree is that checkout is not asked for its own files. Paths are compared by spelling, so no symlinked spelling is followed: neither a symlink in the worktree that points into an install folder, nor a symlinked spelling of the round worktree or of a root (a temp folder reached through two spellings), and `pushd <root>` is not tracked (`cd` is). These are known limits. A change that names no folder (`npm install -g x`) runs. A `powershell` line is read word by word, with no cmdlet knowledge (quotes and backticks honoured, `~`, `$HOME`, `$env:USERPROFILE` and `%USERPROFILE%` at the start of a word expanded, both separators, `=` ends a word): every word is treated as a write target, so a word in these folders asks you and a child is refused, a secret path is refused, and a harness config path or the project's `.pi` is asked (refused for a child) exactly as a bash write to it is; a child's word inside a `.git` folder is refused as a bash write there is. A child's `powershell` word outside its worktree is refused only inside `.git`, an install or package folder, a secret path, the self-modification paths (the rules of step 3, "Self-modification rules", in [permissions](permissions.md#the-steps); files inside a session folder stay free) or a ruling file (`ruling.md`, `ruling-<n>.md`) or a `brief-<x>.md` in a dir where it is the child (the self-ruling refusal; a plain `brief.md` word is not refused); anything else outside runs, where bash refuses it. What bash may write stays free (`.pi/scratch`, `.pi/tasks`, a child's own handoff files). Because every word counts as a write, a read of an install or package folder asks you and is refused for a child, and a search pattern that looks like a protected path is treated as one. Known limits, not seen: words built from variables or string joins, here-strings, quoted nested scripts (`pwsh -c "..."`, `iex '...'`, `cmd /c "..."`, encoded commands), provider prefixes and `\\?\` paths, environment folders other than the home spellings, and a relative word after a directory change.

`codemode` is not on the gate's default list: each call its script makes (`tools.read`, `tools.bash`, ...) passes the gate on its own, as a direct call would (`tests/replay/test_replay_codemode.py`).

Who sees an ask:

- The owner pane gets one gate dialog (full command, cause, the judge's reason). A judge that cannot clear the call refuses it instead of opening a dialog ([Who decides](permissions.md#who-decides)); the dialog opens for a fixed ask, a protected-target ask or a judge `owner` answer with a class. The dialog has two answers, allow once and deny; nothing is remembered.
- A session opened by another session asks in its own pane.
- A child's ask goes to its parent's pane through an ask dir the parent adapter owns (`gate.childAsk`, `parent` by default, `deny` keeps a plain deny); the child's ask ends after 15 minutes without a ruling (the parent's dialog closes with it) or when the starting session is gone; dialogs in the main session keep waiting (`gate.askTimeoutMs` has no effect). A child can never write that dir.
- A headless session denies an ask at once, as does a subagent launched in a group or a chain. An owner who is away does not: the dialog waits for the owner and only a dismissal denies. A floor decision never counts as an ask: it is decided without a presence probe and keeps its own reason ([permissions](permissions.md#presence)).
- A child's text-only hit on a line the parser could not read (a push, a git config key, a remote, a policy file) is a deny with a rephrase hint, never a parent ask; for a push this holds only for a child that is not a builder (a builder's unparsed plain push is decided like main's) ([permissions](permissions.md#floors)).
- Every decision is a line in `<agentDir>/pi-foreman/state/gate/log.jsonl`; judge calls are logged to the usage log with role `classifier`.

Child traces: with the foreman's retro on, a bound child writes `trace-<launchId>.jsonl` and each record carries `role`
and `runId` (the launch id); see [retro](retro.md). `tasks` and `chain` launches are not covered.

## Owned paths

The gate's path rules allow the foreman's own artifacts outside the workspace without a prompt, computed at runtime from the session's roots: the handoff
dirs, the session's `subagent-artifacts`, the worktree root's round dir (`close.worktreeDir`, default `../<repo>.worktrees`; see below), the children's scratch root, reads of
`<agentDir>/pi-foreman` and the global npm root. A child's **writes** outside its worktree, its scratch dir and its own handoff files are refused by the gate (`child-write-outside`): sibling worktrees, other children's scratch dirs, other sessions' handoff dirs and `pi-foreman/claude-config`; so are the self-modification paths (`<agent dir>/settings.json` as `selfmod-agent-settings`, `pi-foreman/state` as `selfmod-state`, the worktree's `.pi/foreman.json` as `selfmod-project-pi`). In the round worktree a write-tool write of `.workflow/LEDGER-x.md` is allowed for a builder and refused for a reviewer or explorer (`child-readonly-write`). The `parent` and
`child` handoff files still ask. The list and the reasons are in [permissions](permissions.md#owned-paths).

**A child's reads are not fenced.** An earlier permission layer refused a child's read of other sessions' notes and worktrees, of other children's scratch dirs and of `pi-foreman/claude-config`. That refusal is gone, on purpose. At head a child can read other sessions' handoff notes, sibling worktrees, other children's scratch dirs, other sessions' `subagent-artifacts` folders, `<agent dir>/pi-foreman/claude-config`, `<agent dir>/settings.json` and `<agent dir>/foreman.json` with `cat`, `ls`, `grep -r` and the read and grep tools: no rule decides the call, so it goes on to the mode step. Its own worktree files (`.workflow/LEDGER-x.md`, `.pi/foreman.json`) are built-in reads. The one foreman folder a child cannot read is `<agent dir>/pi-foreman/state` (`selfmod-state-read`). Writes to all of these stay refused as above.

The gate does not read a script file a child runs: `node x.mjs`, `python3 x.py` and `bash x.sh` are judged by their words, whatever the file holds (a run of a file in the scratch dir is a `default-write-in` allow, for a reviewer or explorer too). The split-literal scan (see [permissions](permissions.md#split-literals)) survives in one place: a line whose text spells a guarded token from pieces is never given a built-in allow. The read question is gone.

A plain `git ls-remote origin` is a read (`default-git-read`) for the main session, a builder, a reviewer and an explorer, like `git fetch`: it writes nothing to the worktree. A remote written `<transport>::<address>` is not excluded: it is `default-git-read` too. These forms are no built-in read: `--upload-pack=<cmd>` and its short form `-u <cmd>` (also `-u<cmd>`; a reviewer or explorer is refused it as `child-readonly-write`; main and a builder get the judge: `danger-git`), git's global `--exec-path=<dir>` before it, and a line that sets a variable (`GIT_SSH_COMMAND=… git ls-remote`, `export HOME=… ; git ls-remote`), which runs. `--output <file>` (separate value) of any git subcommand names a written file, like `--output=<file>`; a reviewer or explorer is refused it when the file lands in the worktree or the current folder is in the worktree (see the read-only roles above).

A plain `git fetch` has a built-in allow row; `git fetch --upload-pack=<cmd>` (it runs code) is judge-first (`danger-git`) instead; `npm ci` and `npm install`
are allowed for the foreman only. A child's `npm ci` or `npm install` asks unless its launch sets `install: true` (builder); the ask text names the flag. The foreman's rows are unchanged.

The `live.json` file in each handoff dir (`handoffs/*/live.json`, written by the adapter at session start) is write-ask next to `parent` and `child`, so neither the session's model nor a child can forge it.

### Session files

Pi session `*.jsonl` files are denied for write, edit, `foreman_move`, `foreman_copy` and shell write words (redirects, `tee`, `sed -i`, the destination of `cp` and `mv`), for the foreman and for children. The adapter appends its state entries itself. Reads stay allowed. The session's `subagent-artifacts` dir stays writable.

A `$NAME` in a bash line resolves to a same-line assignment only inside a closed grammar: every statement (split on
`;`, `&&`, `||`, newline) is a sole `NAME=<plain absolute path>` or a simple command from `mkdir cp mv cat ls tee touch
tar node npm npx python3 git test echo true` with plain words (letters, digits, `/ . _ ~ = : @ % + , -`, `$NAME`,
`${NAME}`, `2>&1`, `>/dev/null`, `>`/`>>` with a plain word). A pipe, `&`, parentheses, braces, brackets, backtick, `#`,
`<`, `$(`, `${` beyond a bare name or any other statement form makes the line resolve nothing, and it asks as before. The
exact rules are in [permissions](permissions.md#variables-in-bash-lines), including the two extra cases a child with a scratch dir gets (one literal assignment, `$FOREMAN_SCRATCH` on a heredoc or pipe line).

## Child scratch

Each single-child launch gets a scratch dir under the session's worktree root (`<root>/.foreman/scratch/...`), or under the OS temp dir when the session has no usable root (`$FOREMAN_SCRATCH`, see
[ceremony](ceremony.md)). The foreman's default reads and shell writes do not reach `.foreman/scratch` through the owned worktree root. Writes and removes are allowed inside that dir only, never the dir itself or anything
outside it:

- Gate (`child-write-outside`): a child is refused, not asked, any write below `/tmp` or the resolved OS temp dir outside its scratch dir and its own workspace: a write or edit tool path, a shell redirect (`> /tmp/out.txt`), and the targets of `tee`, `touch`, `mkdir`, `mv`, `cp`, `install` and `ln`. The reason names the refused path, the worktree and the sanctioned targets. A read from `/tmp` is not refused.
- Gate (default `default-write-in`): `cp`, `mkdir`, `rm` and `cd` with every destination or operand inside a live scratch dir of the asking role, and path-tool writes inside such a dir, are allowed without the model. POSIX shell forms only. For any child (every child role, explorer included) only, a `mkdir` or `mkdir -p` of its scratch dir itself (`mkdir -p $FOREMAN_SCRATCH`) counts as inside; the main session's verdicts are unchanged; `rm`, `mv`, `touch`, a redirect or `cp` onto the scratch dir itself stay refused, and so does the dir above it.
- A recursive delete whose target the harness cannot read (a variable operand, a glob without a readable directory, a `cd` into a variable, `xargs rm`, `find -exec rm`, a PowerShell or cmd `Remove-Item -Recurse`) goes to the judge (`danger-delete-unknown-target`); a clear runs it, a refusal goes to the agent. Use the literal path to skip that. A literal PowerShell or cmd recursive delete outside the roots, `Remove-Item @list`, a delete fed by a recursive listing, `-EncodedCommand` and `iex` of a computed string, and `git clean` with a variable operand are judged the same way.
- The harness removes the dir at run end only after a realpath check that it is a real directory below the
  `<root>/.foreman/scratch` base (or the `<tmp>/pi-foreman-scratch` root, for lanes of older runs) and neither inside nor around the repository.

### Kept output folder

Each single-child launch also gets `<agent dir>/pi-foreman/child-out/<session>/<launch>` (`$FOREMAN_OUT`, mode 0700), named in the child's task and in the launch result. It is a second scratch-like write root: the same path rules, floors and `rm` allowance apply inside it, and nothing outside it is added. The harness does not remove it at run end, so a log the child writes there is readable by the foreman afterwards (`<agent dir>/pi-foreman` is a read root of every role). The guards read `$FOREMAN_OUT` (and `$FOREMAN_SCRATCH`) as the folder only when every mention of the name in the line, read from the parsed words with quotes and escapes removed, is a plain `$NAME` or `${NAME}` reference; this includes a reference inside a nested `sh -c '…'` string. Any other mention leaves the line unresolved and a builder's call goes to the judge (a read-only reviewer's is refused): an assignment, `export`, `env FOREMAN_OUT=...`, `${FOREMAN_OUT:-x}`, a quoted or escaped spelling of the name (`'FOREMAN_'OUT`, `$'FOREMAN_OU\x54'`), a nameref (`declare -n r=...`, `typeset -n`, `local -n`) naming it, or a rebind in a loop body. The same leaves it unresolved after an `IFS` assignment earlier on the line, in a login or interactive shell (`-l`, `--login`, `-i`, `exec -l`, `exec -a -name`) or behind `BASH_ENV=` or `ENV=`, and in a `-c` string nested in such a line; a line nested past the parser's depth limit (4 levels) is judged whole, also a harmless one. Under an env-clearing wrapper (`env -i`, `env -u NAME`, `exec -c`) in front of `sh -c`, the inner shell sees the name empty and it is not resolved. At the start of a foreman session the harness removes launch folders older than 7 days (by mtime, any session, links never followed) and the session folders left empty.

## Worktree children

A single `subagent` launch with `worktree: true` records the flag in the child's launch binding, and the child gets `FOREMAN_CHECKOUT=<the foreman's checkout>` in its environment. Its builder brief says it works only in its own worktree, reads the plan and ledger in the foreman's checkout, never cds into or edits that checkout and commits on its worktree's branch. Children write files (scratch included, at the absolute `$FOREMAN_SCRATCH` path) with the write and edit tools; a readable `cat`/`tee` heredoc or redirect write runs inside the child's own worktree and scratch dir and is floored outside them (see the shell-write guard above). A child's shell write into the foreman's checkout, its `.workflow/` included, is denied as `child-write-foreman-checkout` (a redirect, a write-class operand, a git write verb run from or aimed at the checkout, `git clone` into it); reads are never fenced (nor are the read-only forms of git write verbs: `git branch` list, `git stash list|show`, `git worktree list`, `git config` reads, `git tag` list forms, also under `-C <dir>` or after `cd <dir> &&`) and the child's own worktree and scratch dir are not part of the fence ([permissions](permissions.md#owned-paths)). Only single launches carry a binding: a `tasks` or `chain` launch gets the brief line but not the flag, so it has no `FOREMAN_CHECKOUT` and no checkout fence (its writes outside the worktree and scratch dir are still `child-write-outside`).

## Child shell time limit

A child's `bash` call (a subagent child, and a session that another session opened with `foreman_session_open` or `foreman session open`, local or remote: the one with a handoff dir, `PI_FOREMAN_HANDOFF_DIR`) with no `timeout` gets `ceremony.childBashTimeoutSeconds` (600 s); an explicit `timeout` above `ceremony.childBashTimeoutMaxSeconds` (1800 s) is capped to it, and that call's result then ends with `pi-foreman: timeout <requested> s was capped to <cap> s (child bash cap, docs/safety.md)` so the child sees the cut at the call. The default is clamped to the cap too. The effective ceiling is the lower of `childBashTimeoutMaxSeconds` and `ceremony.childTimeoutSeconds` (1800 s), because pi-subagents stops any child tool call past that per-call limit. The limit bounds a hung command, not a permission: the gate and guards decide the same way with or without it. A top session (no handoff dir) is not limited by these keys. The limit applies to the `bash` tool only, not to `powershell`; it relies on Pi stopping the shell at the timeout (on Windows Pi ends the process tree with `taskkill`). The foreman's own shell calls are not limited by these keys (trace `bash_timeout {action: applied|capped, requested}`).

## Child environment and extensions

Subagent children get a stripped environment: `childenv.ts` removes the intercom identity variables, so a child
cannot pose as its parent session (see [sessions](sessions.md)). Required child extensions
(`safety.requiredChildExtensions`, empty by default) load the listed extensions into every child; a project file may only add entries.

## Bridge isolation

With the Claude bridge, `CLAUDE_CONFIG_DIR` points at an empty folder so the host's Claude Code settings, hooks,
plugins and `CLAUDE.md` do not load into bridge turns (`bridge.isolateClaudeConfig`; a project file cannot set it).
Login steps are in [install](install.md). Rationale: `design/architecture.md`
[bridge isolation](../design/architecture.md#bridge-isolation).

### Bridge project-config trust

A project `.pi/claude-bridge.json` that sets an executable path, `AskClaude` or `strictMcpConfig: false` raises an error notice at session start and a
doctor FAIL. The owner can trust the file as it is with the slash command `/foreman trust bridge`: a confirm dialog shows the risky keys and the
file's sha256, and a yes writes the record `<agentDir>/pi-foreman/state/bridge-trust.json` (user layer). While the hash of the file matches, the notice
and the FAIL stay silent; any edit of the file is untrusted again. The dialog is the owner's alone (no model answer), there is no CLI
subcommand, and the file is a policy floor: a tool or shell write to it is refused.

## Pre-bash hooks

`safety.preBash.hooks` is an ordered list run before every `bash` tool call (user and overlay config only; a project or session value is ignored,
because a hook runs code). An entry ending `.mjs`, `.cjs` or `.js` is a module (absolute path, or relative to the agent dir) whose default export
(or `preBash`) takes `{command, cwd, tool, session, role}` and returns `{ block: true, reason }` to block. Any other entry is a command, split on
whitespace and run without a shell, with the same JSON on stdin; exit 2 blocks (stderr is the reason), exit 0 passes. A hook can only block, never
allow: the guards and the permission checks run after it. **Fail-open by default:** a hook error (a throw, any other exit code, a start failure, the
5 s timeout) is traced as `prebash_hook_error` and ignored. **Strict mode** (`safety.preBash.strict: true`): a hook error blocks the call. An explicit
block blocks in both modes.

Plan mode (a read-only explorer launch needs no ledger) is detected from the latest `plan-mode` custom entry (`{ enabled }`) on the session branch.

## Known limit: a reader chained with `find`

The reader skip for protected operands (see Owned paths) covers a command whose every unit is a minimal reader. A read-only line chained with `find` (`cat protected/file; find . -name x`) loses the skip for the protected file, because `find` is not in the reader set. The set is not widened; split the line or use the read tool.

Protected files (the write-ask paths `config/foreman.defaults.json` and `package.json`) are the foreman's to apply and commit. A child's `git add` or `git commit` naming one is denied with the text "The foreman stages and commits this file; report the needed change.", and every builder brief (not a rung-up handoff entry) ends its ledger block with one `Protected files (...)` line saying the same, so a builder reports the change instead of retrying.

## Known limit: writes the gate does not label

The gate names a write from the words of a line. Two forms it does not name, for the main session and a builder alike:

- An `awk` program whose body writes into `.git` (`awk 'BEGIN{print "x" > ".git/hooks/pre-commit"}'`) is not labelled as a write: the gate decides nothing.
- A program's own output option that names another checkout is not labelled: `tree -o <other checkout>/f` carries no label. `sort -o <other checkout>/f a` is refused for a builder (`child-write-outside`) but carries no label for the main session.

For a line that carries a judge-first label, the judge decides (a clear runs it, a refusal goes to the agent). An interpreter one-liner (`python3 -c "…"`, `node -e "…"`, `perl -e`, `ruby -e`), a script built at run time (`bash -c "$X"`, `eval "$X"`), an interpreter or a shell fed on stdin (`python3 - <<EOF`, `bash <<'EOF'`, `busybox sh <<'EOF'`, `echo cmd \| sh`), a script run by `zsh`, `fish`, `pwsh` or `cmd /c` and every remote command (`ssh`, `docker`/`podman exec`, `kubectl exec`) are judge-first (`danger-inline-code`, `danger-remote`). So is stopping processes by pattern: `pkill` and `killall` (`danger-kill-pattern`); `kill <pid>`, `kill $!`, `kill %1`, `taskkill` and `pgrep` run. A program word built from a variable or substitution (`$PY -c ...`, `$(which rm)`), an unread wrapper option (`env --ign ...`, `env -S ...`), a wrapper the walker does not unwrap (`ionice`, `chroot`, `unbuffer`, `parallel`) and `builtin exec ...` are judge-first too (`danger-unknown-program`). Known gaps that run: an unquoted variable that splits into words, `osascript -e` code, and a curl form whose file list is built from a variable. `python script.py` and `node file.js` carry no label and run. `git add .git/x` carries no label: it is the built-in `default-git-add` allow for main and a builder (a reviewer is refused it, `child-readonly-write`).

**Writes through a link into `.git`.** A `write` or `edit` whose path reaches `.git` through a link (a link to an existing folder, a dangling link, a link to a link, a link in the scratch folder) gets the verdict of the plain `.git` path: `child-write-outside` for a builder and a reviewer, no decision for the main session. Known limit: a chain of more than 8 links whose end does not exist yet is followed for 8 links and gets the verdict of the place reached (a builder's write to a 9-link chain ending in a new file in `.git` is allowed). A chain that ends at an existing file is followed to its end as long as the system's real-path lookup resolves it; a longer chain is treated like one whose end does not exist. The system refuses to open such a chain at all (too many links), which was checked on macOS only.

## Known limit: shell forms the walker does not read

The walker reads the forms listed under [forms the walker now reads](permissions.md#the-judge-first-list): the operands of `[[ ]]` and `select` lists, sourced streams, aliases, function bodies at the call, `xargs` programs from input, the look-behind for unmodelled programs, `toybox`, assignments before a command, a script run after a folder it cannot state, and an `eval` that changes folder. Each is judge-first or walked, never a new allow. These forms stay open; a line with one runs with no judge call unless another part of it is a floor or judge-first hit:

- a program named under a variable folder (`$V/bin/x` runs as the program it names; the #347 rule is kept, not reversed);
- `cd -` and `popd` that return to a folder the session inherited (`OLDPWD`, the directory stack) with no earlier non-literal folder change in the line; `cd */` (the glob's folder is unknown, so it is not flagged); `cd $D && make` and `cd $D && npm test` run build files from an unknown folder;
- a relative literal file that resolves to a stream (`cd /dev; . ./stdin`, a link to `/dev/stdin`), and a relative script word after the look-behind (`cd $D; caffeinate ./x.sh`);
- `GIT_DIR=`, `GIT_WORK_TREE=` and `CDPATH=` before a command (see the git floors above);
- `echo 'branch -D main' | xargs git`: arguments fed on stdin to a known program are not read by the git checks;
- options that start another program: `sort --compress-program`, `tar --to-command`;
- positional references inside an `eval` or `bash -c` text in a body;
- `coproc`, `trap`, `find -exec sh -c`, `npx sh -c` and `nameref`.

## Known limit: network reads (R31c)

The gate's web-read rule ([permissions](permissions.md#web-reads)) takes any host, by owner decision. Residuals:

- A GET to any host can carry data in its URL (path or query). The allow checks the command shape, not where the data goes.
- `curl -L` follows redirects and the resolver may point a name anywhere; the allow sees the first URL only.
- `~/.curlrc` (and the `wget` startup files and HSTS cache) still apply; the allow does not read them.
- Output goes only into the session or the role scratch dir; each child role has its own scratch dir, so a child can read a file another child of the same role left there.

## Known limit: MCP scope in children

The permission gate judges every `mcp__` call on its payload; the MCP scope (`roles.<id>.mcp`, see [roles](roles.md#rolesidmcp)) decides which tools exist in a child. Both apply. Residuals:

- Children read the trusted project's `.pi/mcp.json` the way Pi does. A shell write to `{cwd}/.pi/*` goes through the gate, but a project you trust can still name servers there; they load only when a role's ceiling lists them.
- Group launches (`tasks`, `chain`) that need MCP are refused until the pinned pi-subagents forwards per-entry bindings; launch those roles singly.
- With `safety.subagents.allowWorkflow` on, a workflow script could pass `extensionBindings` per child and forge a binding. A script (inline or file) whose text names `extensionBindings` or `pi-foreman/1` is therefore refused (`launch_refused`, reason `workflow_binding`); only bindings the adapter writes exist. The text scan is best-effort: a computed key (`"extension" + "Bindings"`) defeats it. A script path is read from the launch `cwd` (as pi-subagents resolves it); a script that cannot be read, and a named workflow resource, which the adapter cannot read at all, are refused whenever a role has an MCP ceiling (`roles.<role>.mcp`). `allowWorkflow` is off by default, which is the real protection.

## Known limit: the review verdict channel

A reviewer gives its verdict, item results and findings through the tool `review_verdict`, which writes a record into a folder the harness made for that launch (`<agent dir>/pi-foreman/state/review-records/<session>/<launch>/`). The floors protect the folder like `state/child-asks`: no tool call or shell line of a session writes it, and a child drops its own `pi-foreman/1` binding key from its process env after reading it, so a process the child starts (a test run, a nested pi) cannot write its record. The gates read the record only (see [review](review.md#the-verdict-tool)); no report text.

What this does not stop:

- A foreman can start a pi process by hand with a forged reviewer binding that names a real record folder; that process's own tool code writes a record. `scripts/foreman_review_bench.py` starts reviewers this way. No per-launch secret is kept.
- A foreman writes the reviewer's task and can resume a failed reviewer and press it toward a pass.

The gates hold against misreads, accidents and casual shortcuts, not against a foreman that cheats on purpose; the owner's look at the PR remains the last check.

## Known limit: stale "needs attention" notices

pi-subagents delivers `subagent_control_notice` custom messages with `pi.sendMessage` (`triggerTurn` for async runs), and a queued message cannot be withdrawn. Since pi-subagents 0.89 the wake is a custom run that pi-subagents sends itself: there is no `input` event for it, so the R26 item 2 check at `input` (every unseen notice for a run whose end event already arrived: `handled`, no turn, trace `notify_deduped {reason: "run_ended", runId}`) no longer applies to a wake. A stale-only wake therefore starts a turn; the notice text stays hidden from the model and the display (`context`, `message_end`), and the turn cause is `child`. The wake cannot be aborted: pi-subagents treats an aborted wake turn as an owner abort and holds every later wake until the owner types. The `input` path covers only a notice caught up at an owner prompt; a notice held back (appended without a turn) is caught up at the next custom `message_end` as well. The open-tool signal (`reason: "tool_open_threshold"`) is latched per run and tool call (`AttentionNotices.openOnce`, key `runId:toolCallId`): a repeat of the same signal, delivered again or on a second channel as a `subagent_control_notice`, is hidden at `message_end` and in `context` (trace `notify_deduped {reason: "tool_open_repeat"}`) but, like a stale-only wake, still starts a turn under pi-subagents 0.89, because the `input` check no longer applies to a wake (it matches only the 0.78 wake text); it starts no turn only when caught up at an owner prompt; another tool call of the run fires once more, and a notice without `toolCallId` passes. The copy that pi-intercom relays for the async record's `intercom` channel is an `intercom_message` with the notice only as text (no run or tool call id), so it cannot be matched without parsing text; `foreman setup` removes that duplicate: it writes `control.notifyChannels: ["event"]` into `<agent dir>/extensions/subagent/config.json` (the `intercom` channel is off, so only the native notice arrives; `/foreman doctor` warns when the key differs). The trade-off is a foreground run, which gets only the intercom copy and so no attention notice; every child launch is detached (`detach.ts`) and children have no `subagent` tool, so none arises. A single launch that passes its own `control` can bring the second copy back. `notices.ts` (`staleNoticeRunIds`, `dropEndedRunNotices`, `isRepeatOpenNotice`) holds the rules. Pi's hooks cannot cancel a queued custom message itself; fixing that needs a Pi hook to withdraw a queued custom message (for example a `message_start` handler that can cancel it), or a run-end check in pi-subagents' `control-notices.js` before it calls `sendMessage`.

## Known limit: `/sync`

`/sync` pulls, commits (explicit paths only) and pushes the repositories listed in `sync.repos` of your user config (see [sessions](sessions.md)). It never forces a push, runs no repository hooks and refuses a repo whose local config sets any key outside a short allowlist of harmless keys (so filters, hooks, ssh/credential helpers, url rewrites, `http.*`, submodules and similar are refused), or that holds a secret or a linked file. Remote urls must be https, ssh, git or scp-like (local paths, `file://` and helper transports are refused); submodule gitlinks are ignored and refused; the config is re-checked before commit and push. **Known limit:** a child agent or other code running as your user can plant repository state (config, remotes, commits) between syncs; /sync refuses every planted state it knows (git's local file transport is off, remote names must be plain names), but it is not a boundary against such code. List only repositories you trust children not to touch.

## Worktree root and nested checkouts

- **Owned root.** Only a session in the main checkout owns the whole worktree root (`close.worktreeDir`, spelled and real path); a round session keeps its own tree and never owns sibling rounds. For a custom root every child gets a block glob (`<repo>` becomes `*`) next to the default `*.worktrees/*` one, so other repos' rounds under a shared root stay closed; a child's own round stays open. The setting is user or overlay config only, and a value that would cover the main checkout, home, the agent dir, the install dirs, the temp root or `/` is refused (`root_blocks_protected`) and falls back to the default. A root already holding another repo's worktrees is refused (`root_collision`, a snapshot). See [close](close.md#the-worktree-root).
- **Nested-checkout rule.** A git checkout inside a workspace or round tree counts as part of it only when its `.git` file points into that repo's `modules/` admin area and the admin dir points back at that exact `.git` file (linked submodule worktree), or the submodule's `core.worktree` names the checkout (plain submodule). A forged `.git` file aimed at another round's admin dir fails this check; forging it would need a write under `.git/`, which children cannot make. The lift stops at the session's workspace or round. A round worktree never lifts into the main checkout or another round.
- **Inside such a tree** the gate's write roots treat the nested checkout as inside the child's own tree, so a child's writes and git commands there are not `child-write-outside`; every other foreign repository stays fenced. `git submodule` verbs are not read specially: the path rules and the URL rule for `update`, `sync`, `init` and `foreach`, and the refusal of `--recursive`, are gone, and a `.gitmodules` URL is not compared with the configured one (a known limit: a child's `git submodule sync` or `init` writes URLs into shared git config). Cleanup never deletes nested checkouts pi-foreman did not create.

## Known limit: stream suffix on a Windows folder

On Windows every self-modification rule folds trailing dots and spaces of a path component, but a stream suffix on a folder component (`.claude::$INDEX_ALLOCATION\settings.json`) is not folded, so such a write is not caught.

## Known limit: worktrees on Windows

On Windows pi-subagents cannot spawn a script hook without a shell, so the `foreman-worktree-setup` hook does not run there. Managed worktrees keep a symlinked `node_modules`, and builders must not run `npm ci` in them (it would rewrite the main checkout's `node_modules`). `/foreman doctor` WARNs on a symlinked `node_modules` in a live worktree.

## Known limit: background runs on Windows

On Windows the add-on's `bg_run` runs under Git Bash, so the guards' bash reading matches what runs: on Windows pi-foreman sets `PI_BG_SHELL=bash` and `PI_BG_SHELL_PATH=<Git Bash>` in its extension factory (before the add-on loads) unless either is already set, and only `cmd.exe` is used when no bash resolves; in those cases the gate rules and the shell-write guard classify the command as bash. cmd syntax the bash scanner does not model (`&` as a separator, `^` escapes, `%VAR%` expansion, cmd built-ins such as `del`, `rd` or `copy`) can therefore pass with a verdict that is wrong for what actually runs. In those cases keep background commands to plain program calls (`node …`, `npm test`).

## Known limit: remote machine trust boundary

A remote child (see [sessions](sessions.md#remote-child-sessions)) runs on a machine that hc reaches; the parent talks to it only through `hc exec` and `hc run`, and `sessions.machines` is the allowlist (the names also have to appear in `hc machine ls`). hc holds the connection and the credentials; pi-foreman stores none and the remote never connects back on its own. The one credential the hc intercom transport (`setup --intercom-hc`) adds is `hc machine add <parentName>` on the remote machine: it lets a remote child send intercom messages to the parent, and whoever runs as that user on the remote can then reach the parent machine through hc as well. Add it only for a remote you trust, and leave it out if the child needs no intercom. The handoff dir on the remote machine is the trust boundary: any process running as that user there can write or change its files (a `close.json`, a notice file), and the parent cannot tell that from the child. Files are fetched as data and act on nothing. Treat remote files like any peer message, and list only machines whose users you trust.

## Known limit: registry without a lock

`sessions.json` is read, changed and written back without a lock (`foreman session brief`, the open and close verbs all do this, the write itself is atomic). Two of them running at once can lose one update. The loss is accepted for now.

## Known limit: model-written HTML pages

Plan pages and `html` notes are shown as the model wrote them: no content security policy, no script or network stripping. The approval of an HTML plan covers its source bytes (the version is the sha256 of the whole file). What a script, a remote resource or CSS renders when the owner opens the page is outside it. This is accepted: the page opens like the note tool says, with scripts and network access.

CSS can hide text from the generated markdown copy that reviewers read (`display:none`, `visibility:hidden`, `font-size:0`, `opacity:0`, the `hidden` attribute) or add text it does not hold (CSS `content:`). The converter counts these and the plan-review facts list them, so the reviewer can judge whether the page misleads; the harness refuses nothing for them. Rulings never go into the page, so an approved page cannot change by a ruling.

## Owner scripts

An approved owner script runs with the owner's rights, and no guard reads it: no floor, no judge and no sandbox applies inside the run. The owner's answer in the dialog is the only control. The owner chose this (2026-11-10) for changes the guards close to every agent, such as user config, global installs and protected files.

**Mechanics.** The foreman writes a script into the scratch dir and calls `foreman_script` with `action: "propose"`, the path, a description (at most 600 characters), the risk and the undo (at most 300 each). The script must be a regular file below the scratch dir (no symlink, one hard link, at most 64 KiB, UTF-8). The dialog uses the owner-dialog shape (the plain question first, the path as plain text and never a link). It shows the three texts, each made one line with control and escape characters removed and never cut (a text over its limit refuses the proposal), then the path, the line count and the short sha256 that the harness adds. It does not show the script body, and no reviewer or classifier reads it. The dialog lists approve first, then revise (with a note), then reject. That order is the owner's decision of 2026-11-11: the owner answers these dialogs on a phone, one tap, no second step. In the terminal the first row is preselected, so a stray Enter approves; the plan checkpoint keeps approve last. One notice before the choices holds the summary and, as its last line, whether the tool can undo the script (see Undo). It is one notice because the terminal replaces an info notice by the next one sent right after it, which would hide the description, risk and undo. Every foreman session may propose, also one opened by another session; a subagent child never (the tool is not registered there and refuses with `script_child`). No ruling file, no parent verdict and no timeout approves: without a UI, in print or json mode, or when the dialog is dismissed, the proposal stays pending and nothing runs. The dialog counts as the `script` family of `foreman_dialogs`.

The approval is tied to the script's bytes and lives in the session's memory only; nothing is written to the state directory, so a reload or restart drops it. If the file changes while the dialog is open, the proposal stays pending. One proposal per session: a new `propose` drops the earlier one and its approval, and `dry`, `run`, `status` and `undo` take no path.

**The run.** Only the harness starts the script. For every run it writes the approved bytes to a new private file (mode 0700, in a new temp dir), runs that file with POSIX `sh` (`/bin/sh`; on Windows Git Bash, never `cmd.exe`, else `no_posix_shell`) from the workspace root, and removes the file afterwards. The path in the scratch dir is never executed, so the script must not rely on `$0` or sibling files, and its shebang is ignored. The dry run gets `--dry-run` as its only argument and `DRY_RUN=1`; the real run gets neither. The foreman cannot add arguments or environment. The environment is the harness's own without the intercom identity; credentials stay. The run blocks the tool call; the limit is 600 s (`timeoutSeconds` up to 3600). On the limit, on an abort of a dry run or an undo and after a normal exit the process group is killed.

**Abort of a real run (background).** An abort of the tool call of a real `run` (Escape, a compaction) after the script started does not kill the script: it runs on in the background (the call returns "Script still running in the background (pid …); its result arrives as a message"), still under its time limit. While it lives, `run`, `dry`, `undo` and `propose` are refused (`script_running`: "an owner script is still running (pid, since)"); `status` shows it as running, and the foreman keeps working meanwhile. When it ends, the attempt is recorded with its real outcome (the exit code, or `timeout` when the limit killed it), the log is written as for any run, the undo window starts at the real end, and one `pi-foreman-script` message carries the result as data. The message starts a new foreman turn when the session is idle (after Escape it is), else it is delivered as a follow-up. The action `stop` kills the background run and records it as `stopped`; as a started real run it counts as an attempt and makes undo available. Closing the session, `/reload` and resume kill a background run and record it as `aborted`. A run aborted before the script started, and every aborted dry run, undo or propose dry run, still kills or spawns nothing as before. Output goes to `<scratch dir>/script-<name>-<hash8>-<dry|run|undo>-<n>.log` (the name keeps its `.sh`), where `n` counts per kind (dry-1, dry-2, run-1, undo-1) and a log is never overwritten. The tool result carries the exit code, the log path and the last lines.

**Undo.** A script that supports undo carries the whole line `# foreman-undo: supported`. The harness looks for it once, at propose, in the proposed text, and stores the result. Undo is allowed only when the line was in the proposed text and is in the bytes that really ran: a silent fix that removes the line ends the ability (`undo_no_marker`, `status` shows undo not available), one that adds it does not give it. `undo` runs the bytes of the latest real run (never the file on disk, never another session's proposal) with the single argument `undo` and no `DRY_RUN`, after any real run that started the script, whatever its exit. There is no second dialog; each attempt shows the owner a warning notice (name, short hash, attempt n of 3), writes a `script_run` trace record of kind `undo` and a log of kind `undo`. It exits 0 once and counts once; a failed undo may be retried, three attempts in all. It is available for 60 minutes after the real run. It is refused for a script without the marker (`undo_no_marker`), before a real run (`undo_not_run`), after it is done (`undo_done`), after three attempts (`undo_attempts`), after the hour (`undo_expired`), with no proposal (`undo_no_proposal`) and for a subagent child (`script_child`). After the hour, or after a new propose replaced the proposal, the way is a new propose.

**Status.** `status` prints a JSON report. After a real run that used the approval up it says `approvalUsed: true`, `attemptsLeft: 0`, the hash that ran (`ranHash`) and when (`ranAt`, ISO time); `hash` keeps its meaning, the hash of the proposed text, and `ranHash` is the hash of the bytes that ran. Its `undo` part shows `supported`, `available`, `used` and `attempts`; `availableUntil` appears only with undo supported and not yet used, and `attemptsLeft` only with undo supported (0 once used).

**The dry run is the script's own promise.** The harness only checks that the text contains `--dry-run` or `DRY_RUN` (a comment satisfies it); whether the script really changes nothing on that run is up to the script. On approve the dry run runs at once. A real run needs a dry run of the same bytes with exit 0. The foreman is told to read the dry-run output and, when it shows an unexpected state or a different change than described, to stop and propose again with a corrected description.

**Silent-fix bound.** When the script changed after approval, the harness measures the new text against the bytes the owner approved (never against the last fix, so fixes cannot add up): at most `safety.scripts.silentFixLines` changed lines (added plus removed in a minimal line diff, default 5; 0 turns it off; a project or session layer can only lower it) and at most 400 bytes in the added lines. Within the bound the new bytes run after a new dry run, and the owner gets a notice (the script name, the old and new short hash, the changed lines) and the trace a `script_fix` record. Outside it the call refuses with `script_changed` and the foreman proposes again.

**Expiry and attempts.** An approval covers dry runs, and real runs until one exits 0, at most 3 real attempts; then it is used up (`script_consumed`). It expires 60 minutes after the dialog (`script_expired`).

**Limits.**

- Standard input is closed and there is no terminal, so a prompt (a password prompt, `sudo`) fails.
- The secret redaction covers only the tool result; the log file in the scratch dir is not redacted.
- A process that detached itself from the script's process group outlives the run. On Windows nothing is killed after a normal exit (the tree kill needs a live root), only on the limit or an abort.
- A description that does not match the script is not detected. The owner approves a summary the foreman wrote; the hash ties the approval to the bytes, not to the description.
- Anyone who can write the scratch dir of the checkout can edit the script within the silent-fix bound; that edit then runs after a notice only, without a new dialog.
- The shell floors are unchanged: the same change through `bash` is still stopped, and the opaque-script gap described under [permissions](permissions.md#floors) stays open.

Trace records: `dialog` with surface `script`, `script` (decision, by, hash), `script_fix` (from, to, added, removed), `script_run` (kind dry, run or undo, hash, exit, seconds; attempts for undo).

## What an install runs on your machine

This is what `foreman setup` and Pi run when you install pi-foreman, and where the code comes from.

- **The clone.** Pi clones this repository from GitHub into your agent directory. Install without `@<ref>` follows the default branch. To pin a version, add a tag or commit: `pi install git:github.com/Shredi/pi-foreman@<ref>`.
- **The npm install.** Pi runs `npm install` in the clone. The `.npmrc` there turns install scripts off (`ignore-scripts=true`), so no dependency runs code while it installs. The versions come from the committed `package-lock.json`.
- **The fork package.** `pi-intercom` comes from GitHub by commit, not from the npm registry. The `.npmrc` line `allow-git=root` lets npm 12 install it, because it is a direct dependency of this package. Some npm 11 versions before 11.9 (seen on 11.5 to 11.8) print a warning about that line and carry on. npm 10, npm 11.13 and later and npm 12 print nothing. npm 11.9 to 11.12 have a bug and refuse this package anyway, so the install fails with `EALLOWGIT` (see [npm stops with EALLOWGIT](install.md#npm-stops-with-eallowgit)). npm 12 needs the line: without it the install fails.
- **Add-ons.** Setup installs the add-ons you accept at exact versions. It switches install scripts off for these installs. The add-ons bring their own dependencies, and those are not locked: a new release of a dependency can be picked up at install time. If Pi installs a missing add-on by itself at start, or you run `pi install` yourself, scripts run unless you turn them off. To do that, set `ignore-scripts=true` in your user-level npm config (`npm config set ignore-scripts true`).
- **Your own overlay.** Setup installs an overlay package you name with its install scripts on, because you vouch for it. An overlay is usually your own scripts and tools and needs no install script. Setting `ignore-scripts=true` in your user-level npm config covers the overlay and every install Pi starts, and is the recommended setting. Overlay authors should not rely on install scripts.
- **Files setup writes.** Setup writes the marked resume block (and an add-on env block) into your shell startup files or PowerShell profile, the agent directory and, on `--mods`, the herdr-app mods folder. When the Node test runner starts setup (`NODE_TEST_CONTEXT` is set), setup refuses to write the real versions of these places unless `PI_FOREMAN_ALLOW_REAL_HOME=1` is set, so a test cannot change your home.
- **The page server.** The first page link of a session (or the herdr-app Agents mod at start) starts `foreman pages serve`, a background process that listens on `127.0.0.1` (port 47317 by default) and serves the harness pages behind a secret per page folder. It runs as you, reads only the pages a session registered, stops after 12 hours of no use or when `pages.server.enabled` is false, and opens a network address only when your own user config sets `pages.server.bind`; see [pages](pages.md) for the threat statement. Switch it off with `pages.server.enabled: false`; links are then file links.
- **Pi's tool download.** Pi downloads the search tools `fd` and `rg` from GitHub releases the first time it starts. pi-foreman does not control that download.
- **No updates by themselves.** Nothing updates until you run `pi update` or `foreman update-check` and act on it.
- **Other package managers.** If you set Pi to use pnpm or bun, neither the lockfile nor the `.npmrc` settings apply to the clone.
