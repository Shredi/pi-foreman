# Development

> Covers the repo layout, test commands, the replay rig, CI, Windows notes and how the docs are kept current.
> Read it when you change pi-foreman itself.
> It must run on Linux, macOS and Windows. Python is stdlib only (3.13+) and runs the existing scripts; new harness code is TypeScript, and a new `.py` file is allowed only as a test, bench task data or vendored `core/` (the rule is in [AGENTS.md](../AGENTS.md), `extensions/core-adapter/test/python-files.test.ts` enforces it).

## Layout

- `extensions/` Pi extensions (TypeScript): `core-adapter/`
- `agents/` role definitions; `instructions/` foreman and reviewer prompts
- `core/` vendored Python core; `scripts/` own Python (config, guards, retro, sync, bench, update-check); `foreman findings list|dismiss|export` and `foreman retro models` read
  the reviewer findings store (`scripts/foreman_findings.py`)
- `config/` defaults, schema, `symbols.json` glyph sets, opt-in `presets/`
- `integrations/herdr/pi-foreman-sidebar/` Herdr plugin (Python daemon, manifest, rows snippet)
- `bench/` benchmark presets, prices and Harbor agents; `bin/` the `foreman` and `ledger` wrappers
- `design/` architecture record; `tests/` Python tests, `tests/installer`, `tests/replay`
- `setup.mjs` setup script (`foreman setup`); `packages.lock.json` pinned Pi and packages
- Runtime dependencies (`package.json`, exact pins mirrored in `packages.lock.json`): pi-subagents, pi-intercom, `unbash` (the gate's shell parser), and `@inquirer/prompts` (the arrow-key setup picker, imported lazily by `setup.mjs`). `@earendil-works/pi-tui` is a Pi-provided peer (`"*"`), not a dependency, because Pi warns about host packages under `dependencies`; a checkout has it as a devDependency for `setup --preview` and the installer tests, so a package install without dev dependencies has no `--preview`

Python rule: a new `.py` file is allowed only as a test (`tests/**/test_*.py`), bench task data or vendored `core/` ([AGENTS.md](../AGENTS.md); `extensions/core-adapter/test/python-files.test.ts` checks it against the frozen list `python-files.txt`). New harness code is TypeScript.

Running from a checkout instead of the installed package: [install](install.md#developing).

## Tests

```sh
python -m unittest discover -s tests -v          # npm test (through the test lock, `--exec` mode)
node --import ./extensions/core-adapter/test/_hermetic-env.mjs --test "extensions/core-adapter/test/*.test.ts"   # npm run test:node (through scripts/foreman_test_run.mjs)
node --test "integrations/herdr-app/pi-foreman/*.test.mjs" "integrations/herdr-app/pi-foreman-plan/*.test.mjs"   # herdr-app mods (also in npm run test:node)
node integrations/herdr-app/pi-foreman/bench.openprs.mjs   # Open PRs render cost (stubs hook built in): one row per shape with PRs, repos, sessions, HoverCards, full card builds, elements, median ms of 5 renders; `--main <path>` benches another main.js
node --import ./tests/installer/_hermetic-env.mjs --test "tests/installer/*.test.mjs"   # npm run test:installer
npm run test:ci                                   # pre-PR: every CI step a local machine can run, in CI's order; replay is the slow step
npm run test:gate-sweep -- --seeds 20             # opt-in: the permission-gate generator test over 20 seeds (about 2.5 s each)
npm run typecheck                                 # tsc --noEmit (strict, allowJs)
npm run lint:ts                                   # oxlint with types over extensions and setup
node setup.mjs --dry-run                          # installer preview, writes nothing (exits 1 until pi-foreman is installed as a package; see install.md#developing)
```

The installer suite preloads `tests/installer/_hermetic-env.mjs`, which points `HERDR_APP_HOME` at an empty temp dir so no installer test reads the real app home. It also puts an `npm` shim first on PATH that refuses `ci`, `install`, `i` and `add` (exit 1, `npm <sub> refused under the installer tests`) and forwards every other subcommand to the real npm, so a test run never reinstalls packages in your checkout. When `node_modules` is older than `package-lock.json`, setup stops at that refusal: run `npm ci` yourself after a lock change.

**Real places under the test runner.** A child of `node --test` has `NODE_TEST_CONTEXT` set, and setup (`setup/real-home.mjs`) then refuses to write or remove the real default places: the shell startup files, the PowerShell profile folders (and the Documents query on Windows when neither `PI_FOREMAN_HOME` nor `PI_FOREMAN_TEST_PS_DOCUMENTS` is set), `~/.pi/agent` and `~/.config/herdr-app`, of the account in the user database (`os.userInfo().homedir`, so a test's `HOME` does not change it). A test that spawns setup points `PI_FOREMAN_HOME`, `--agent-dir` and `HERDR_APP_HOME` at temp dirs (`import "./_sandbox-home.mjs"` does the first); `PI_FOREMAN_ALLOW_REAL_HOME=1` lifts the guard. With `--dry-run` the guard prints `real-home guard: would refuse <path>` instead of refusing. `sandbox-import-lint.test.mjs` requires that every test file under `tests/installer` (nested folders included) that starts a process (`spawn*`, `execFile*`, `fork`, `execSync`, `exec` from `child_process`) imports `_sandbox-home.mjs` or `_hermetic-env.mjs`.

A fresh worktree needs `npm ci` before `npm run test:node`.

**Gate generator test.** `extensions/core-adapter/test/gate-generator.test.ts` (data in `_gate-gen.ts`) hides seven dangerous payloads in about fifty shell constructs, alone and nested two and three deep, and runs every line through the real `gateEvaluate` as a builder and as a reviewer; a line that runs with no block, judge look or ask fails unless `KNOWN_GAPS` (or `PLAIN_GAPS`, for plain lines) marks its shape with an id and a source, and a mark whose gap closed fails too. Harmless twins are pinned per construct, a real bash checks that each construct runs its payload, and a sample goes through the real `tool_call` handler. It runs in `npm run test:node` (seed 1, about 12 s); `npm run test:gate-sweep -- --seeds N --seed S` sweeps seeds. The project skill `.agents/skills/verifying-permission-gate` says how to read a failure.

A new `context` or `before_agent_start` hook must keep the messages already sent byte-identical (the rules are in [cache](cache.md#stable-prefix)). `extensions/core-adapter/test/prefix-stable-catchall.test.ts` collects every such handler the adapter registers and fails when one rewrites a sent message or the system prompt, so a new hook needs no entry there.

`npm run test:node` and `npm test` run through `scripts/foreman_test_run.mjs`, so parallel sessions do not overload the host. Only one full suite runs per machine: the wrapper takes an exclusive lock file `<agentDir>/pi-foreman/state/test-lock` (the temp dir when the agent dir does not exist; `FOREMAN_TEST_LOCK_DIR` overrides the directory) holding `{id, pid, started, cwd, command, host}`. Every run prints one stderr line `run <id> (pid N, cwd <cwd>); stop it with: node scripts/foreman_test_run.mjs --stop <id>` (also with the lock off) and keeps a record `{id, pid, cwd, command, started, state}` (`waiting` then `running`) in `test-runs/<id>.json` next to the lock, removed on exit. `--stop <id>` stops only that run, on every OS and without a signal or a pattern kill: it writes `test-runs/<id>.stop`, which the run polls while queued (it leaves the queue and runs nothing) and while running (its process tree is stopped as for the time limit and the lock released). The stopped run prints `run <id> stopped on request` and exits 130; `--stop` waits up to 15 s for the run to end, then exits 0, or 1 when the run is still alive (naming its pid) or the id is unknown or its process is dead (a dead record is cleaned). `--stop-cwd` stops the runs of this worktree only. `--list` prints the holder and the runs, one line each. A second run prints `waiting for the test lock held by run <id> (pid N, cwd <cwd>), since HH:MM: <command>, queue position P of Q` to stderr (`unknown` for fields a lock file of an older wrapper lacks), again at once when the holder changes, and `still waiting for … ; waited M min` every minute; it polls every 250 ms. The wait is bounded by progress: after `FOREMAN_TEST_LOCK_WAIT_MINUTES` (default 20; a positive number, fractions allowed; invalid means the default) counted from the last holder change, so a queue of live runs that keeps moving does not give up, the wrapper prints `gave up waiting for the test lock after M min; held by …`, runs nothing and exits 75. A live holder counts as busy however idle it looks, and is never taken over. A time limit is set with a leading `--timeout <s>` or `FOREMAN_TEST_TIMEOUT=<s>` (the flag wins; a positive number of seconds, fractions allowed; an empty env value is unset; a bad value exits 2 with nothing run). It is one deadline for the lock wait plus the run and also applies with the lock off. When it passes, the wrapper stops the run and every descendant without a process group (POSIX: `ps -A -o pid= -o ppid=`, SIGTERM, after 5 s SIGKILL of everything seen in either listing; if `ps` fails only the main test process is stopped, with a note; Windows: `taskkill /pid <pid> /T /F`), releases the lock after that, prints `time limit of <s> s reached after <e> s; stopped the run` (plus the holder waited on, if any) and exits 124. macOS has no `timeout` command; agents set `FOREMAN_TEST_TIMEOUT` below the shell tool's own limit. The holder touches the lock file every 5 s (heartbeat). A lock is stale, and is taken over atomically, when its pid is dead, its heartbeat is older than 60 s, or it is unreadable and older than 5 s; a lock file without an `id` (old-format wrapper, no heartbeat) with a live pid is stale only when its `started` is older than `FOREMAN_TEST_LOCK_MAX_MINUTES`. A live holder caps its own run at `FOREMAN_TEST_LOCK_MAX_MINUTES` (default 30): it stops its tree, releases the lock, prints `run <id> passed the run cap of M min; stopped the run` and exits 124. The lock is released on exit, failure, SIGINT and SIGTERM (the signal goes to the child first). `node --test` runs with `--test-concurrency` set to half the cores (`FOREMAN_TEST_CONCURRENCY=N` overrides). `FOREMAN_TEST_LOCK=0` or a truthy `CI` skips the lock (CI sets `CI`; the macOS leg runs `npm run test:node`, the other legs call `node --test` directly). `npm run test:node` and the CI adapter step pass `--import ./extensions/core-adapter/test/_hermetic-env.mjs` (hermetic env for the core-adapter tests: session variables cleared, fake `gh` and `npm` on PATH, seeded npm root and app home, spawn counter, and git housekeeping off for every git child through `GIT_CONFIG_*`: `maintenance.auto=false`, `gc.auto=0`, so no detached `git maintenance` races a rig that copies a repository). The wrapper starts every command (node mode and `--exec`) with the running-session variables of `extensions/core-adapter/test/session-env.json` removed from its env (the one list, read through `scripts/session_env.mjs`; the child git env `GIT_CONFIG_*` is not on it on purpose); `scripts/replay_run.mjs` and the installer preload `tests/installer/_hermetic-env.mjs` (scrub first, then `HERDR_APP_HOME`) do the same, so `npm test`, `test:node`, `test:installer` and the replay suite never see a session's flags. A test file started by hand with plain `node --test` is scrubbed only by the preloads it imports. Leading node options such as `--import` stay before `--test`; the first plain argument starts the globs. `--exec -- <command>` takes the lock around any command without the concurrency flag. Builders run targeted tests only, through `node scripts/foreman_test_run.mjs [--timeout <s>] --targeted <node args and files/globs>`; the reviewer runs the full suite once per change. A targeted run is a node-mode run (same `--test` argv, spawn guard and env scrub) that takes one of `FOREMAN_TEST_TARGETED_SLOTS` (default 2) machine-wide shared slots, the files `test-slot-<k>` next to the lock, instead of the exclusive lock, so it never waits for a full-suite run and never blocks one. Slots follow the lock's rules (holder body, 5 s heartbeat, stale takeover of dead, silent or unreadable holders, one FIFO queue `test-slots.queue` that feeds any free slot, `FOREMAN_TEST_LOCK_MAX_MINUTES` run cap, `FOREMAN_TEST_LOCK_WAIT_MINUTES` give-up restarted whenever a slot holder changes, `FOREMAN_TEST_LOCK=0` or `CI` skips). Its `--test-concurrency` is `max(1, floor(cores / FOREMAN_TEST_TARGETED_SHARE))` (default share 4); `FOREMAN_TEST_CONCURRENCY` does not apply to it. Invalid values of the slot and share keys mean the defaults. Run id, `--stop`, `--stop-cwd` and `--list` work as for the suite; the record has `mode` `targeted` or `suite`, and `--list` also prints the slot holders. A waiting run prints `waiting for a targeted test slot (N of N busy), queue position P of Q; held by: run <id> (pid …); run <id> (pid …)` at once, when the holders change and every minute; the exit-75 give-up line names the slot holders. File-based on every OS, no signals beyond the process-tree stop of the time limit. **Run temp root:** every run (node mode and `--exec`, not `--stop`/`--list`) first sweeps old `pf-*` entries (top level of the temp dir and `~/.cache/pi-foreman-tests` only, own files, mtime older than one day, symlinks not followed, `pf-rb-work` kept, at most 2000 per run), then makes `<tmpdir>/pf-run-XXXXXX` and starts the command with `TMPDIR`/`TMP`/`TEMP` (POSIX; Windows only the helper variables) plus `FOREMAN_TEST_TMP_ROOT` and `PI_FOREMAN_TEST_TMP` pointing at it (`scripts/test_tmp_root.mjs`; under literal `/tmp` or on Windows the root goes to `~/.cache/pi-foreman-tests`, like `mkTestTmp`). The root is removed on every exit (normal end, `--stop`, lock give-up, deadline, signals); entries a test left in it are named on stderr as `test-run: N temp entries left by this run: <first 5>` (a warning, not a failure: fix the test). A nested run reuses the outer root. A detached run (`--detach`) makes and removes the root in the background worker that runs the command, never in the launcher that returns early; `--wait`, `--history` and the other control calls never sweep or remove a root. A direct `node --test` with a hermetic preload (one root per test file process on Node 26, where preloads run only in the file children), or `python -m unittest` (`tests/_isolation.py`), makes and removes its own root the same way but never sweeps: the sweep runs only in the runner, at most 2000 entries per run. Tool caches (`node-compile-cache`, `jiti`, `tsx-<uid>`) are not counted as leftovers. A SIGKILLed run leaves its `pf-run-*`; the next run sweeps it after a day. **History.** Every wrapped run (suite and targeted, lock on or off) appends one JSON line to `test-history/history.jsonl` next to the lock (`test-runs/` keeps only live records and stop files): `{id, mode, kind (exec|node), detached, command, commandHash, cwd, treeStart, tree, enqueued, acquired, ended, exit}`; `acquired` is `null` when the lock was never taken (with the lock off it equals `enqueued`). `tree` is a sha1 of `HEAD`, `git diff HEAD --binary` and the untracked files with size and mtime (empty outside a git checkout; approximate, computed at enqueue (`treeStart`) and after the run ends (`tree`), 10 s cap). Over 2 MB the file is renamed to a unique `history-<time>-<pid>.jsonl` and the newest two archives are kept; a history error never changes a run's exit code. `node scripts/foreman_test_run.mjs --history [--days N]` (default 7) prints per mode and kind: runs, waited runs (more than 5 s between enqueue and lock), wait median/p90/max over those, exit 75, exit 124 while queued and while running, exit 130, run duration median/p90. **Reuse of a passing run.** Before it queues a full-suite run (not `--targeted`; foreground or detached), the wrapper computes the tree key and looks in the history and the kept archives for a run with the same `commandHash` (sha256 of the full argv; `command` is cut at 119 characters, so it cannot serve; lines without the field are never a source), the same cwd (by real path), mode and kind, exit 0, `ended` within `FOREMAN_TEST_REUSE_HOURS` (default 24), no `reusedFrom`, and a non-empty `treeStart` (the tree key taken at enqueue) equal to its `tree` and to the current key. On a hit it queues nothing, prints `foreman_test_run: reused run <id> (passed, same code, ended <time>)` (plus the log path if the log exists) and exits 0; a detached start does the same before the background start and returns the source id, so `--wait <id>` reports its `done` line (a source whose done file is gone is a miss). A reuse appends a history line with `reusedFrom`; `--history` counts those in a `<mode> <kind>: reused N` line (printed only when above 0) and keeps them out of the other figures. `FOREMAN_TEST_REUSE=0` always runs, an explicit `FOREMAN_TEST_REUSE=1` wins over `CI`, a truthy `CI` otherwise runs; the hermetic test env helpers set `0`. The tree key is approximate (untracked files by size and mtime; git-ignored files and the node version are not in it) and a child could forge a history line, so this is no security limit; CI runs the suites regardless. Measured over 2026-11-21 to 11-25 (371 full-suite runs): 33 runs had an earlier exit-0 run with the same command, cwd, kind and tree within 24 h; they waited 381 min in the queue and ran 195 min (an upper bound: end-tree based, matched on the truncated command). **Detached runs.** `FOREMAN_TEST_DETACH=1 npm test` (or a leading `--detach`, for a direct call; the env form works for every npm script) starts the run in the background with stdout and stderr in `test-history/<id>.log` and returns at once with the run id, the log path and the `--wait` command. The id reaches the run in `FOREMAN_TEST_RUN_ID` (not passed on to the started command); a detached run ignores `FOREMAN_TEST_TIMEOUT` and `--timeout` and keeps the lock rules (FIFO, 20-minute progress give-up, 30-minute run cap); each detach start removes done files and logs older than 7 days. On exit a run writes `test-history/<id>.done.json` (`exit`, `ended`, `waitedMs`, `ranMs`) before it removes its record. `node scripts/foreman_test_run.mjs --wait <id> [--max <s>]` (default 240, at most 540; set the shell timeout above it) polls and ends with one state line `run <id> <state>`: `done` (exit = the run's exit; the last 40 log lines come first), `queued, position X of Y, lock held by …` or `running for M min` (exit 3: ask again), `starting` (log younger than 30 s, no record yet; exit 3), `died` (no done file and the record gone or its process dead; log tail; exit 1), `unknown run` (exit 2). The suite's own exit can also be 1, 2 or 3, so read the state line.

**Spawn guard.** On macOS, processes that set a process title register with the system's app-launch service; such registrations at test-run rates correlate with a reported failure of that macOS service. Measured on macOS: only `npm` and node processes with a changed `process.title` register; git, python, plain node and node's test runner do not. So a test run has two hard rules: it starts no `npm`, and no node process of the run changes its process title. There is no limit on the total count of child processes. The test preload (`_hermetic-env.mjs`, through `_spawn-count.mjs`) counts every child process a test process starts, per command (git, python, node, npm, other), and writes one small file per process into a temp directory the wrapper names in `FOREMAN_SPAWN_COUNT_DIR`. After a node run the wrapper prints `child processes: N (git a, python b, node c, npm d, other e)` (a summary only) and exits non-zero when a run that otherwise passed started any `npm`/`npm.cmd` or had a titled node process (`--exec` runs have no guard). CI runs the guard on the macOS leg only (`npm run test:node` replaces the adapter and herdr-app steps there). Title rule: the wrapper (node mode only) appends `--require=<path>` of `extensions/core-adapter/test/_proc-watch.cjs` to the run's `NODE_OPTIONS`, keeping an existing value, so the preload runs in the `node --test` runner, the file processes and node descendants. It compares `process.title` with its start value (in an unref'd 1 s check and at exit) and, on a change, writes a record naming the test file (`FOREMAN_TEST_FILE`, set by `_spawn-count.mjs` in each file process so a descendant is named by the file that started it; "test runner" for the runner); the wrapper lists each file. Leftover warning: `_spawn-count.mjs` keeps each async child until its `exit` event and, when the test process ends, records those still running; the wrapper prints `warning: child processes still running when a test process ended:` and one line per file with the count and kinds. It never changes the exit code. Parent watch: the wrapper sets `FOREMAN_TEST_WRAPPER_PID`; the preload checks once a second that this pid exists and exits the process when it does not, so a wrapper killed with SIGKILL leaves no running `node --test` runner or file process (they stop within a few seconds). Limits: a child started with a cleaned environment (no `NODE_OPTIONS`) is not covered by the title rule; a titled process killed by a signal within its first second, and a title set and restored before the next check or exit, are not recorded; on Windows `process.title` is the console title shared by the processes on one console, so a title equal to the console's current title is not recorded (CI runs the guard on the macOS leg only); a title set on the command line (`node --title=…`) is set before the preload notes its start value and is not recorded; the leftover check sees direct async children only, and a child that exited but was not yet reaped can show up falsely (warning only); on Windows a quickly reused pid can hide a dead wrapper, and a killed wrapper that its own parent has not reaped yet (a zombie) still answers until the reap. An `npm` or `npx` reached through a shell is caught on POSIX by the fake `npm` and `npx` (same log): the counter takes the larger of the direct `npm` count and the log's lines, so a direct spawn counts once. On a guard failure the runner names the test files that started `npm` or had a titled node process. A test that runs a stub `npm` of its own on a temp PATH sets `FOREMAN_SPAWN_GUARD_EXEMPT=1` around the call so the counter skips it. The global npm root reaches the code under test by a seam: the preload seeds a slot on `globalThis` under `Symbol.for("pi-foreman.npm-root")` with a temp directory (`owned.ts` `npmRootOnce`, `pi-model-data.mjs`), and puts a fake `npm` and `npx` that log to `FOREMAN_FAKE_NPM_LOG` and fail next to the fake `gh` (POSIX only). Tests of the lookup itself clear the slot and use their own stub (`npm-root-once.test.ts`). To measure outside the guard, preload a script that wraps `ChildProcess.prototype.spawn`, `spawnSync`, `execFileSync` and `execSync` and logs one line per start, via `NODE_OPTIONS="--import <script>"`, which also counts node descendants. In production a process starts one `npm root -g` from this package, shared by both lookups (`npmRootOnce` in `owned.ts` and the sync one in `pi-model-data.mjs`, which accepts only a successful npm answer) through the raw answer in the slot; the one exception is the sync model-data lookup (reached only when no `pi` on PATH resolves) called while the first session's async lookup is still in flight (at most 4 s), which cannot wait and starts its own; there is no environment override of the result (it is a read-only owned root), so each child process resolves it itself. pi-subagents resolves the global npm root itself with `npm root -g` on the first skill lookup, so tests that reach that lookup set `PI_OFFLINE=1`.

## Sample view

The herdr-app mod `pi-foreman` can draw its sidebar from invented data, to look at every marker of the legend in [herdr](herdr.md#legend-of-the-sidebar-markers) in one picture. Props are set on the mod's block in a layout file (`<app home>/layouts/<name>.json`, the same place as `foreman`): add `"props": { "sample": true }` to the `pi-foreman` block, best in a layout of a second app home (`HERDR_APP_HOME` pointing at a temp dir that holds a copy of the mod) so your own layout stays as it is. The switch has one setting: `"manyPrs": true` next to it (ignored without `sample`) draws the invented ~50-PR feed `SAMPLE_MANY` of `sample.mjs` (52 PRs in 18 repositories, mixed states, one unreviewed, one without a title, one without a page address, and one repository with 12 PRs of which 9 fail and 1 conflicts, to see the capped group and its "+N more" line) instead of the legend's, to look at the Open PRs section with many PRs. Otherwise it has no other effect: with it the mod reads the host lists, the radar document and the PRs from `integrations/herdr-app/pi-foreman/sample.mjs`, runs no `foreman`, `hc` or opener, polls nothing and does not write the Agents order. Without the prop nothing changes. `sample.mjs` has one row per legend key; `render.legend.test.mjs` fails when a key of the table has no row or a row has no key, and draws the sample through the stubs.

To look at the sample view without touching your own app window (herdr-app 0.1.x, macOS):

1. Make an empty directory as a second app home, and keep its path short: the app's socket `herdr-app.sock` lives in it, and a long path fails with "path must be shorter than SUN_LEN", so use a short temp directory. Copy `integrations/herdr-app/pi-foreman` and `integrations/herdr-app/pi-foreman-plan` into its `mods/`, and put a layout file into its `layouts/`: a copy of the layout you use, with `"props": { "sample": true }` on the `pi-foreman` block.
2. Before you start the second window, put `"frame.welcomed": "finished"` into the app home's `shared.json` (create it as `{"frame.welcomed": "finished"}` when the file does not exist yet): a fresh app home shows the welcome dialog over the sidebar, or you can close that dialog by hand. Start the second window: `HERDR_APP_HOME=<app home> herdr-app`. The app fills in the shipped mods there itself. The window attaches to the same herdr-core, so it shows your spaces; the sample view itself starts nothing.
3. Switch to the sample layout, check the status, and save a picture:

   ```sh
   HERDR_APP_HOME=<app home> herdr-app do layout.switch --name <layout>
   HERDR_APP_HOME=<app home> herdr-app status      # the errors list must be empty
   HERDR_APP_HOME=<app home> herdr-app shot <file.png>
   ```

4. Close the second window when done: `HERDR_APP_HOME=<app home> herdr-app do app.quit`. This quits only the second window.

`shot` saves the last drawn frame, and a window that is not in front does not advance its animations, so the pulse and the spinner show as a still frame in a picture; look at the window itself for the motion.

## Installer test rig

`tests/installer/rig/sandbox.mjs` exports `createSandbox({ versions })`, one hermetic sandbox per test: a temp agent dir, a fake `HOME`, and a bin dir first on `PATH` holding shims for `pi`, `npm`, `herdr`, `herdr-app`, `hc` and `python`. It returns `{ agentDir, home, binDir, env, calls(), snapshot(), cleanup() }`. Pass `env` to the process under test (it sets `HOME`, `PATH`, `PI_CODING_AGENT_DIR`, `PI_FOREMAN_PI_BIN`, `FAKE_PI_LOG`, `PI_FOREMAN_PICKER=off`, `CI=1`); `calls()` returns every shim call as `{tool, argv, cwd}` from one JSONL log (`$FAKE_PI_LOG`); `snapshot()` returns the agent dir as `{relative path: contents}`; call `cleanup()` in a `finally`.

The shims are Node scripts in `tests/installer/rig/shims/` (`pi` is `fixtures/fake-pi.mjs`), started through `process.execPath` by a `#!/bin/sh` wrapper, or a `.cmd` wrapper on Windows. The shims other than `pi` write only to the log; the `pi` shim (`fixtures/fake-pi.mjs`) also writes `settings.json` in the sandbox agent dir. `SHIM_VERSIONS` is a JSON map the shims answer from: `npm view <pkg> version` returns `map[pkg]`, `herdr --version` returns `map.herdr`, `herdr-app --version` returns `map["herdr-app"]`, `hc --version` returns `map.hc`, `python --version` returns `map.python`; a missing key exits 1. `npm install` and `npm ci` exit 0. No test touches the network or the real agent dir.

Screen snapshots: `tests/installer/screens.test.mjs` draws each setup screen from `setup/fixtures/preview.json` through the frame-capture terminal at 100x30 and 80x24 (key scripts drive navigation) and compares to `tests/installer/screens/*.snap.txt`. After an intended change, rewrite them with `UPDATE_SNAPSHOTS=1 node --test tests/installer/screens.test.mjs` and review the diff. To see a screen yourself, run `node setup.mjs --preview <screen>` (same sample data, so you see the snapshot bytes live). Rig tests: `tests/installer/rig.test.mjs`.

## Replay rig

`node scripts/replay_run.mjs` runs each `tests/replay/test_*.py` as its own `unittest` process, in parallel: `FOREMAN_REPLAY_JOBS` workers (default `min(4, availableParallelism)`), then the modules in its `SERIAL` list one by one. It prints a PASS or FAIL line per module, the 15 slowest, the wall time, and the last 80 lines of each failing module; exit 1 on a failure, 2 when no module is found or the arguments are bad. `--shard i/n` (or `FOREMAN_REPLAY_SHARD=i/n`; the flag wins) runs only shard i of n: the sorted modules are dealt round-robin, pool first, then the serial ones continue the count, so the n shards are disjoint and cover every module. `--list` prints the stems a selection runs and exits without starting Python. One shard locally: `node scripts/replay_run.mjs --shard 2/4` (preview with `--list --shard 2/4`). Each module starts `pi --mode rpc` with
a temp `PI_CODING_AGENT_DIR` and temp project against a scripted fake provider and compares the trace to golden
sequences. No real model calls. The Pi CLI comes from `FOREMAN_PI_CLI`, else the global npm root, else Pi's managed
install (`~/.pi/agent/install/current-version`); none found is an error naming the paths tried, not a skip. pi-subagents, the permission system and pi-intercom come from the repo's `node_modules` (run `npm install` first); the rig
adds only this repo as a package and filters intercom out for non-intercom rigs. Rigs wait with `driver.wait_until(pred)`: it polls the asserted condition and raises with the last state seen on timeout; do not add fixed sleeps before assertions. `FOREMAN_FAKE_DELAY=<tag>:<step>:<ms>` (`fake_provider.ts`) delays the fake model's answer to that script step (the step `locate()` computes), so a test can force a timer to fire inside a run (`test_replay_wait_race.py`). When `driver.py` times out waiting for an RPC record, the `TimeoutError` message (prefix `no RPC record in time`) carries the stderr tail, the last 25 records seen as (type, customType, role) and the count and last 5 unparseable stdout lines (each cut to 300 characters). `FOREMAN_REPLAY_UPDATE_GOLDEN=1` regenerates the replay goldens; run it only for the rigs you intend to change and review the diff. Design: `design/architecture.md`
[section 10](../design/architecture.md#10-replay-rig-and-tests), installer: [section 11](../design/architecture.md#11-installer).

## CI

GitHub Actions runs a matrix of Linux, macOS and Windows on Python 3.13 for pull requests and after each merge to main, plus manual dispatch (no feature-branch push trigger). Which legs run where: the `test` job runs its macOS leg on pull requests and main; the macOS legs of `replay` and `fresh-install-advisory` run on push to main (and manual dispatch) only, and are left out of the matrix on pull requests. The reason is runner capacity: GitHub has too few free macOS runners, and PR legs were cancelled with "not acquired by Runner" before any step ran. The cost is that a macOS-only replay fault is found after the merge, on main, not before it. `ci-ok` does not need the macOS replay leg on a PR, because the leg is absent from the matrix there and the `replay` job's result comes from the legs that ran. The `test` job runs Node 22 (the minimum in `engines`) on Linux and macOS, the `replay` job on Linux, macOS and Windows, and both also Node 26 on Linux. The Windows leg is the separate `test-windows` job: three shards that run at once. Shard `1/3` runs the python, conformance, herdr, installer and shim steps, and shards `2/3` and `3/3` split the adapter tests with `node --test-shard` (`1/2`, `2/2`). Its `timeout-minutes` is 50 (measured 13 to 16, 18 to 20 and 15 to 24 min for shards 1/3, 2/3 and 3/3 over two runs; about twice the slowest shard), and `ci-ok` fails when any shard fails, is cancelled or is skipped. The run on main catches combination failures, because branch protection is non-strict (a PR need not be up to date with main). A new push to a PR cancels the superseded run; runs on main are not cancelled. The required checks are `ci-ok` and `pr-policy` (see [Auto-merge](#auto-merge)). `ci-ok` passes only when the `test`, `test-windows`, `replay`, `bench-smoke`, `fresh-install` and `review-gates-model` jobs all succeeded. Every job has a job-level `timeout-minutes` sized well above its normal run time (`test` 75, each `test-windows` shard 50, `replay` 45, the short jobs 5 to 15), so a hung test fails after that limit instead of GitHub's 360-minute default, and `ci-ok` treats a timed-out job as failed. `fresh-install` installs the way a new user does (`npm ci` in a clone, then the managed `npm install --omit=dev --legacy-peer-deps` in a fresh `git clone`) on Linux and Windows with the bundled npm and on Linux with pinned npm 11.13.0; a Linux cell with npm 11.12.1 must fail with `EBADENGINE` and `EALLOWGIT`. `review-gates-model` (Linux only, in `ci-ok`) runs the TLA+ model of the review gates (`.agents/skills/verifying-review-gates/model/ReviewGates.tla`) with TLC on Java 25 (`actions/setup-java`, Temurin, pinned by commit hash) and a `tla2tools.jar` (TLA+ tools release v1.7.4, the latest stable one, 2.3 MB) downloaded in the job and checked against a fixed SHA-256 (a different file fails the job). The job lists the gate files the model covers in its log (`reviewgates.ts`, `bound.ts`, `ledgercall.ts`, `childblocked.ts`); the model can drift from the code, so a change to one of them also updates the model. Cost: about 21 s of TLC on a 10-core Mac (10.3 million states, every order of up to 7 events over 2 checkouts), plus a Java install and a jar download; in CI the job takes about 1m22s, 59 s of it TLC on this model and 14 s on the permission-flow model (`.agents/skills/verifying-permission-gate/model/PermissionFlow.tla`) that runs in the same job. It is the only place Java is used: `package.json`, setup, install and the macOS and Windows legs have none. The main check of the same rules stays the TypeScript walk `extensions/core-adapter/test/review-gates-generator.test.ts` (about 1.1 million steps in under 2 s, in the `test` job). Local run of the model, with Java 25 on `PATH` or in `$JAVA_HOME`: download the jar once into a cache outside the repo, check it against the SHA-256 in `ci.yml`, then `cd .agents/skills/verifying-review-gates/model && java -cp <cache>/tla2tools.jar tlc2.TLC -config ReviewGates.cfg -workers auto -metadir "$(mktemp -d)" ReviewGates.tla`. `fresh-install-advisory` (not in `ci-ok`) runs the same with the newest npm on Linux and Windows on every run, and with the bundled npm on macOS on push to main only; it never blocks merging. The replay suite runs as the `replay` job, sharded per OS (`--shard i/n`): Windows 4 shards, Linux 2, macOS 1 on push to main only; on a pull request that is eight legs (Node 22 on Linux and Windows, plus Node 26 on Linux), and nine on main. GitHub caps concurrent macOS jobs per account, and macOS arm64 capacity is scarce (PR legs were cancelled with "not acquired by Runner" after 15 min in the queue), so macOS runs as one replay job on main (shard 1/1, which covers every module) plus the `test` job on both. Windows is the slow OS, so it keeps most shards. Every OS still runs the full suite. The `test` job no longer runs replay. Each shard runs through `scripts/replay_run.mjs` in parallel (`FOREMAN_REPLAY_JOBS` sets the worker count; the Windows legs use 2 workers, the others the default 4, because 4 cold `pi` starts on a 4-vCPU Windows runner timed out; the first RPC after launch, `session_id()` in `tests/replay/driver.py`, has a 60 s startup deadline, every other request 15 s); the Windows legs turn Defender real-time scanning off first for speed.

CI installs npm packages with `npm ci --ignore-scripts` from the committed lockfile (except the fresh-install jobs, which run plain `npm ci` and `npm install` and rely on `.npmrc`), every action is pinned to a full commit hash with a version comment (Renovate keeps both current, after a three day wait), and the replay job uses the locked Pi in `node_modules`, not a global one. A local `npm install` can write `git+ssh` back into `package-lock.json` for the two fork packages; `tests/installer/supply-chain-pins.test.mjs` fails when it does, so change the URL back to `git+https`.

`npm run test:ci` (`scripts/foreman_ci.mjs`) is the pre-PR check. It does not run the fresh-install jobs (they need the network). It runs every CI step a local machine can run, in CI's order except that `lint-ts` sits after `typecheck` here (in CI it runs next to `ruff`): `unit` (`npm test`), `core-pin`, `ruff` (skipped with a line when ruff is missing), `conformance` (`pull_core.py --conformance`, skipped when pytest is missing), `node` (`npm run test:node`), `installer`, `typecheck`, `lint-ts` (`npm run lint:ts`), `replay` (the replay suite against the `node_modules` Pi CLI) and `bench` (the smoke probe on the fake provider, skipped when `harbor` is not on PATH). It prints one line per step (the two test runners print their own output) and exits 1 on any failure; `--only <step>` runs one step. A `[pre-pr]` reviewer is asked to run every suite the repository's CI runs that can run locally and to name them in `review_verdict` `suites`.

## Auto-merge

A PR merges itself once its required checks are green: press GitHub's own **Enable auto-merge** button (squash) on the PR. No label or workflow is involved.

- **Required checks on `main`:** `ci-ok` (ci.yml) and `pr-policy` (`.github/workflows/pr-policy.yml`). `pr-policy` is its own workflow so a body edit reruns only it.
- **Policy rules:** the PR body opens with a plain `## Summary` for the owner (by instruction only; `pr-policy` does not check it) above `## Changelog`; its dense part lists each CI run the round started on its branch before the review request, and each failed run with its fix (also by instruction only). The workflow checks only that the body has a `## Changelog` section with at least one `- ` bullet before the next `## ` heading (`###` does not end it), and `CHANGELOG.md` is not among the changed files (neither as `filename` nor `previous_filename`). The workflow uses `pull_request` with a read-only token, no checkout and the body only through `env`, so no PR code runs and fork PRs work.
- **Turn it on for a repo (owner, once):** `node scripts/repo_automerge.mjs <owner/repo> [<owner/repo>...] --checks ci-ok,pr-policy` is a dry run that prints what it would change; add `--apply` to write. It enables `allow_auto_merge` and `delete_branch_on_merge` (read back afterwards), sets the required checks on the default branch and turns required pull-request reviews off. Rulesets are reported, never edited. With `--checks` the dry run also reports the default branch's force pushes, deletion and whether administrators are included (`WARN` when open; see [safety](safety.md#protect-the-default-branch-on-the-server)). A repo that fails is reported and the next one runs; the exit code is 1 if any failed. Where the plan has no branch protection (a private repo on a free plan) the script says so and skips it; there the button does not appear.
- **Trade-off:** with required reviews off a solo owner can merge their own PR, so the checks are the only gate. Keep required reviews on where a second person exists, and then auto-merge waits for the approval as well.
- **After the merge:** when the watch on the PR (`pr_watch`, see [tools](tools.md)) reports the merge, it triggers `git switch <default> && git pull --ff-only && git branch -d <branch>`, which the gate allows when the branch is merged (default rule `default-git-branch-merged`) ([safety](safety.md), [permissions](permissions.md)).
- **A PR merged on the host:** run a watcher with `bg_run`. Poll `gh pr view <n> -R <owner/repo> --json state,mergeCommit` every 60 s; stop on `CLOSED` (report closed without merge) or `MERGED` (report repo, PR and merge sha). Then retry `gh run list -R <owner/repo> --commit <sha> --workflow ci.yml --json databaseId -q '.[0].databaseId'` every 15 s for up to 5 minutes until a run exists, and run `gh run watch <id> -R <owner/repo> --exit-status` to follow the CI run on the default branch.
- **Known limit:** a PR that edits `pr-policy.yml` runs its own version of the workflow under `pull_request`, so the owner's button press stays the real gate for such a PR.

## Releases

Cut a release with `gh release create <tag> --generate-notes`. The notes come from the merged PRs' titles and their `## Changelog` sections (one to three user-facing bullets each). PRs do not edit CHANGELOG.md; it is kept as history. Overlays read the GitHub release page to see what changed.

## Lint

Three checks, and `just lint` runs all three (CI runs the type check on the Linux leg of the `test` job, and ruff and oxlint on the Linux leg with Node 22):

- **Type check.** `tsconfig.json` sets `strict` and `allowJs`, with no `checkJs`: our `.mjs` modules are read for their types (a TS import of `profiles.mjs` gets the inferred shape) but their own code is not type-checked. Two temporary lists hold back files of the running judge-first-unknown round, each with a comment: the `exclude` in `tsconfig.json` (its new `extensions/core-adapter/test/judge-first-unknown*.test.ts` files) and the `ignorePatterns` block of `.oxlintrc.json` (its edited files). Both are removed after that round merges.
- **TypeScript linter.** oxlint 1.94.0 with the type-aware add-on oxlint-tsgolint 7.0.2008 (both exact `devDependencies`, so `npm ci` installs one platform binary of each). `npm run lint:ts` runs `oxlint --type-aware --deny-warnings extensions setup`; the paths are the tsconfig scope, and the rest of the tree follows in a later round. `.oxlintrc.json` holds the rules: the `correctness` category plus a bug-oriented set of type-aware rules (no-floating-promises, no-misused-promises, await-thenable, no-base-to-string, restrict-template-expressions, unbound-method, switch-exhaustiveness-check and about fifteen more). Every rule that is off has a reason in the file. Two of the bundled rules are off on purpose: `eslint/no-control-regex` (ANSI escapes are intentional) and `unicorn/no-useless-spread` (a deliberate snapshot before a loop). The `no-unsafe-*` family, `no-unnecessary-condition` and `require-await` stay out with their counts. Fallback when the type-aware mode breaks: typescript-eslint with the same rule list, each name under the `@typescript-eslint/` prefix.
- **Python linter.** Ruff checks the Python (`ruff.toml`: target py313, rules E4, E7, E9, F, B (bugbear), RUF100; `core/` and the bench task data excluded). The version is pinned in `.github/lint-requirements.txt` (`ruff==0.17.5`); Renovate keeps the pin current. Install that version any of these ways:

```sh
pipx install ruff==0.17.5                  # or: uv tool install ruff@0.17.5
python -m pip install -r .github/lint-requirements.txt
ruff check .                               # from the repo root; `just lint` runs the same
```

  CI runs it in the `test` job, on the Linux leg with Node 22 (`python lint (ruff)`: install from the pin file, print `ruff --version`, `ruff check .`). `# noqa` markers stay only where a rule needs a reason; RUF100 fails on a marker that no longer suppresses anything. Fix a finding in the code when it is one; mark it with the reason when it is deliberate.

`npm run lint:ts` runs in CI as the `typescript lint (oxlint)` step, in the same job and leg as ruff. Fix a finding in the code, or add a rule-off with its reason to `.oxlintrc.json`; an inline disable needs a reason comment too. Next steps, in order: `no-unsafe-*` after typed JSON-parse helpers exist; lint paths beyond `extensions` and `setup` (about 100 findings in the plain `.mjs` folders); `noUncheckedIndexedAccess` (about 3,500 compiler errors).

## Task runner (just)

[`just`](https://just.systems) is optional: the `justfile` names the same commands as this page, and CI does not use it (CI calls the `npm` and `ruff` commands directly, so a CI failure never depends on a local `just` install). Install it once:

- macOS: `brew install just`
- Linux: the distro package (`apt install just`, `dnf install just`), `cargo install just`, or a prebuilt binary from the just releases
- Windows: `winget install --id Casey.Just`

`just` lists the recipes (`just --list`). `just ci` runs what CI runs and a local machine can: it is `npm run test:ci`. The Windows shell is PowerShell (`set windows-shell` in the `justfile`). Recipe names use `-` because `just` does not allow `:`.

## Windows notes

Use `path.resolve` on drive-letter paths before comparing, `realpathSync.native` for short runner names, quote or
forward-slash paths interpolated into shell strings, simulate win32 in unit tests by injecting platform and
separator, never `shutil.rmtree` a `.git` dir (rename it), and keep POSIX-only mechanics in skip-marked tests.
